================================================================================
 LTE 모듈 판별 — INT-WDT 크래시 원인 격리 실험 (계획서)
 작성: 2026-07-07   대상: esp32c3-mini_gps
================================================================================

■ 목적 (한 줄)
--------------------------------------------------------------------------------
만성 INT-WDT 크래시가 "펌웨어" 때문인지 "LTE 모듈(하드웨어)" 때문인지를,
펌웨어를 고정하고 물리적 LTE 모듈만 바꿔가며 판별한다.


■ 실험 설계 (핵심: 펌웨어 고정, 모듈만 변수)
--------------------------------------------------------------------------------
공통 펌웨어(양 스텝 동일):
  - IDF 통합 관찰본 (idf_caltest, Block1~8 + HW-DIAG 크래시 카운터/부저/배너)
  - config: TX/RX 스왑(PIN_LTE_RX=4, PIN_LTE_TX=2) + DTR 반전(LTE_DTR_IDLE=HIGH)
    → 구 모듈이 통신되는 그 설정(=구 모듈 로직)을 양 모듈에 동일 적용.
  - CONFIG_RTC_CLK_CAL_CYCLES=576 (크래시 재현 설정)

  [Step A] 지금 연결된 장치 + 구(舊) LTE 모듈  → 위 펌웨어 플래시 → 크래시 관찰
     · 크래시 재현 안 됨  →  "옳은 펌웨어"로 간주 (이 조합은 크래시 없음).
     · 크래시 재현 됨      →  펌웨어/공통요인 의심 (아래 해석표 참고).

  [Step B] 크래시 나던 신(新) 모듈 + (동일) TX/RX·DTR 스왑 펌웨어 → 크래시 관찰
     · 크래시 발생  →  "하드웨어(모듈) 문제"로 간주 (펌웨어 동일한데 모듈만
                       바꿨더니 크래시 = 크래시는 모듈을 따라감).
     · 크래시 없음  →  모듈 무관, 다른 요인.

해석표(판정 논리):
     Step A(구)   Step B(신)    결론
     ─────────    ─────────    ───────────────────────────
     무크래시     크래시        → 신 모듈 하드웨어 문제 (핵심 가설 확증)
     무크래시     무크래시      → 스왑 펌웨어가 크래시를 막는다? (추가조사)
     크래시       크래시        → 모듈 무관, 펌웨어/보드 공통요인(전원/클럭)
     크래시       무크래시      → 구 모듈 쪽 요인 (드묾)


■ arduino CLI vs IDF — IDF로 결정
--------------------------------------------------------------------------------
결정: **IDF 통합본**으로 진행.
근거:
  1) HW-DIAG 크래시 카운터(NVS, 재부팅에도 유지) + 부저6회 + 배너 = 크래시
     관찰에 최적. arduino 필드/모듈러 본(15_field_v2, 15_a_modular)엔 카운터 없음.
     (카운터 있는 arduino 는 hwdiag_lte_buzz 뿐인데 그건 LTE 단독 블록임.)
  2) 전체 통합 앱(GPS/LTE/모션/슬립/recovery) = 실제 필드 동작에 가장 근접.
  3) CAL_CYCLES 제어 가능(현재 576). 4) 앱 로직은 15_a_modular 와 동일.


■ 크래시 판정 방법 (관찰)
--------------------------------------------------------------------------------
- 부저: 크래시 재부팅 시 빠른 6회. 클린 전원 시 길게 1회. (주 신호)
- 시리얼(drive_logger.py): 배너 "CRASHES=N"(재부팅에도 누적), 패닉 덤프
  "Interrupt wdt timeout on CPU0", reset_reason.
- 판정: 수 분 관측하며 CRASHES 증가율 / 부저6회 빈도. baseline(576)은 대략
  분당 1회 수준.
- ※ 크래시(INT-WDT)는 idle 에서 발생 = LTE 등록/신호와 무관하게 관측 가능.
  (CSQ=99/미등록이어도 크래시 관찰엔 지장 없음.)


■ 준비 상태 (작업 직전까지 셋팅 완료)
--------------------------------------------------------------------------------
- 펌웨어 빌드 완료: idf_caltest/build/caltest.bin (486KB)
  · config: RX=4/TX=2 스왑, DTR=HIGH, CAL=576, 통합본+HW-DIAG.
- 플래시 명령(크래시루프 대비 재시도):
    python -m esptool --chip esp32c3 --port COMxx --baud 460800 \
      --before default_reset --after hard_reset write_flash @build\flash_args
- 관찰: python drive_logger.py COMxx 115200
- 미실행(대기): 사용자가 장치 연결/모듈 장착 확인 후 플래시+관찰 진행.


■ 실험 결과 (2026-07-07)
--------------------------------------------------------------------------------
1) [초대형 발견] 관측된 "5분마다 재부팅"의 정체 = INT-WDT 하드크래시가 아니라
   recovery 의 의도적 esp_restart (BOOT_STUCK_RESTART_MS=5분, LTE 무-POST 시).
   reset_reason=3(SW), rst:0xc(RTC_SW). → 필드 "잦은 재부팅" 상당수가 이 LTE-stuck
   복구재시작이었을 가능성 큼 (INT-WDT 와 별개).
2) recovery esp_restart 비활성 후 재관찰 → 통합 앱은 사실상 무크래시:
   - sss(구모듈): ~2시간 연속 0크래시.
   - aa(신모듈): ~21분 후 wake=crash 1회(심한 프리즈, coredump 기록실패).
   → INT-WDT 는 바쁜 통합앱에선 극히 드묾(idle-WFI 적음). 잦은 크래시는 idle/최소빌드.
3) 모듈 판별은 교란됨: aa(1회) vs sss(0회)는 표면상 신모듈 HW 지지하나,
   aa=신모듈+aa보드개체+온라인TX부하 가 묶여 분리 불가.
   → 결정적 판정은 [미수행] 두 보드 간 "모듈 교차(swap)" 필요.
4) [배포] 위 안정 코드로 IDF 필드본을 양단말 플래시:
   CAL_CYCLES=0, recovery 재시작 30분 완화(HARD_RESET_LIMIT 10),
   LTE config 단말별(sss=swap / aa=native), HW-DIAG 유지, cdc.
   결과: aa=ONLINE/REG5 완전정상, sss=모뎀응답O·무신호(구모듈 안테나).


■ 되돌리기 메모
--------------------------------------------------------------------------------
- 필드본 recovery/CAL 은 부재중 정한 기본값(recovery 30분·CAL0). 운영본처럼
  하려면: BOOT_STUCK/STUCK_RESTART_TIMEOUT_MS=5분, HARD_RESET_LIMIT=2, CAL=576.
- 실험 후 신 모듈 정상운영 복귀 시 config 원복: RX=2/TX=4, DTR=LOW.
- 구/신 모듈 배선표: 구_LTE모듈_배선_DTR_정보.txt 참고.
