■ 쉬운 요약 (비전문가용) — 한눈에
--------------------------------------------------------------------------------
· ESP32-C3 칩은 "심장박동"인 내부 클럭(RC 오실레이터)으로 동작합니다. 그 클럭이
  순간 멈추면(스톨) CPU도 그 순간 멈춥니다. = 소프트웨어 잘못이 아닙니다.
· 멈춘 결과는 두 가지로 나타납니다:
    (1) 재부팅   — 감시장치(워치독)가 멈춤을 감지해 칩을 리셋. (흔함)
    (2) 완전 먹통(하드 프리즈) — 클럭이 아예 죽어 워치독마저 못 돌아 리셋도 안 됨.
        → 전원을 완전히 뺐다 꽂아야만 살아남. (더 심각)
· 두 증상 모두 뿌리는 같음: 클럭/전원이 순간 불안정.
· ★[2026-07-09 확정] 근본 원인 = **(B) PCB 전원 전달부** (접점/솔더/디커플링/레귤레이션).
  전원 격리 실험으로 확정: 같은 칩·같은 펌웨어를 **깨끗한 독립 전원(브레드보드)에 물리니 33분+
  무크래시**, 그런데 **PCB(제품 기판)에선 계속 크래시(수백 회)**. ⇒ **내부 클럭(RC 오실레이터)/
  실리콘은 정상, 크리스탈 교체 불필요.** RTC 캘리브레이션에서 자주 넘어진 건 "전압이 흔들릴 때
  그 지점이 가장 취약해서"일 뿐(발진기 결함 아님). (소프트웨어=CAL=0 는 빈도만 ~10배↓, 근본 아님.)
· ★[최종 모델] 크래시 = **전원 마진 부족(B)** + **LTE TX 전류 버스트(트리거)** 의 상호작용.
  레일 전압이 낮을수록 / 모뎀 전류가 클수록(신모듈 > 구모듈) 크래시가 잦음. clean 전원은 어느 모듈·
  어떤 TX 에도 무크래시(수십분+). 구모듈도 저-레일 배터리서 POST(TX) 중 크래시 실측됨(드묾).
  ⇒ 모듈/크리스탈 결함 아님 — **PCB 전원부가 LTE TX 전류 버스트를 못 버티는 것**이 핵심(모듈은 빈도만 조절).
· 크래시 순간 코드 위치는 우리 앱 코드가 아니라 저수준 시스템(초기엔 IDLE-WFI, 이후엔
  systick 타이머 ISR) = **앱 버그 아님은 확실.** (단 systick 은 워낙 자주 도는 지점이라
  "그 자체가 단일 원인"의 강한 증거는 아님 — "저수준=하드웨어" 방향만 확실.)


■ 한 줄 결론
--------------------------------------------------------------------------------
간헐적 재부팅/먹통의 원인은 **소프트웨어 버그가 아니라 하드웨어**입니다 (이건 확실).

멈춰 있고, 인터럽트/타이머가 300ms+ 처리되지 않아 워치독(INT-WDT)이 발동해 리셋됩니다.

  ★[2026-07-09 확정] 전원 격리 실험(standalone C3 clean power vs PCB, 동일 CAL=576)으로 (B) 확정:
   같은 펌웨어·같은 칩 rev 인데 PCB=crash-loop(252회) / clean power(격리전원, 모뎀 액티브)=0회.
   ⇒ 근본원인 = **(B) PCB 전원 전달부**(접점/솔더/디커플링/레귤레이션). 내부 RC 오실레이터/실리콘
     무죄, 크리스탈 불필요. RTC 캘리브레이션 coredump 는 "전압 흔들릴 때 그 busy-wait 이 가장
     취약한 지점"이라 거기서 넘어진 것(발진기 결함 아님). → 상세: 아래 "■ ★★★ 결정 실험" 섹션.
   [이전 두 갈래 프레이밍 (A)클럭 / (B)전원 중 (B)로 판정 완료.]
   [보강] 트리거 = LTE TX 전류 버스트(어느 모듈이든). 크래시율 ∝ 전류량(신모듈>구모듈) · 레일 낮을수록↑.
    구모듈도 저-레일 배터리 POST(TX) 중 크래시 실측(sss). ⇒ "모듈 vs 전원" 이분법이 아니라
    (레일 마진)×(TX 전류량)이 율을 정하는 스펙트럼 — 전원이 근본, 모듈은 율만 조절. (상세: 아래 "■★★★" 두 섹션.)

  ★★★[2026-07-14 필드 최종 해결 — 종결] 신PCB + 신모뎀 3단말에 최종 운영본(CAL=576 유지) 올려
   **하루 실운행 → 크래시 0건.** 벤치서 약전원 단말을 crash-loop 시키던 그 CAL=576 에서도 0건 =
   "소프트 아님, HW 전원 마진 근본" 이 필드에서 최종 확정. 한 단말은 모뎀 개체 불량(CSQ=-1, 물리
   전원차단·12s hardCycle 다 무효)이었고 **모뎀 교체로 즉시 정상**(동일 펌웨어가 다른 단말선 정상)
   = 모뎀 HW 불량 확정. ⇒ **신PCB(전원 전달부 마진 확보) + 정상 모뎀이면 CAL 완화 없이도 무크래시.**
   → 조사 종결. (최종 운영본 사양/버그헌트 10건: 아래 "■ 최종 운영본(2026-07-14)" 섹션.)

■ 변인 격리 대조 실험 — LTE / 부저 배제 (2026-07-06 추가, 결정적)
--------------------------------------------------------------------------------
HW팀이 LTE 모듈을 의심하여, 블록을 하나씩 제거하며 크래시 재현 여부를 대조:

  실험 1) LTE 단독 구동본 (GPS/모션/I2C/슬립 전부 제거, LTE 만 bringup+반복 POST/TX)
     → 크래시 재현 (~1분당 1회). coredump: Crashed task 'IDLE',
       esp_vApplicationTickHook ← xPortSysTickHandler ← SysTickIsrHandler.
     → 크래시가 LTE 코드 실행 중이 아니라 IDLE/systick 에서 발생.
       LTE 하드부하(TX)를 해도 크래시율이 늘지 않음.

  실험 2) LTE 완전 OFF + 부저(GPIO1) 완전 OFF (순수 idle 루프만)
     → PIN_PWR_EN(GPIO6)=HIGH 로 공유레일 차단(LTE/GPS 무전원),
       GPIO1(부저핀)=LOW 고정(활동 없음). 그래도 크래시 재현.
     → 시리얼 패닉: "Interrupt wdt timeout on CPU0", MEPC=0x403853d6.
       해석(동일 빌드 elf):
         #0 esp_vApplicationTickHook  freertos_hooks.c:34
         #1 xPortSysTickHandler       port_systick.c:233
         #2 SysTickIsrHandler         port_systick.c:149  ← systick 타이머 ISR
     → 실험 1 과 완전히 동일한 백트레이스.

  결론: LTE 모듈·부저(GPIO1) 모두 배제해도 동일 크래시(systick 타이머 ISR 에서
        INT-WDT)가 그대로 발생. → **LTE 무관, 부저/GPIO1 무관.**
        원인은 특정 주변 블록이 아니라 시스템 타이머/클럭 도메인의 하드웨어 스톨.

  추가 정황(전원 무결성): LTE-OFF 검증 중 단말을 물리적으로 흔들자 crash-type
        리셋(부저 6회 알람)이 유발됨. 배터리/USB 접점 흔들림 → 순간 전압딥(브라운
        아웃/글리치)으로 추정. → 전원 접점/디커플링 점검 우선순위 상향.


■ 이것이 하드웨어(소프트웨어 아님)인 이유
--------------------------------------------------------------------------------
1. 크래시 태스크가 **IDLE 태스크**입니다. 우리 애플리케이션 코드(GPS/LTE/I2C 등)가
   전혀 실행되고 있지 않은, CPU가 유휴 상태로 인터럽트를 기다리는 순간에 발생.
   → 소프트웨어 버그라면 특정 애플리케이션 코드 경로를 가리켜야 함. 그렇지 않음.

2. INT-WDT는 "인터럽트가 정상적으로 처리되지 못함"을 감지하는 워치독입니다.
   CPU가 WFI로 대기 중인데 이게 발동했다 = **CPU를 깨울 타이머 인터럽트가 오지
   않았다** = 인터럽트를 구동하는 클럭/타이머가 순간 멈춤(스톨).

3. 소프트웨어 워치독 타임아웃을 60초로 매우 길게 잡았는데도 발동 = 수 밀리초짜리
   블로킹 I/O 대기가 아니라 실제 장기/영구 프리즈.

4. 소프트웨어 측 후보는 모두 배제됨: I2C(Wire), USB CDC, LTE AT 폴링, GPS NMEA 등
   애플리케이션 코드는 크래시 시점에 실행되고 있지 않았음(IDLE).


■ 소프트웨어 완화책과 그 한계 (참고)
--------------------------------------------------------------------------------
- RTC 슬로우클럭(내부 RC) 캘리브레이션 경로가 이 스톨에 가장 민감함이 확인됨.
  ESP-IDF 옵션 CONFIG_RTC_CLK_CAL_CYCLES=0 (캘리 비활성)로 빌드 시
  재부팅 빈도가 약 10배 감소(crash-loop → ~1/2분).
- 그러나 **완전 제거는 안 됨.** 캘리 경로를 없애도 IDLE 상태에서 동일한 클럭/
  인터럽트 스톨로 INT-WDT가 저빈도로 계속 발동.
  → 근본 해결은 소프트웨어가 아니라 하드웨어에 있음을 재확인.


■ 추가 확증 (2026-07-08) — CAL=0 배포본에서도 잔존 + "하드 프리즈" 극단 사례
--------------------------------------------------------------------------------
CAL=0 완화본을 실단말(aa, sss)에 배포·운용 중에도 동일 크래시가 잔존함을 재확인.
진단용으로 reset_reason 을 NVS 에 누적 기록(USB 없이 배터리 재부팅도 캡처)해 관찰:

  1) 재부팅 = 감지된 브라운아웃 아님 (BROWNOUT 카운터 0). 실제는 INT-WDT + Task-WDT
     (둘 다 워치독) → 앱 버그·완전 브라운아웃 아닌 "워치독성 스톨".
     ※ 단 BROWNOUT=0 이 (B)접점 글리치를 배제하진 못함 — 순간 접점 글리치는 브라운아웃
       문턱을 깔끔히 못 건드려 검출 안 될 수 있음(오히려 reset_reason=UNKNOWN 로 나타남).

  2) [aa] Task-WDT 로 리셋된 건의 coredump 백트레이스 (동일 SHA 빌드):
       Crashed task: '' (인터럽트 컨텍스트 — 특정 태스크 아님)
       #0 esp_vApplicationTickHook   freertos_hooks.c:35   ← SysTick 타이머 훅
       #1 xPortSysTickHandler        port_systick.c:199
       #2 SysTickIsrHandler          port_systick.c:148    ← systick 타이머 ISR
     → reset_reason 이 Task-WDT(loop hang)로 찍혀도, 실제 멈춤 지점은 앞선 IDLE WFI
       건과 동일한 "SysTick 타이머 ISR". 즉 loop 코드가 아니라 타이머/클럭 도메인이
       멈춤. (앞의 IDLE coredump 3건과 같은 시그니처 — 라벨만 다르고 뿌리는 동일.)

  3) [sss] 극단 사례 — "하드 프리즈(완전 정지)":
     - 단말이 완전 무응답: 시리얼 출력 0, 게다가 esptool 조차 연결 실패
       ("Failed to connect to ESP32-C3: No serial data received"). USB 포트는
       잡히나(전원 있음) 칩이 어떤 것에도 응답하지 않음.
     - 해석: 클럭이 완전히 멈춰 CPU 가 얼고, 워치독마저 못 돌아(워치독도 클럭 필요)
       리셋조차 안 됨 → 영구 정지. 소프트 리셋(RTS)으로도 회복 불가, 완전 전원차단·
       재인가(power-cycle)만 회복됨.
     - 즉 같은 클럭 스톨이 더 심해지면 "재부팅"을 넘어 "먹통"이 됨 = 최악 형태.

  → 종합: 동일한 저수준 HW 문제(클럭 도메인 (A) 또는 전원/접점 무결성 (B) — 상단 두 갈래)가
     심각도에 따라 (a) 워치독 재부팅(INT-WDT/Task-WDT — aa)  (b) 하드 프리즈(먹통 — sss)로
     나타남. 소프트웨어(CAL=0)는 빈도만 낮출 뿐. **근본원인 (A)/(B) 확정은 접점/솔더 배제 후.**

  4) [보강] INT-WDT/Task-WDT 설정값 + 패닉 헤더 원문 (해석 근거):
     - CONFIG_ESP_INT_WDT_TIMEOUT_MS = 300  → 인터럽트가 300ms 이상 처리 안 되면 INT-WDT
       발동. 즉 크래시 = "시스템 타이머/인터럽트가 300ms 넘게 멈췄다"는 의미.
     - CONFIG_ESP_TASK_WDT_TIMEOUT_S = 5 (기본, IDLE task CPU0 감시) / loop task-WDT 는 앱이
       60s 로 재설정. Task-WDT 발동 = 감시 대상이 그 시간 동안 못 feed = 장기 스톨.
     - CONFIG_RTC_CLK_SRC_INT_RC = y  (외부 32.768kHz 크리스탈 없음, 내부 RC 사용) — 재확인.

     동일 시그니처), loopTask 는 lte::httpPost(AT+SHREQ = POST = TX) 중. device_uid=sim-47743482(sss 확정).
   · ⇒ 위 2×2 의 "구모듈=무크래시 / 신모듈=필요 트리거" 는 정정. **구모듈도 "저-레일 + TX(POST)" 면 크래시함.**
   · ★최종 해석: 크래시 = **순수 전원 마진 (B) 의 확률적 현상.** LTE TX 전류 버스트(어느 모듈이든) = 트리거,
     **크래시율 ∝ 전류량(신모듈 > 구모듈).** 신모듈=빈발(crash-loop), 구모듈=드묾(저확률·0 아님 — sss 배터리서
     실측 발생; aa 배터리 12분 0 도 "저확률"이지 0 아님). clean power 는 어느 모듈도 무크래시 = **전원이 근본**
     재확인(모듈 종류는 크래시율만 조절, 별개 원인 아님).
   · ※ 앞 절 "모듈 무관 순수 PCB 전원"(1차) → "신모듈 필요 트리거"(2차) → 본 보강 "전류량이 율을 조절하는
     스펙트럼, 전원이 근본"(최종). 관측 누적에 따른 정련 과정.

  ■ 최종 확증 (2026-07-09) — standalone(clean) + 신모듈 + 최대 TX(깊은 실내) 30분 무크래시:
   · 깊숙한 실내(약신호) = 모뎀이 RF 최대 출력으로 TX → 전류 버스트가 최악. 그 최악 TX 부하를 clean power
     가 **30분 연속 버팀(POST 지속, 크래시 0).** ⇒ 정상 전원은 어떤 TX 부하도 감당함.
   · 반면 우리 PCB 는 신·구 모듈 불문 크래시(구모듈은 자체 기성품 브레이크아웃이라 그 조합[sss+구모듈]의
     크래시 = 우리 보드 전원/TX 라인 탓). ⇒ **PCB 보드측 TX/전원 라인이 근본 원인 — 최종 확정, 모듈 무관.**
   · HW 조치(확정): 그 **TX/전원 라인(디커플링·레귤레이션·접점·전압 드롭)이 LTE TX 전류 버스트를 견디도록**
     수정. (clean 레일은 최대 TX 30분도 버팀 = 모듈·칩·크리스탈 결함 아님.)


■ ★★★ 3번째 보드 확증 (2026-07-11) — HW팀 데모 PCB: USB약전원=브라운아웃 / 배터리=135TX 무크래시
--------------------------------------------------------------------------------
대상: HW팀 전달 "데모 버전 PCB" (MAC ac:a7:04:d1:91:64 — aa/sss의 68:ee:8f 와 별개 칩).
      lte-only 진단본(railOn=PWR_EN LOW + CBC VBAT 로깅 + bringUp RST카운터), 구모듈 RX4/TX2, CAL=576.

  ■ USB 포트 only (약전원):
   · 부팅 railOn(GPS+LTE 공유레일 인러시) 순간 **명시적 BROWNOUT** — reset=9(ESP_RST_BROWNOUT),
     ROM 로그 "E BOD: Brownout detector was triggered", 크래시-루프(br 카운터 누적 →5).
   · 동시에 모뎀이 **"UNDER-VOLTAGE WARNNING" URC**(SIM7080 자체) 방송 → 우리 healthy() 가 UV abort →
     AT 중단. 등록/TX 진행 불가. (전원·모뎀 양쪽이 저전압을 스스로 신고)

  ■ 배터리 (충분전원):
   · 부팅 안정, 브라운아웃·UNDER-VOLTAGE 소멸. 모뎀 VBAT = **4.09V**(AT+CBC 실측, 안정).
   · SIM 재삽입 후 REG=3(거부)→**REG=5(로밍 등록)**→ONLINE. 2초 POST(TX) **5분간 135회 200성공**
     (실데이터 업링크 TX 135버스트) + **크래시 0** — RST[br=5 iw=0 tw=0 pn=0 sw=0 ot=0] 불변.

  ■ 의미(전원 마진 모델 3번째 독립 확증):
   · 데모 PCB의 **유일한 실패 = USB 약전원 인러시 브라운아웃**. 배터리(충분전원)면 **최대 실TX 135회에도 무크래시**
     = standalone clean-power(30분 무크래시)와 동일 거동. ⇒ "전원 충분=무크래시 / 공급원 약함=크래시" 재확인.
   · 단 트리거 지점 = **부팅 인러시(브라운아웃)** 로, aa/sss 의 **TX-중 RTC-cal(INT-WDT)** 와는 다른 앞단 증상
     (같은 "전원 마진" 계열, 다른 트리거). 데모 PCB 는 배터리에선 aa/sss 보다 튼튼(TX중 무크래시).
   · ⇒ aa/sss 의 TX-중 크래시는 **그들 PCB 전원경로 특유의 약점**. 데모 PCB 전원경로 마진이 상대적으로 좋음.

■ HW/PCB 팀 권장 검토 사항 (싼 것부터 — 단일 원인 확정 전)
--------------------------------------------------------------------------------
⚠️ 두 갈래(전원/접점 무결성 vs 클럭 도메인)를 열어두고, **싸고 흔한 것부터** 배제 권장.
   특히 "USB면 안정 · 배터리면 재부팅 · 흔들면 재부팅 · BROWNOUT 카운터=0" 조합은
   접점/냉납 쪽을 더 지지함 (USB 가 부실 접점을 우회해 안정화된다는 해석).

1. [최우선·저비용] 접점/솔더링 무결성 — 배터리 홀더/커넥터, USB 커넥터, 주요 부품(ESP·
   모뎀·디커플링 캡) 냉납(cold solder)·미세 크랙 점검. 재현: 보드/커넥터를 눌러가며(접점
   압력) crash-type 리셋이 나는지. (흔들림 재현 + USB 안정화가 이쪽을 시사.)
2. [저비용] 전원 무결성: VDD 디커플링(특히 오실레이터/RTC 도메인), 모뎀 TX/인러시 등 큰
   전류 스파이크 시 순간 전압 딥/글리치 계측. (접점 글리치가 브라운아웃 문턱을 깔끔히 못
   건드려 BROWNOUT 미검출 + reset_reason=UNKNOWN 으로 나올 수 있음.)
3. [조건부·고비용] RTC 슬로우클럭 소스(내부 RC 150kHz): 위 1·2 로 원인이 안 잡히고 클럭
   도메인이 실제 원인으로 좁혀질 때만 — **외부 32.768kHz 크리스탈** 검토. ※ ESP32-C3 32K 핀
   =GPIO0/GPIO1, 현재 GPIO1=부저 → 채용 시 부저 핀 재배치 등 보드 리비전(고비용). 확정 전
   착수 비권장.
4. (SW 저비용 대안) sdkconfig RTC 클럭소스를 INT_8MD256(8MHz RC/256)로 변경 검토 —
   크리스탈 없이 내부 RC보다 안정적일 수 있음(슬립 전류 트레이드오프). 리비전 전 시도 가치.
5. 내부 RC 오실레이터 안정성 계측(지터/드리프트/순간정지)은 3번 갈래 확인 시 병행.

--------------------------------------------------------------------------------
목표: 크래시 순간 전원/GND에서 무슨 일이 일어나는지 파형으로 포착. 개발자 실측상 **ESP 3.3V DC 는
      크래시 때 안 떨어짐**(멀티미터) → DC 강하가 아니라 **고주파 노이즈/트랜지언트**를 봐야 함.
      (내부 RC 는 핀이 없으니 전원/GND 를 찍는다.)

장비: GW Instek GDS-1052-U (50MHz 2CH, USB CDC). 제어 스크립트/의존/명령/트리거·해석 전부 =
      **Desktop\esp32c3-mini_gps\GDS-1052-U\ 폴더 (스크립트 5종 + SCOPE_DEBUG_RUNBOOK.md).**
      에이전트는 gds_setup.py 로 설정 푸시, gds_capture.py 로 파형→PNG 저장 후 PNG 를 직접 판독.
      프로브 10x → 스코프 :CHAN:PROB 10 필수. (스코프 Code10 시 USB 재연결/전원재기동)

프로빙 우선순위 (물리: 팁=신호, 짧은 GND클립=옆 GND):
  1순위 ESP 3.3V VDD  — AC 커플링 + 미세 vdiv(20~50mV/div) → TX 순간 리플/스파이크. (DC로는 안 보임)
  2순위 모뎀 VBAT     — DC → LTE 2A TX 버스트 sag. 트리거 소스로 사용.
  ★핵심 2CH 동시: CH1=3.3V(AC 미세), CH2=VBAT(DC). CH2 VBAT falling 트리거 → TX 순간 CH1 글리치 상관 관측.
  3순위 그라운드 바운스 — ESP GND ↔ 전원 GND 전위차 @ TX.
  트리거 대상 = LTE-only(idf_lteonly)의 2초 주기 POST(TX), 또는 부팅 모뎀 파워온 인러시.

해석: 3.3V AC 스파이크 큼 → 전원노이즈가 RC 교란(디커플링/레귤 보강) · VBAT sag+3.3V 상관글리치 →
      전류버스트 마진부족 확증 · 어느 레일도 안 움직임 → RF/EMI(차폐/안테나 이격) · 3.3V 큰 DC강하 → 브라운아웃.
※ 스코프가 이 PC 에선 Code10 으로 안 붙음 → 스코프가 붙는 다른 기기에서 GDS-1052-U 폴더째 옮겨 실행 권장.
