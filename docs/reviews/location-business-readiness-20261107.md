## 결론

디스크 정리, 외부 알림 훈련, API/PDF 실행 계정 분리는 확인됐다. 그러나 **사업 준비 전체에서 남은 것이 보존 정책과 18차 배포뿐인 상태는 아니다.** 18차 자체에도 기록 귀속, 건별 증거, 동의 철회, 손실 방지에 대한 보완이 필요하다. 기록 OFF 상태의 배포 절차를 작성하는 것은 가능하지만, 그 배포를 취급대장 운영 완료로 판단하지 않는다. 우선 보완 후 고정된 수정본으로 릴리스 절차를 준비하는 편이 낫다.

이 검토는 기술 구현과 제출 문구의 일치 여부를 확인한다. 법적 지위, 위탁/제3자 제공 구분, 회사 정책의 최종 확정은 위치정보관리책임자와 담당 전문가의 검토 대상이다. 첨부된 비밀번호 규칙·2인 승인 표는 이번 프로젝트 요구사항으로 대조했으며, 모든 서비스에 동일하게 강제되는 법문이라고 해석하지 않았다.

## 2. 18차를 활성화하기 전에 보완할 사항

### P1 — 기록 대상의 귀속이 현재 소유권에 의존한다

`src/services/access_ledger.rs:332` 부근은 메모리에 모은 기록을 DB에 쓸 때 `devices.owner_id`를 다시 조회한다. `Target::Device`의 `subject_user_id`가 이 값으로 결정된다. 기본 flush 간격은 30초이고 DB 오류 시 더 늦어진다. 조회 후 기록 저장 전 SIM 소유자가 A에서 B로 바뀌면 A의 기록이 B로 귀속될 가능성이 있다.

또한 회사 차량 기록은 회사 소유자 계정을 대상으로 삼는다. 회사 소유자와 실제 운전자는 같은 정보주체라고 단정할 수 없다. 이는 SIM 중심 이력을 하드웨어 UUID로 바꿨다는 뜻은 아니다. **SIM 이력의 기준은 유지되지만 감사 기록의 정보주체 매핑이 충분하지 않다.**

조치: 권한 확인·응답 생성 시점의 실제 행위자와 대상 정보주체/배정 구간을 확정해 이벤트에 넣는다. SIM·차량·하드웨어 인증 ID·운전자·조회자를 분리한다. 과거 기록 조회는 해당 기록의 당시 귀속을 사용하고, 복수/미확정 정보주체를 현재 소유자로 임의 치환하지 않는다. 소유권 변경과 flush 경합, 차량 배정 변경, 회사 운전자 열람 시험을 추가한다.

### P1 — 건별 기록 요구와 1시간 집계는 다르다

현재 표는 한 시간의 최초/최종 시각, 횟수, 합쳐진 조회 기간만 남긴다. 3회 이상의 조회에서 중간 시각·개별 범위는 복원할 수 없다. 제3자 제공 통보와 해당 제공 건의 대응 관계도 부족하다.

1시간 집계가 모든 경우 법적으로 불가능하다고 단정하는 것은 아니다. 다만 사용자가 요구한 건별 추적·제공 일시·단계별 이력의 증거로는 부족하다. 건별 이벤트를 원장으로 두고 시간 집계는 화면/통계 용도로 유지하는 방안을 권한다. 실시간 스트림은 무엇을 한 제공 단위로 볼지 정하고 시작·종료·범위·건수·실제 수신자를 연결해야 한다.

`every_recorded_route_is_registered_and_uses_a_stored_value` 시험은 목록의 규칙이 라우터에 존재하는지만 확인한다. 새 위치 응답 경로를 추가하고 기록 목록을 빠뜨리는 반대 방향 누락은 검출하지 못한다. 위치 응답 경로 전체의 분류를 강제하는 검증이 필요하다.

### P1 — 동의 철회에도 6개월 이내 기록 삭제를 막는다

`migrations/0100_location_access_log.sql:54` 및 coverage 트리거는 6개월 미만 DELETE를 일률 거부한다. 보존 설정도 185일 미만을 거부한다. 일반 보존기간과 동의 철회에 따른 삭제는 같은 경로가 아니다.

[위치정보법 제24조 제4항](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1029559327)은 동의 철회 범위의 개인위치정보와 확인자료 파기를 규정한다. 이를 단순히 회사가 선택하는 ‘6개월 유지 또는 조기 삭제’로 두지 않는다. 철회에 적용되는 범위·다른 법률상 별도 보존 근거를 검토하고, 정당한 철회 처리가 트리거 때문에 불가능해지지 않도록 승인된 삭제 경로를 마련해야 한다. 다른 목적의 보안 접근기록/권한 변경 기록과도 구분한다.

### P1 — 기록 유실을 설명할 수는 있지만 막지는 못한다

`access_ledger.rs:221` 이후 기록기는 메모리 큐/집계를 30초마다 저장한다. 큐가 차면 drop 수를 남기고, DB 오류이면 재시도한다. 정상 종료 flush와 중단 구간 표시는 장점이다. 그러나 비정상 종료 시 마지막 미저장 이벤트를 잃는다. DB 장애가 있으면 손실 가능 구간은 정상 상태의 30초보다 길어질 수 있다.

민감한 관리·파일 제공·파기 실행에는 내구성 있는 이벤트 저장을 먼저 보장하고, 기록 저장 실패 때 실행을 막을 작업을 정한다. 일반 조회/실시간 전송은 durable outbox/spool과 손실·지연 알림을 설계한다. 타임아웃·디스크 부족·DB 재시작·강제 종료 시 실제로 무엇이 남는지 검증한다. 감시도 로그 기록기 오류와 적체를 별도로 보아야 한다.

### P1 — 보안 접근기록과 취급대장이 모두 완성된 것은 아니다

- 성공 응답만 기록한다. 실패·거부 요청은 취급대장과 구분된 보안 감사 기록에 남겨야 한다.
- 외부 전송은 시도 시점이며 성공 여부가 없다. 시도/전달 성공/실패를 구분한다. FCM 전송 API 성공을 이용자의 통보 확인으로 간주하지 않는다.
- 공유 링크는 링크 번호만 남아 실제 수신자 확인에 한계가 있다. 익명 공개 링크를 법인 운전자 위치 제공의 기본 수단으로 삼기 전에 통제 범위를 정한다.
- 내부 처리·브라우저 직접 주소 변환·별도 레거시 프로세스의 누락 범위가 문서에 명시돼 있다. 이를 포함/제외하는 근거와 실제 데이터 경로를 정리한다.
- 트리거는 일반 UPDATE/DELETE를 막지만 테이블 소유자는 트리거를 바꿀 수 있다. 운영 API의 DDL 권한 제거, 마이그레이션 역할 분리, 별도 기록 저장소/무결성 검증을 검토한다.
- 관리자 대장 화면은 아직 없다. API 구현과 캡처 가능한 운영 화면은 구분한다.

### P1 — 로그 토큰 노출과 잘못된 보관 안내

웹 `src/ws.js:81`은 접속 토큰을 URL query에 넣는다. 18차 문서는 nginx 로그에 이 토큰 및 공유 링크 토큰이 남는 것을 확인했다. 마스킹과 안전한 인증 전달 방식이 필요하다. 기존 로그의 노출 범위·토큰 유효기간을 확인하고 필요한 회수/보호 조치를 정한다. 이 판단은 운영 로그 보관기간을 늘릴지와 무관하게 먼저 할 수 있다.

`src/services/privacy_location_facts.rs`의 `NOT_RECORDED`는 ‘보관 기간(1년)이 지난 위치 기록은 남아 있지 않다’고 안내하지만, `routes/devices.rs:1815`는 `retention: permanent`이고 실제 운영 TimescaleDB에 위치 retention job이 없다. **현재 제공 문구를 사실과 맞춰야 한다.** 실제 삭제 여부를 확인하지 않고 1년 뒤 파기된다고 안내하지 않는다.

## 4. 법령과 보관 정책에서 구분할 사항

현행 [위치정보 보호조치 기준](https://www.law.go.kr/LSW/admRulLsInfoP.do?admRulSeq=2100000279386)은 업무별 최소 권한, 권한 변경 기록, 취급대장, 접근사실, 보안 프로그램, 안전한 저장·전송을 각각 다룬다. 취급대장 일반 보존 최소 6개월, 접근사실 최소 1년, 권한 부여·변경·말소 기록 최소 5년을 구분한다. 운영 로그 전체를 90일 보관하는 것으로 이를 대체할 수 없다.

[개인정보 안전성 확보조치 기준 제8조](https://law.go.kr/admRulLsInfoP.do?admRulSeq=2100000281400)의 2년 보관 대상 여부도 확인해야 한다. 따라서 13개월을 모든 경우의 정답으로 확정하지 않는다. 관리자 접근기록에는 실제 식별자·접속지·시각·업무·처리 대상이 필요하며, IP는 신뢰하는 프록시에서 확정한다.

[위치정보법 제19조](https://law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1015334231)의 주체가 지정하는 제3자 제공에 해당하면 수신자·일시·목적 통보가 요구된다. 법인 운전자/회사/우리 서비스의 지위와 동의 범위를 먼저 정한다. 일반 알림 OFF나 일괄 24시간 제한을 필수 통보에 그대로 적용하지 않는다. 묶음 통보는 법령상 요건·주체의 동의에 맞추며 임의로 1시간 집계를 그 동의로 대체하지 않는다.

## 5. 관리자 PC 별도 네트워크 계획

사용자 계획은 타당하다. 다만 공인 IP는 네트워크를 식별할 뿐 특정 사람/PC까지 보증하지 않는다.

```text
개발자 PC
  → 개인별 인증 + MFA + 허용된 VPN/원격 접속
전용 관리자 PC (별도 고정 공인 IP, V3, 잠금/패치, 원격 세션 이력)
  → 지정 IP + 가능한 장치 인증 + 관리자 개인 계정 + MFA
GPS 관리자 웹/API 및 SSH
```

- VPS의 일반 앱/단말기 HTTPS는 계속 서비스하되 관리자 URL/API와 SSH는 별도 제한한다. 관리자 페이지 메뉴만 숨기는 것은 차단이 아니다.
- 개발자가 관리자 PC에 접속해도 본인 계정으로 작업한다. 관리자 공용 계정·공유 SSH키·공유 MFA로 합치지 않는다. 원격 접속자와 웹/SSH 행위자를 연결할 수 있게 한다.
- RDP를 인터넷 전체에 개방하지 않는다. 원격 접속 시작/종료·실패, 파일 전송/클립보드 정책, 자동 잠금·접속 만료를 설정한다. VPS의 IP가 관리자 PC로 보인다는 이유로 개발자의 행위 기록을 생략하지 않는다.
- 책임자의 승인과 관리자의 실행은 서로 다른 계정이어야 한다. 자기 승인·승인 후 대상/범위 변경·재사용·만료된 승인 실행을 서버에서 거부한다.
- 정규 동의 범위의 자동 서비스 제공과 예외적 외부 제공/수동 파기를 구분해 불필요한 매회 수동 결재를 만들지 않는다. 이번 표의 수동 절차는 **조회·검토 → 책임자 승인 → 관리자 실행 → 결과 검증·기록**이다.
- 자동 보존기간 파기는 사전 승인된 정책을 버전으로 기록하고 실행 결과를 남긴다. 수동 예외 파기는 2인 승인 범위로 구분한다.
- 관리자 IP 변경·회선 장애에 대비해 Cafe24 콘솔 등 별도 복구 경로를 준비하고, 예외 접근의 사유·승인·만료를 남긴다. 지정 IP 미준비 상태에서 운영 접속을 무작정 차단하지 않는다.
- 방화벽 변경 전에 공유 VPS의 다른 프로젝트 포트를 서비스별로 분류한다. GPS와 무관하다고 일괄 차단하지 않는다. 사업자용 운영/관리 경계를 확실히 하려면 GPS 전용 서버로 분리하는 방안도 검토한다.

이번 검토에서 정책을 임의 확정하거나 기능/운영을 변경하지 않았다. 개발 가능한 항목을 회사 결정 대기로 모두 묶을 필요는 없다. 역할·MFA·로그 비밀값 차단·기록 귀속·원장 내구성·보관기간 적용 엔진·검증 환경은 먼저 준비할 수 있고, 실제 보유기간/동의/제공 범위와 운영 활성화는 승인된 정책에 맞춘다.

## 8. 인계 문서 정합성 보완

- HANDOFF의 현재 운영 표는 17차이나 그 아래에 ‘위 상태는 16차’, ‘VPS 여유 약4.8GiB’가 남아 있다. 역사적 수치임을 분리하고 현재 확인은 17차/8.8G로 정리한다.
- 18차 문서의 ‘운영자 로그인/IP가 남지 않는다’는 표현은 정밀화한다. 실제 `login_attempts`는 존재하지만 성공 시 실패 이력을 지우고 1일 후 정리하는 임시 방어 기록이므로 장기 감사 요건을 충족하지 못한다.
- ‘기록되지 않는 처리’의 1년 자동 파기 안내를 운영 영구 보관 상태와 대조해 정정한다.
- 완료된 디스크 정리를 인프라 문서의 별도 미완료 항목처럼 읽히지 않도록 구분한다.
- 외부 감시의 ‘완료’는 시험한 두 경로의 알림 수신 완료이며 사무실/VPS 동시 장애 대응까지 완료한 뜻이 아니다.
