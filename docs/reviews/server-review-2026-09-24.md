# 서버 전반 검토 및 prod/dev 비교 — 2026-09-24

이번 작업은 검토다. 펌웨어·서버 소스 수정, 배포, 서비스 재시작, 운영 DB 쓰기, 테스트 메시지·결제·장치 명령 전송은 수행하지 않았다. 이 보고서만 저장했다. 빌드 및 재현용 임시 파일은 로컬에 생성했다.

## 1. 우선 수정할 문제

P1은 데이터 격리·인증·핵심 정확성 때문에 우선 처리할 항목, P2는 기능 오류·운영 신뢰성 개선 항목이다. 조건부 문제에는 발생 조건을 명시했다.

### 1) [P1] 공유 링크의 과거 위치 조회가 소유자 경계를 적용하지 않는다

- 근거: `gps-tracker-api/src/routes/share.rs:296`의 `public_locations`, `:338`의 `public_daily_stats`는 `device_id`로만 조회한다. `resolve_token`은 유효기간·폐기 여부를 확인하지만 데이터 소유자를 반환하지 않는다.
- 일반 위치 조회는 `locations.rs:143`에서 `user_id`를 제한한다. 공유 경로에는 이 제한이 빠져 있다.
- 재현 조건: A가 기록을 남긴 장치를 기록 삭제 없이 해제 → B가 페어링 → B가 새 공유 링크 발급. 이 새 링크는 남아 있는 A의 과거 기록까지 조회할 수 있는 쿼리 구조다. A의 기존 링크 폐기와는 별개의 문제다.
- 현재 DB 관측: 현재 소유자와 `user_id`가 다른 행 476개는 모두 `user_id=NULL`이었다. 타인 소유 이력의 실제 유출이나 공격 발생을 확인한 것은 아니다.
- 수정 방향: 공유 발급자·현재 소유권·페어링 시점을 확인하고 일반 조회와 동일한 데이터 범위를 적용한다. 공유 조회도 공통 위치 조회 계층을 사용한다.

### 2) [P1] 로그아웃 후 React Query 캐시가 다른 계정에 재사용된다

- 근거: `gps-tracker-web/src/api.js:36`의 `clearTokens()`는 토큰과 일부 별도 캐시만 지운다. React Query 클라이언트는 유지된다.
- `state/keys.js:14`의 `me`, `:19`의 `devices`, 임차인·예약 등 키에 계정 구분이 없다. 기본 `staleTime`은 30초다.
- 같은 SPA에서 A 로그아웃 → B 로그인 시 A의 응답을 신선한 캐시로 판단할 수 있다. 프로필 로그아웃은 전체 페이지를 다시 로드하지 않는다.
- **로컬 재현 성공:** 실제 `api.js`, query 설정·키를 실행했다. A의 `me`를 저장하고 B로 전환한 다음 조회하자 A의 값이 반환됐고 B용 fetch는 0회였다.
- 수정 방향: 계정 전환 시 진행 중 쿼리 취소와 사용자 데이터 캐시 제거를 함께 수행하고, 쿼리 키를 사용자/세션으로 구분한다.

### 3) [P1] 이전 계정의 늦은 refresh 응답이 새 계정 로그인을 덮어쓴다

- 근거: `gps-tracker-web/src/api.js:118`은 요청 시작 때의 세션이 여전히 유효한지 확인하지 않고 `activeStorage() || s`에 갱신 토큰을 쓴다.
- 재현 조건: A refresh 요청 진행 → 로그아웃 → B 로그인 → A refresh 응답 도착.
- **로컬 재현 성공:** B의 토큰이 A의 갱신 토큰으로 교체됐다. 로그아웃만 한 경우에도 지운 세션을 다시 만들 수 있는 구조다.
- 수정 방향: 인증 세대 번호와 요청 당시 refresh 토큰을 비교해 이전 응답을 폐기하고, 로그아웃 때 진행 중 갱신을 취소한다. 여러 탭의 refresh 회전 경쟁도 함께 다룬다.

### 4) [P1] 장치 ingest가 식별자를 인증 수단으로 취급한다

- 근거: `gps-tracker-api/src/routes/ingest.rs:108`은 인증 추출기·장치 서명 없이 payload를 받고, `:125` 이후 UID/ICCID로 기존 장치를 찾는다. `api_key_hash`는 빈 값으로 생성된다.
- 실제 nginx는 펌웨어를 위해 평문 HTTP `/ingest`를 허용한다. 별도의 장치 인증 제한은 해당 경로에서 확인되지 않았다.
- 장치 UID/ICCID를 아는 요청자는 해당 장치의 수신 상태·좌표를 위조할 수 있는 설계다. 응답 과정에서 `beep_pending`·`reset_pending`도 소비하므로 실제 장치가 받아야 할 명령을 소진시킬 수도 있다.
- 이는 기존 구현의 설계상 공백이다. 실제 위조 POST나 명령 소비 시험은 하지 않았다.
- 수정 방향: 개별 장치 비밀키 기반 검증과 재전송 방지, 전송 보호를 단계적으로 도입한다. 이미 배포된 펌웨어 및 KC 시험 경로의 호환 정책을 별도로 둔다.

### 5) [P1] KC 스캔 기능을 일반 사용자도 사용할 수 있다

- 근거: `gps-tracker-api/src/routes/devices.rs:252`의 `scan_unpaired`는 일반 `AuthUser`만 요구한다. 최근 10분 내 송신한 모든 미소유 장치의 UID를 반환한다.
- 같은 파일의 `pair`는 미소유 장치를 UID만으로 클레임할 수 있다. 원자적 소유권 변경은 구현되어 있지만 장치를 실제 보유했는지는 확인하지 않는다.
- 결과: KC 검사 편의를 위한 검색 기능이 일반 계정에도 장치 발견·선점 경로를 제공한다.
- 실제 제공 중인 운영 JS에 스캔 UI와 API 호출이 포함된 것을 확인했다.
- 수정 방향: KC 시험 계정/관리자 및 지정 시험 장치로 범위를 제한하고, 일반 제품은 기기별 페어링 증명을 요구한다.

### 6) [P1] GPS 배치 저장 방식과 통계 계산 방식이 맞지 않는다

- 근거: `ingest.rs:281` 이후에는 배치 GPS 여러 점을 **한 행 + `fixes_jsonb`**로 저장한다. `services/stats.rs:102`는 행의 `recorded_at, lat, lng`만 읽는다.
- 따라서 배치 중간점은 일별 거리·속도·fix 수 계산에서 빠진다. 공유 위치 조회 및 continuous aggregate도 JSONB 내부 점을 펼치지 않는다. 반면 일반 위치 이력은 JSONB를 펼친다.
- 실제 DB의 최근 배치 300행에 GPS 점은 4,122개였다. 저장 손실은 아니지만 조회·통계 경로마다 사용하는 점 수가 다르다. 이 수치만으로 거리 오차율을 계산하지는 않았다.
- `stats.rs:155`의 인접점 간 거리 50m 미만=정지 판정도 별도 문제다. 예를 들어 15초마다 30m 이동하는 연속 저속 주행을 정지로 셀 수 있다. 현재 DB에는 거리 500m 초과·이동시간 0인 일별 통계가 3개 있지만, 실제 이동인지 GPS 잡음인지는 추가 대조가 필요하다.
- 수정 방향: 공통 GPS 점 전개·중복 제거·시간/좌표 검증 계층을 두고 일별/운행/공유/집계 결과를 일치시킨다. 정지는 개별 구간 길이가 아니라 시간창·속도·위치 분산을 함께 사용한다.

### 7) [P2] 과거 기록 삭제 후 파생 통계가 남는다

- 근거: `devices.rs:858`의 `delete_range`는 위치·이벤트·장치 최종 위치를 수정하지만 `daily_stats` 갱신/무효화나 집계 refresh는 하지 않는다.
- 통계 워커는 `services/stats.rs:53`에서 오늘·어제를 갱신한다. 더 오래된 날짜를 삭제하면 기존 일별 통계가 자동으로 바로잡히지 않는다.
- 실제 Timescale 집계 refresh 범위도 1분=7일, 5분=14일, 1시간=30일이다. 범위 밖의 과거 기록 삭제는 별도 refresh가 필요하다.
- 수정 방향: 삭제된 날짜·시간 범위를 작업 큐에 넣어 모든 파생 통계를 재계산한다. 배치 내부 시간점의 부분 삭제도 포함해야 한다.
- 운영 데이터 삭제 재현은 수행하지 않았다.

### 8) [P2] 파일 업로드 안내와 실제 요청 크기 제한이 다르다

- 근거: `routes/documents.rs:29`는 파일 10MB를 허용한다고 정의하지만 `main.rs:94`의 전역 body 제한은 1MiB이며 문서 업로드 라우트에 별도 상향 설정이 없다.
- 렌트카 인수/반납 사진 제출은 라우트에 40MiB 예외가 있으나, 운영 GPS nginx API 경로에는 해당 크기를 허용하는 설정이 없다. GPS server 및 http 전역에 body 크기 상향이 없는 것을 확인했다.
- 결과: 안내 범위 내의 사진·PDF라도 업로드가 차단될 수 있다. multipart/base64 오버헤드도 고려해야 한다.
- 수정 방향: 특정 업로드 경로의 nginx·애플리케이션 한도를 함께 정하고 프런트 안내와 일치시킨다. 실제 파일 전송은 하지 않았다.

### 9) [P2] `/diagnostic` URL이 서로 다른 화면에 사용된다

- 근거: `gps-tracker-web/src/App.jsx:177`은 로그인 사용자의 `DiagnosticPage`를 `/diagnostic`에 연결한다.
- 실제 nginx의 `location /diagnostic`은 Rust DHT 진단 페이지로 보낸다.
- **HTTP 확인:** `GET https://gps.serial.kr/diagnostic`의 제목은 `DHT11 진단 타임시리즈`다.
- 결과: SPA 내부 이동과 직접 접속·새로고침에서 서로 다른 화면이 나타난다.
- 수정 방향: 제품 진단 화면과 KC/DHT 시험 페이지의 URL을 분리한다.

### 10) [P2] 운영 프런트의 보관 소스와 제공 중인 산출물이 다르다

- 실제 `/home/mmm/gps-tracker-web/src/pages/Dashboard.jsx` 및 `src/api.js`에는 KC 스캔 추가분이 없다.
- 그러나 제공 중인 `dist-root/assets/index-BikNpKDW.js`에는 `scanDevices`, 스캔 안내·재조회 UI가 있다. 운영 화면에 스캔 기능이 없다는 뜻이 아니다.
- 서버 소스만 다시 빌드하면 현재 제공 기능을 재현하지 못할 수 있다. 운영 API의 배포 소스는 로컬 main과 실질적으로 일치했고, 사용되지 않는 옛 `partition_worker.rs` 파일만 추가로 남아 있었다.
- 수정 방향: 커밋·빌드 ID·산출물 해시를 묶은 릴리스를 배포하고, 실제 제공 중인 버전을 확인할 경로를 둔다.

## 2. DB·운영 상태

| 확인 항목 | 관측 |
|---|---|
| 운영/개발 health | 둘 다 `ok=true`, `db=true` |
| 운영 DB | PostgreSQL 14.18, TimescaleDB 2.19.3, 약 78MB |
| 압축/집계 작업 | 현재 등록 작업 모두 최근 실행 성공, 기록된 누적 실패 0 |
| 마이그레이션 | 운영 1~60, 개발 1~35. 각 서버의 적용 checksum은 그 서버의 배포 소스와 일치 |
| 역할 | 운영/개발 앱 역할 모두 superuser 아님 |
| 개발 역할의 운영 DB 접근 | CONNECT·public schema USAGE는 허용됨. users/devices/location_records SELECT와 devices UPDATE는 거부됨 |
| 최근 24시간 운영 로그 | ERROR 0건, 1초 초과 slow SQL 20건, 1NCE 요청 실패 1건, 오피넷 키 미설정 경고 4건 |
| 보존 정책 | 압축 7일 정책은 있음. 마이그레이션 0040에 적힌 1년 retention job은 현재 없음 |

추가 정리할 항목:

- **개발 역할의 CONNECT 차단 문서와 실제 권한이 다르다.** 테이블 읽기/쓰기는 차단되어 있어 운영 데이터 접근이 열려 있다고 단정하면 안 된다. 문서의 4계층 차단 중 DB 연결 차단은 현재 성립하지 않는다.
- **retention과 진단 데이터 수명:** 원본 위치의 1년 자동 삭제 설정이 실제로 없고, `diag_dht`에도 보존기간 정리가 없다. 정책을 확인한 뒤 코드·운영 설정·문서를 맞춰야 한다. 이번에 임의로 삭제 정책을 추가하지 않았다.
- **백업:** VPS의 확인한 cron/timer 및 `/home/mmm/backup`, `/home/mmm/backups`, `/var/backups` 범위에서는 최신 GPS DB 정기 백업·복원 검증 근거를 찾지 못했다. WAL archive mode는 off였다. 외부 스케줄러나 스토리지 스냅샷의 부재까지 증명한 것은 아니다. Tower의 Seriallink 센서 아카이브를 GPS DB 백업으로 간주하면 안 된다.
- **오피넷:** 운영 키가 없어 기본/캐시 가격으로 동작한다. 실시간 유가 기반 리포트라고 설명하려면 설정 또는 UI 표시를 정리해야 한다.
- **시험용 공개 조회:** `diag.rs:114`의 `esp-` 접두사 자동 허용은 KC 기기라는 명시적 증명이 아니다. 공개되는 필드는 시간·신호·전압·fix 여부·위성수이고 좌표는 해당 응답에 포함되지 않는다. 허용 목록/시험 접근 토큰으로 범위를 명확히 하는 편이 낫다.
- 운영 공유 API의 rate limit, 원자적 refresh 토큰 회전, 페어링 경쟁 방지, 일반 위치 API의 사용자 필터, 예약 겹침 제약 등 이미 적용된 방어도 확인했다. 이번 검토는 이런 방어를 제거하는 방향이 아니다.

## 3. dev가 운영보다 앞선 부분

dev는 6월 계열에서 갈라진 별도 기능 개발본이다. 실행 시점이 오래됐다는 이유만으로 독자 기능까지 없다고 판단하면 안 된다.

## 4. dev를 통째로 가져오면 안 되는 이유

1. **마이그레이션 번호 충돌**

   | 번호 | 운영 | 개발 |
   |---|---|---|
   | 0033 | device_beep | device_maintenance |
   | 0034 | location_heading | device_car_info |
   | 0035 | device_reset | speed_kmh |

   숫자가 같아도 적용 내용과 checksum이 다르다. 단순히 main을 dev DB에 배포하면 sqlx 검증에서 충돌한다. 기존 적용 이력을 임의로 덮어쓰는 방식도 피해야 한다. 운영용 신규 번호로 기능을 이식하고 dev 환경 정합성을 별도 복구해야 한다.

2. **운영의 후속 기능·보안 개선이 빠져 있다.** dev에는 현재 운영의 Timescale/배치 JSONB 처리, 렌트카·예약·서류 확장, KC 진단, 로그인 시도 제한, WS 소유권 재검증 등 여러 후속 변경이 없다. 일부 열은 수동 반영되어 있어 단순 스키마 버전 비교만으로 전체 기능을 판단할 수도 없다.

3. **공개 dev의 결제 webhook도 점검 대상이다.** 배포 소스의 webhook은 시크릿이 없으면 요청을 수락하는 구버전 로직이고, dev 서비스의 실제 `.env.dev`에는 `TOSS_WEBHOOK_SECRET`이 없었다. 운영은 시크릿이 설정되어 있고 미설정 시 기본 거부하도록 개선되어 있다. 실제 결제/webhook 호출은 하지 않았다. 독자 기능과 함께 구버전 보안 동작을 옮기면 안 된다.

4. **독자 UI도 마감이 필요하다.** 정비 날짜 수정은 COALESCE/빈 값 미전송 방식이라 값을 지우는 기능이 불완전하다. 오프라인 캐시는 사용자 분리가 필요하다. 속도 저장은 펌웨어부터 화면까지 검증해야 한다.

## 5. 권장 작업 순서

1. 공유 데이터 범위, 계정 캐시·refresh 경쟁, 일반 사용자 KC 스캔 범위를 먼저 수정한다. 장치 인증은 펌웨어 호환성을 고려한 별도 단계로 설계한다.
2. GPS 배치 전개·통계·삭제 후 재집계를 일관되게 만든다. 지도에서 보이는 경로와 보고서 수치가 같아지는 것을 검증한다.
3. 업로드 한도, 진단 URL, 릴리스 식별/소스 정합성을 정리한다. DB 보존·백업·접근 문서도 실제 설정과 맞춘다.
4. dev의 정비/만료일 → 대표 사진·편의 UI → GPS 속도 원본 순으로 선별 이식한다. 경로 계획·오프라인은 제품 요구와 정확성/계정 분리를 보완한 뒤 반영한다.
