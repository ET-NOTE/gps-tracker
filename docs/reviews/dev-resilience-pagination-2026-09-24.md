# GPS 통신 이상 복구와 대량 이력 조회

범위: dev 전용. KC 스캔·공개 시험 진단 정책과 실제 펌웨어는 유지한다. prod 배포에는 사용자 허가가 필요하다. Windows의 기존 24시간 더미 송신기도 유지한다.

## 수신과 실시간 복구

- 과거 점을 일괄 버리던 최대 uptime 워터마크를 제거한다. 저장된 배치의 식별자와 대조해 재전송 사본만 제외하고, 아직 저장되지 않은 지연 점은 보존한다.
- 한 장치의 배치 저장은 DB 장치 행 잠금으로 직렬화한다. 같은 배치의 동시 재전송과 소유권 변경·삭제·통계 집계 경합을 방지한다.
- 같은 배치 안의 중복도 제거한다. 최신 좌표는 배열 순서가 아닌 실제 fix 시각으로 고르고, 오래된 배치나 중복 POST가 장치의 최신 위치·시각을 덮어쓰지 않는다.
- 수락한 점의 KST 날짜를 통계 재집계 큐에 넣는다. 자정을 가로지르는 배치는 양쪽 날짜를 등록하며 관리자 재계산도 실제 점 날짜를 사용한다.
- 음수 age/uptime, 범위를 벗어난 좌표는 장치 상태를 바꾸기 전에 거부한다. 구형 단일 GPS 및 uptime 없는 배치 형식은 유지한다.
- 브라우저 WebSocket 재연결은 구독 후 REST 이력을 다시 읽는다. 서버 lagged 알림과 늦은 좌표도 이력 재조회로 연결하고 최신 마커가 과거로 돌아가는 것을 막는다.
- 위치가 없는 heartbeat는 GPS 시각을 갱신하지 않는다. 계정 종료 뒤 대기 중이던 프레임 콜백도 무시한다.

현재 프로토콜의 한계: 재전송 시 `up_ms`는 고정하고 `age_ms`는 실제 대기 시간만큼 늘려야 한다. uptime이 있으면 boot/boot_id와 함께 비교하고 복원 시각 오차 30초를 허용한다. uptime이 없는 구형 배치는 동일 좌표·500ms 오차로만 중복을 추정한다. boot 표식까지 재사용하는 빠른 전원 재투입이나 큰 시계/전송 지연 오차를 완벽하게 구분하는 것은 아니다. 향후 펌웨어의 고유 부팅 ID·샘플 ID가 필요하며 이번에 KC 펌웨어를 바꾸지는 않는다.

## 조회 계약과 자원 제한

- 신규 `GET /devices/:id/locations/page`: `since` 포함, `until` 제외, 최대 31일 범위. 기본 2,000점, 최대 5,000점씩 반환한다.
- 응답은 `items`, `has_more`, `next_cursor`. cursor는 좌표 시각과 source를 함께 사용하므로 같은 시각의 서로 다른 GPS source도 빠지지 않는다. 사용자·장치·기간·필터가 바뀌면 cursor를 거부한다.
- 기존 `/locations`의 배열 및 grouped 계약은 유지한다. 기존 limit은 전송 원본 행 수이며, 신규 page의 limit은 좌표 점 수다.
- 컴팩트 일간 시커는 모든 페이지를 순차 조회하고 완료된 경로만 표시한다. 날짜 변경/닫기 시 요청을 중단한다. 조회 중에는 누적 좌표 수를 표시하고 중간 실패를 정상적인 빈 경로로 표시하지 않는다.
- 브라우저 메모리를 위해 한 조회가 250,000점을 넘으면 명시적 안내를 표시한다. 조용히 잘라 표시하지 않으며 상세 시커의 집계 조회를 사용하도록 안내한다.
- 집계 API의 조용한 5,000개 잘림을 제거했다. 프런트는 최대 2,000개 버킷의 시간 구간으로 나누어 요청한다. 각 구간은 끝 시각을 제외하여 중복 집계가 없다. 너무 큰 단일 요청은 400으로 명시적으로 거부한다.
- 페이지 사이에 장시간 DB snapshot을 유지하지 않는다. 조회 중 지연 데이터 삽입/삭제가 발생하면 새로고침해야 최신 전체 상태를 다시 읽을 수 있다.

## DB 변경

`0063_location_range_queries.sql`은 배치 첫/마지막 시각의 표현식 인덱스와 `location_points_between` 함수를 추가한다. JSONB를 전체 좌표로 펼치기 전에 해당 전송이 조회 시간대와 겹치는지 검사한다. 기존 데이터의 at_ms가 양수인 경우도 포함한다.

최신 위치는 마지막 좌표 시각 인덱스에서 최신 전송 하나를 고른 뒤 해당 배치만 펼친다. 같은 시각의 source·배치 우선·anchor 순서는 canonical view와 맞춘다. 활동 날짜는 전체 좌표 DISTINCT 정렬 대신 각 배치의 실제 날짜 목록을 합친다. 원본/이전 소유자 필터는 유지한다.

시간 연산은 UTC로 고정하여 연결 시간대나 DST가 표현식 인덱스를 바꾸지 않도록 했다. [PostgreSQL 표현식 인덱스의 immutable 요구](https://www.postgresql.org/docs/15/sql-createindex.html)를 따른다.

## 재현 명령

```powershell
# 실제 프런트 WS client로 dev 연결·재연결·이력 복구 검사 (전용 검증 계정)
node --experimental-vm-modules ops/verify_dev_faults.mjs

# 기존 연속 송신기의 실시간 배치·REST 검사
```

`ops/test_dev_resilience.py`는 dev 환경 파일을 가진 VPS에서 임시 장치·계정을 생성하고 제거한다. 배포 과정에서 3042 사전 검사와 공개 HTTPS 검사에 포함된다. `--benchmark`는 별도 100,000점 성능 비교를 추가한다. 이 스크립트는 prod URL/DB를 거부하며 생성한 ID만 정리한다.

## 검증 결과

최종 dev 릴리스: `dev-20260924-191237-973c63d`. 소스 `973c63d`를 Hub에서 빌드했고 API health와 웹 version.json의 릴리스가 일치한다. 후속 벤치마크 계측·문서 변경은 애플리케이션 산출물을 바꾸지 않는다.

- 프런트 17건, Rust 4건, Rustfmt/Clippy 검사 및 Hub API/웹 빌드 통과.
- 임시 3042와 공개 dev HTTPS에서 기존 API 회귀 8개 그룹과 신규 이상 상황·페이징 회귀 6개 그룹을 각각 통과.
- 중복, 겹친 배치, 늦게 도착한 새 점, 배열 순서 뒤바뀜, 동시 재전송, boot 변경과 uptime 재사용, 구형 uptime 없는 배치 재전송, no-fix 및 잘못된 좌표를 검증.
- KST 자정을 가로지르는 배치의 양쪽 활동 날짜와 재집계 큐 확인. 원본 점 수와 일별 통계 fix_count 합계 일치. 동일 배치 재전송 전후 거리 합계 동일.
- 실제 10,006개 점을 6페이지로 조회하고 중복/누락 없음 확인. 같은 시각의 서로 다른 source, 배치 내부 페이지 분할, 끝 시각 제외, cursor 장치/기간 혼용 거부 검사.
- 실제 31일치 5분 집계 8,928개를 구간별 조회하여 누락·중복 및 fix_count 차이가 없음을 확인. 너무 큰 단일 집계 요청은 조용한 잘림 대신 400 반환.
- SQL 범위 함수와 canonical view의 결과를 UTC·America/New_York·Asia/Seoul 연결에서 대조했다. 음수/양수 at_ms와 날짜 경계 포함.
- Windows에서 실제 프런트 `TrackerWS`로 연결을 끊고 재연결: 연결 2회, resync 1회, 연결 공백을 포함한 9점 REST 복구, 최종 고유 송신 11점 = 저장 11점. 전용 임시 장치 3033의 검증 후 페어링과 본인 이력을 정리했다.
- 브라우저 컴팩트 시커에서 2,000점 이상의 하루 이력이 17:30~19:10 시간대로 표시되고 경로를 선택할 수 있었다. API 재시작 뒤 실시간 화면은 `이동 중 10km/h · 방금`으로 갱신됐다.

### 성능 관측

별도 dev 임시 장치에 1,000행 × 100점 = 100,000점을 넣고 `work_mem=4MB`, SQL timeout 8초 아래에서 측정한 뒤 제거했다. 아래는 동일 실행의 관측값이며 운영 최악 지연·최대 동시 접속 성능을 뜻하지 않는다.

| DB 조회 | 기존 canonical 경로 | 개선 경로 |
|---|---:|---:|
| 최신 좌표 | 389.290ms | 0.656ms |
| 활동 날짜 | 373.129ms | 190.300ms |
| 선택 1시간의 1분 집계 | 110.611ms | 92.872ms |

최신 좌표 실제 HTTPS 응답 12.8ms. 10,006점 전체 6페이지 조회는 약 1.0~1.2초였다. 선택 1시간의 원본 3,600점과 최적화 조회 결과도 일치했다. 모든 SQL 회귀 임시 장치는 제거되어 `dev-sim-regression-*` 잔여 장치 수 0개다.

### 최종 연속 송신·운영 확인

- 19:17 KST경 기존 송신기 성공 512회, 실패 0회. 송신 상태의 누적 3,192점과 DB 저장 3,192점·고유 uptime 3,192개가 동일 cutoff에서 일치했다. 24시간 송신은 계속 실행 중이다.
- 최종 릴리스에서도 실제 WS 3배치(각 5점, 12.86km/h)와 REST를 확인했다. 기존 가상 장치의 REST 지연 37~60ms.
- 19:16 KST VPS load 0.37/0.39/0.27, 가용 메모리 841MiB, 디스크 5.7GB(87%). dev DB migration 63까지 적용. 새 PostgreSQL 인스턴스는 만들지 않았다.
- prod PID 2630525/시작 시각, API·웹 index·nginx SHA256이 유지됐다. prod/dev health와 KC 진단 HTTP 200, 이 배포 이후 dev ERROR journal 항목 없음.
