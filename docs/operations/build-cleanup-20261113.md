## 삭제 범위와 보호

- 컴파일 출력 2곳과 `package-lock.json`이 있는 웹 프로젝트의 `node_modules`만 삭제했다. 상세 11개 경로는 [실행 결과](../evidence/build-cleanup-20261113/applied.json)에 있다.
- Git 소스, 릴리스 압축본·배포 바이너리·펌웨어, 검증 로그·복구 자료, DB 백업·키·권리 체크포인트는 삭제 대상에서 제외했다.
- Cargo 다운로드 캐시 약346 MiB, npm 다운로드 캐시 약61 MiB, 공용 시험 Python 환경 약28 MiB를 유지했다. Docker 이미지·볼륨과 다른 프로젝트도 정리하지 않았다.
- 120 최신 후보, 119 누적 기반, 116 선행 후보와 120 API/PDF 바이너리는 문서의 고정 SHA-256 값과 대조했다. 그 외 보존 파일을 포함한 835개 압축본·바이너리의 정리 전후 해시도 일치했다. 보호 목록은 [계획 원본](../evidence/build-cleanup-20261113/plan.json)에 있다.
- 118 보호 도구를 비롯한 이전 라운드 경로 자체도 유지했다. 최근 몇 개만 남기는 방식의 라운드 디렉터리 삭제는 하지 않았다.

## 중복 압축본 검토

파일 내용이 같은 압축본은 11묶음, 추가 복사분 약37.15 MiB였다. `source.tar.gz`와 `out/source.tar.gz`, 배포 원본과 `security-rollback-20261020/predecessor.tar.gz`처럼 서로 다른 용도가 섞여 있다. `ops/deploy-dev-artifact.sh`도 원본 압축본의 해시를 검증하고 배포 폴더에 복사한다.

동일한 해시는 해당 경로가 불필요하다는 증거가 아니다. 이 작은 중복본을 없애려고 과거 배포·복구 경로를 변경하지 않았으며 전부 보존했다. [분류 결과](../evidence/build-cleanup-20261113/duplicates-retained.json).

## 실행과 검증

1. GPS 빌드 프로세스와 GPS 빌드 경로를 쓰는 실행 컨테이너가 없음을 확인했다.
2. 기존 빌드 잠금 2개를 배타적으로 잡고, 정리 계획과 보존 파일 해시를 저장했다.
3. 적용 직전 경로·할당량·inode·보존 해시·실행 서비스가 계획과 같은지 다시 대조했다.
4. 고정 호스트/루트, 경로와 심볼릭 링크, 별도 마운트, 웹의 `package.json`/`package-lock.json`을 확인하고 11곳을 삭제했다.
5. 보존 파일 해시와 실행 서비스 상태를 재검증했다. 컴파일 캐시 2곳이 없고 다운로드 캐시와 Python 환경이 남아 있음을 확인했다.

도구는 `ops/build_cleanup_20261113.py`다. 기본 작업은 `plan`, 삭제는 저장된 계획과 일치하는 `apply`에서만 실행한다. 이 날짜의 정리 전용 도구이며 timer를 등록하지 않았다. Python 구문 검사와 실제 계획·적용 검증을 통과했다. 캐시만 정리했으므로 API/웹 재빌드나 운영 배포는 하지 않았다.

11월6일 기존 도구의 최초 dry-run도 같은 11곳/5.04 GiB를 보고했지만, Windows 줄바꿈 전달 때문에 마지막 빈 줄에서 종료 코드1이 발생했다. 해당 dry-run은 삭제하지 않았다. 이후 명시적 계획·해시 보호가 있는 위 Python 도구로 실행했다.
