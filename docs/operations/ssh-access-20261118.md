# 개발 협업을 위한 SSH IP 제한 해제 — 2026-11-18

사용자가 다른 사무실의 부사수도 기존처럼 SSH 작업을 할 수 있도록 화이트리스트 해제를 명시적으로 지시했다. **11:27:43 KST** 공유 VPS `210.114.18.16`의 TCP22를 모든 출발지에 허용했다. 개발·운영이 같은 호스트의 SSH를 사용하므로 이 변경은 개발 도메인만의 방화벽 변경이 아니라 호스트 TCP22의 네트워크 정책 변경이다. 계정별 권한은 그대로다.

## 현재 상태

| 항목 | 결과 |
|---|---|
| IPv4 SSH | `22/tcp ALLOW Anywhere` |
| IPv6 SSH | `22/tcp ALLOW Anywhere (v6)` |
| 인증 | 공개키 yes, 비밀번호 no, keyboard-interactive no. sshd 설정/재시작 없음 |
| 개발 계정 | `gps-dev`, 기존 authorized_keys 6개 유지, 키별 출발지 제한 없음 |
| Fail2ban | active 유지. 기존 재시도/차단 시간·예외 IP 설정 동일 |
| DB | 기존 INPUT 단계의 루프백·사무실 IP 허용/그 외 차단 유지 |
| 나머지 | 기본 INPUT DROP, 나머지 서비스 포트/NAT/raw/mangle·부팅 순서 유지 |
| 서비스 | 운영/개발 GPS·Shield·Nginx·SSH·Fail2ban PID/시작 시각 동일. 배포/DB 스키마 변경 없음 |
| Cafe24 | 대시보드 변경 안 함. 아래 외부 접속 검증이 통과해 이번 작업에 추가 대시보드 조작은 필요하지 않았음 |

접속 예: `ssh -i <본인의 기존 개인키> gps-dev@dev-gps.serial.kr`. 비밀번호나 다른 사람의 키를 공유할 필요가 없다.

## 검증

1. 별도 외부 VPS에서 `dev-gps.serial.kr → 210.114.18.16:22`의 TCP 접속은 변경 전5초 시간 초과, 변경 후OpenSSH 배너 수신 성공.
2. 같은 외부 VPS를 ProxyJump로 경유해 기존 승인 키로 **gps-dev 실제 로그인 성공**. 대상 서버가 보고한 접속 원본은 `115.68.178.125`로 사무실 허용 IP와 다르다. 개발 웹 소스 `package.json`을 읽을 수 있었다. 키는 로컬 SSH에서 사용했고 외부 VPS로 복사하거나 에이전트 포워딩하지 않았다. 부사수 본인 PC/키로 직접 시험한 것은 아니다.
3. 새 관리 SSH 연결에서도 IPv4/IPv6 커널 규칙과 UFW 영구 규칙을 확인했다. IPv6는 규칙 확인이며 실제 외부 IPv6 접속을 별도로 시험하지 않았다.
4. sshd 설정/등록 키/Fail2ban 설정, 서비스 PID·시작 시각, 나머지 네트워크 규칙 해시가 최종 변경 전후 같다. 운영·개발 `/health`는 각각 production/development 및 `ok=true`, `db=true`다.
5. UFW 영구 파일에 반영했으며 재부팅은 하지 않았다. 기존 UFW/netfilter-persistent 부팅 순서 설정을 유지했다.

## 첫 적용에서 확인한 기존 규칙 불일치

첫 `ufw allow/delete` 실행은 UFW가 저장된 사용자 규칙을 커널에 다시 적용하면서 검증 해시 차이를 감지했다. SSH 허용은 즉시 기존 사무실 전용으로 복구한 뒤 원인을 대조했다.

기존 커널의 UFW 사용자 체인에는 TCP5432 전체 허용 잔여 규칙이 있었지만, 영구 UFW 파일은 IPv4 사무실만 허용하고 IPv6 예외는 없었다. 앞단 INPUT의 DB 허용/차단이 먼저 적용되어 실제 DB 접근 경계는 이미 사무실/루프백으로 제한되고 있었다. CLI가 이 잔여 규칙을 영구 설정에 맞춘 것이 해시 차이의 전부였다. 변경 후 규칙에서 이 두 차이만 역으로 구성한 해시가 최초 해시와 일치해 다른 변경이 없음을 확인했다.

DB 접근 범위를 넓히지 않았으며 저장된 정책과 커널 사용자 체인이 일치한 상태를 유지했다. 이 상태를 기준으로 SSH 변경을 다시 적용해 나머지 규칙 불변 검증이 통과했다. 첫 시도와 원복/대조 사실도 증거에 남긴다.
