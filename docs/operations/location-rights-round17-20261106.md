# 위치정보사업 준비 — 17차 수집·이용·제공사실 열람 제공

작성: 2026-11-06. 브랜치 `codex/location-business-prep`.

> **상태: 릴리스 절차 리허설 통과(커밋 `682ab5d`), 운영 서버에 산출물 전송과 읽기 전용 점검 통과(2026-11-06 19:39 KST). 운영에는 아직 적용하지 않았다.** 운영은 `pdf-service-20261106-r1`·스키마 98 그대로다. 다음은 적용이며 승인을 받는다(아래 "운영 반영 순서").

## 이번 범위

정보주체가 **본인 위치정보의 수집·이용·제공사실**을 열람할 수 있게 한다([위치정보법 제24조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1029559327)의 열람 대상 가운데 "수집·이용·제공사실 확인자료"). 새 화면이나 새 요청 종류를 만들지 않고, 기존 개인정보 열람 요청과 9·10차의 **계정 자료 제공**에 담당자가 선택하는 항목 하나를 추가했다.

- 항목 이름: `location_facts` — 화면 표시 "위치정보 수집·이용·제공사실 (좌표 제외)"
- 담당자가 **기간**(한국 날짜, 최대 366일)을 지정해 발급한다. 요청자는 기존과 같이 비밀번호를 다시 입력하고 JSON으로 내려받는다.
- 자료는 **내려받는 시점에 기존 기록에서 읽어 만든다.** 새로 저장하는 것은 발급에 붙는 기간뿐이다.
- **좌표·주소는 넣지 않는다.** 언제·어떤 방법으로·무엇을 통해 처리됐는지만 담는다.

이 라운드는 **지금 시스템에 남아 있는 기록을 정확히 보여 주는 것**까지다. 법적 의무 충족 완료를 선언하지 않는다. 조회할 때마다의 기록(접근기록·취급대장)을 새로 남기는 일은 준비 문서의 S3 항목이며 이번에 구현하지 않았다.

## 조사: 남는 기록과 남지 않는 기록

구현 전에 저장소 전체를 조사했다. 결론은 **수집은 계정 단위로 남고, 이용·제공은 일부만 남으며, 조회 자체는 기록되지 않는다**는 것이다.

| 구분 | 사실 | 기록 | 계정 귀속 | 비고 |
|---|---|---|---|---|
| 수집 | 위치 보고 저장 | `location_records` | `user_id` = 수신 당시 소유 계정 | 1년 보관 정책, 본인 삭제·이용 종료·SIM 파기 시 삭제 |
| 수집 | 수집 방법 | `source`, `fixes_jsonb` | 위와 같음 | 펌웨어 정보는 원본 JSON 안에만 있음 |
| 수집 | 중지·차단 중 거절된 보고 | **없음** | — | 응답만 하고 기록하지 않음 |
| 수집 | 수집 중지·재개 | `collection_control_events` | `actor_id` | 단말기 적용 시각 이력은 없음 |
| 이용 | 본인의 지도·이력·통계 조회, 실시간 연결, 내보내기 | **없음** | — | 서버 표준 출력 로그뿐 |
| 이용 | 구역 출입, 주기 첫 위치 | `events` | `user_id` | 전환이 없는 평가는 기록 없음 |
| 이용 | AI 분석 | `ai_analysis_requests`, `ai_analyses` | `user_id` | 실패·시간 초과 요청은 기록 없음 |
| 이용 | 알림 전송 | `events.notified_at`, `fcm_outbox` | `user_id` | 대기 기록은 14일 뒤 삭제 |
| 이용 | 운영자의 장치·최근 위치 확인 | **없음** | — | 대리 접속 시작만 `admin_audit_log` |
| 이용 | 회사 계정(소유자·직원)의 차량 운행 조회 | **없음** | — | 변경 요청만 `fleet_team_audit` |
| 제공 | 공유 링크 | `share_tokens`, `credit_log` | `created_by` | 받는 사람 식별 없음, 열람 횟수·마지막 시각만, 만료 30일 뒤 삭제 |
| 제공 | 열람 요청에 따른 위치 파일 | `privacy_deliveries`, `privacy_delivery_events` | 요청 계정 | 7차 |
| 제공 | 회사와의 계정 연결 | `privacy_company_link_history` | `subject_id` | 연결 상태만. 회사의 조회 건별 기록 없음 |
| 제공 | 외부 지도·AI·알림 서비스 호출 | 일부(AI·알림) | 일부 | 지도 좌표 변환은 건별 기록 없음 |

계정 간 장치 공유, 위치를 보내는 웹훅·문자는 없다.

## 경계

- **좌표·주소·원본 보고·공유 링크 토큰·AI 본문·알림 본문을 읽지 않는다.** 조회문이 그런 열을 선택하지 않는지 단위 시험으로 고정했다.
- **수신 당시 계정이 기준이다.** SIM이 다른 계정으로 옮겨가도 옮기기 전 기록은 이전 계정에, 옮긴 뒤 기록은 새 계정에 나온다. 현재 소유자는 기준이 아니다.
- **회사 차량 연결 이력이 있는 단말기와 파기된 SIM은 제외**하고 개수만 알린다(7차 위치 파일 제공과 같은 보수적 경계). 회사 차량 운행 중 회사 계정으로 수집된 위치는 회사 자료 검토 절차(8·11차)에서 다룬다. 제외는 정보주체의 권리를 부정하는 판정이 아니다.
- **회사 이름을 넣지 않는다.** 여러 회사를 구분할 수 있게 순번만 준다.
- **한도를 넘으면 잘라 내지 않고 중단한다**(409, 내려받기 기록도 남기지 않음). 조회가 10초 안에 끝나지 않아도 같은 안내로 중단한다. 담당자는 기간을 나누어 다시 발급한다.
- 기간의 끝이 미래이면 발급 시각으로 자른다. 기간은 항목을 선택했을 때만 존재한다. 이 두 규칙은 DB 제약으로도 강제한다.
- 발급·내려받기의 기존 통제(관리자 전용, 요청 revision 충돌, 24시간 만료, 회수, 비밀번호 재확인과 시도 제한, 이용 종료 계정 거부)는 그대로다.

## 자료에 그대로 나가는 "기록되지 않는 처리"

자료를 받는 사람이 이 목록을 **전체로 오해하지 않게** 하려고 넣었다. 아래 문구가 정보주체에게 그대로 전달되므로 **위치정보관리책임자의 문구 검토가 필요하다.**

1. 본인 계정의 지도·이동 이력·통계 조회, 실시간 화면 연결, 파일 내보내기
2. 공유 링크를 받은 사람의 열람(횟수와 마지막 시각만 남음, 만료·회수 30일 뒤 링크 삭제)
3. 회사에 연결된 계정(회사 소유자·직원)의 차량 운행 조회와 보고서 생성
4. 운영자(관리자)의 장치 상태·최근 위치 확인
5. 외부 지도 서비스의 좌표 변환, 알림 전송 서비스로의 전달(대기 기록은 14일 뒤 삭제)
6. 완료되지 않은 AI 분석 요청
7. 수집 중지·차단 중 단말기가 보낸 보고
8. 보관 기간(1년) 경과·본인 삭제·SIM 파기로 남아 있지 않은 위치 기록

외부 서비스는 기능으로만 적고 업체 이름을 적지 않았다. 제3자 제공인지 처리 위탁인지의 구분과 업체 표기는 처리방침에서 정할 일이다.

- `gps-tracker-api/src/routes/privacy_packages.rs`: 발급 요청에 기간을 받고 저장, 내려받기에 기간 전달.

- 앱은 같은 웹 화면을 쓰므로 APK 변경이 없다. 펌웨어 변경도 없다.

| 웹 | 고정 이미지(리눅스)에서 225 통과·0 실패(새 시험 1개), 빌드 통과 |

| 규모 | 한 계정 15만 건(104일분)에서 일별 집계 약 0.16초(빌드 호스트, 캐시된 상태) |

새 통합 묶음이 확인하는 것:

1. 항목 없이 발급하면 기간이 없고 기존과 같다. 항목에는 과거에 시작하는 366일 이내의 기간이 필요하다. 미래의 끝은 발급 시각으로 잘린다. DB 제약도 같은 규칙을 거절한다. 관리자가 아니면 거절.
2. 수집: 한국 날짜 경계(자정 넘어 30분의 보고가 다음 날짜로 집계), 단일·묶음 보고의 점 수, 위치 없는 보고의 분리, SIM 이동 전후 귀속, 회사 차량 단말기 제외와 개수. **응답 바이트에 심어 둔 좌표·원본·토큰·AI 본문·기기 이름·타인 메모가 없음.**
3. 이용: 구역 출입·첫 위치 사건만(다른 종류·타인·회사 단말기 제외), AI 분석은 한 번씩.
4. 제공: 기간에 열려 있던 공유 링크와 차감 흔적, 위치 파일 제공과 내려받기, 회사 연결 변동(회사명 없음), 기록되지 않는 처리 목록.
5. 다른 계정은 자기 사실만 본다(이동한 SIM의 이후 날짜 포함). 나중의 소유권 변경이 이전 계정의 자료를 바꾸지 않는다. 회수 후 410.
6. 일별 4,000행·사건 2,000건 초과 시 409와 무기록, 좁은 기간은 성공. 조회 시간 제한에 걸려도 409이고 다음 내려받기는 성공.

### 검증에서 발견해 고친 것

- 기간 없는 발급이 DB 오류(500)가 됐다. `LEAST(NULL, now())`가 NULL이 아니라 현재 시각을 돌려줘 "기간은 항목이 있을 때만" 제약에 걸린 것이다. 통합 묶음의 첫 그룹이 잡았고, NULL일 때는 NULL을 저장하도록 고쳤다.
- 화면: 좁은 폭에서 시작일 라벨이 두 줄로 접혀 입력칸이 어긋날 수 있어 라벨을 줄이고 제목을 분리했다.

### 검증하면서 확인한 것 (기능 변경 아님)

- 회귀 묶음을 다른 순서로 돌리면 축소 묶음의 메모리 최고치 단언(400MiB)이 실패한다. 그 값은 API 컨테이너가 뜬 뒤의 누적 최고치라서, 동시 요청이 있는 묶음을 먼저 돌리면 넘는다. 기존 순서에서는 통과한다. 새 묶음만 돌렸을 때의 최고치는 256MiB로, 기존 묶음 하나(218MiB)와 같은 수준이다. 스테이징은 기존 순서를 유지하고 새 묶음을 마지막에 둔다.
- 개발 PC(Windows)에서는 `business-calendar` 웹 시험 파일이 가끔 프로세스 오류로 죽는다(이번 변경과 무관한 파일). 고정 이미지에서는 재현되지 않았다.

## 한계와 열린 항목

- **건별 조회 기록이 없다.** 본인·회사·운영자의 조회, 공유 링크 열람자, 외부 서비스 호출은 이번 자료에 "기록되지 않는 처리"로만 나온다. 확인자료의 자동 기록·보존(취급대장, 접근기록)은 준비 문서 S3의 별도 작업이다.
- **수집은 일별 집계다.** 건별 수집 시각은 7차 위치 파일(좌표 포함, 31일 이내)에서 확인한다. 위치 파일에는 수집 방법이 없다.
- **보존 기간 불일치.** 공유 링크는 만료·회수 30일 뒤, 알림 대기 기록은 14일 뒤, 장치 감사 기록은 365일 뒤나 연결 해제 시 삭제된다. 확인자료 보존 기간을 정하면 이 삭제 주기를 함께 검토해야 한다. 이번에는 바꾸지 않았다.
- **회사 자료.** 회사 차량으로 수집된 위치의 수집·이용·제공사실은 포함하지 않는다. 회사 자료 검토 절차로 다룬다.
- **실제 규모.** 운영 서버는 디스크가 느려 큰 계정에서 10초 제한에 걸릴 수 있다. 그 경우 기간을 나누어 발급한다. 운영에서의 실제 시간은 배포 뒤 모의 확인에서 본다.
- 정정 요구(오류가 있는 확인자료의 정정)는 기존 정정 요청 종류로 접수하며 이번에 새로 구현한 것은 없다.
