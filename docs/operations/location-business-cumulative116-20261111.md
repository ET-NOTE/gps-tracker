# 116차 — 최신 API·웹의 누적 전환과 복구 리허설

2026-11-11. 마지막으로 확인한 운영 스키마 **99에서 112로 전환하고 115차 API·웹을 사용하는 후보**를 격리 환경에서 검증했다. 누적 전환·장애 복구·권리 경계 회귀 검증은 통과했다. **운영 미배포, `activation_ready=false`**다. 새 DB 마이그레이션이나 펌웨어 변경은 없다. 이번 라운드에서는 운영 서버를 조회·변경하거나 운영 데이터·키를 복사하지 않았다.

## 검증 범위

실제 99 바이너리로 DB를 만든 다음 합성 위치 원본 130,000행을 넣었다. 이 중 17,000행이 배치이며, 623,000개 표본을 전개하면 조회 기간 내 중복 제거 결과는 283,001점이다. 계정·SIM·좌표의 전환 전후 값을 대조했다. 115차의 8 SIM·31일 부하 시험을 이번에 다시 수행한 것은 아니다.

빌드 호스트 `etcom-hub`의 내부 Docker 네트워크와 외부 포트 없는 TimescaleDB 2.19.3/PG14를 사용했다. DB는 2 CPU/1,500MiB·임시 메모리 파일시스템 1,600MiB, API는 550MiB다. 여기서 측정한 전환·복구 시간을 실제 VPS의 디스크 성능이나 정비시간 추정치로 사용할 수 없다. 실험용 키·계정만 사용하고 외부 알림은 보내지 않았다.

API SHA-256은 `a433b9a114131e235068cc0359b8535aaf9529d396b47785c8eb6c4c6ca17d10`이다. 115차에서 검증·빌드한 바이너리를 재사용하되 240개 API 컴파일 입력이 현재 소스와 같은지 확인했다. 일반 Rust 83개·웹 252개 결과는 115차의 결과이며 이번 라운드에서 모두 다시 실행한 것이 아니다.

제한 계정의 단일 99→112 마이그레이션은 0.560초였지만, **DB 암호화 단계만 213.037초**였다. 전체 운영 중단시간을 0.560초로 계산하면 안 된다. 합성 DB 크기는 91,169,283→310,657,827바이트, 시험 클러스터 시작 이후 WAL은 556,909,768바이트였다. 암호화 백업 117,956,783바이트, 덤프 4.034초·복원 2.506초도 위 격리 환경의 측정이다.

`pg_dump`의 Timescale 순환 외래키·chunk 안내는 원본 로그에 남겼다. 전체 덤프를 복원한 뒤 모든 원본 값·파일 해시를 대조했다. 실제 외부 백업·체크포인트 보관 장소와 담당자 검증은 별도다.

## API·웹 교체 실패

고정된 시험 도구로 실제 API 프로세스를 바꾸고 웹 디렉터리 링크를 원자적으로 교체했다. 웹은 루프백 HTTP에서 실제 HTML·진입 JS·vendor·CSS를 바이트 대조했다. 운영 Nginx·WAF·브라우저 서비스워커·모바일 앱 시험을 대신하지 않는다.

- 해시가 맞지 않는 산출물과 스키마 99 복구 대상을 **서비스 중지 전에 거부**했다.
- API 시작 실패, 새 API 준비 직후 실패, 웹 교체 직후 실패를 각각 주입했다. 스키마 112를 이해하는 이전 112 후보 API·웹으로 복구한 뒤 health·권한 있는 위치 조회·정적 파일을 확인했다.
- 세 시험의 전환·실패·복구·검사 합계는 3.474/4.437/6.118초였다. 실제 중단시간이나 운영 복구시간 목표가 아니다.
- 원본 130,000행의 암호문과 SIM 귀속이 동일했고 최종 115 API·웹으로 다시 전환했다. 남은 위치 조회와 idle transaction은 0이었다.

**이 시험의 복구 대상은 운영 중인 99 바이너리가 아니다.** 암호화 뒤 99로 다운그레이드하지 않는다. 이전 112는 113~115의 성능·취소 보완을 포함하지 않으므로 이 호환성 시험이 이전 112의 운영 사용을 권하는 것은 아니다. 운영에서는 동일 검증본 재시작이나 전진 수정, 필요하면 암호화 백업과 최신 권리 체크포인트를 복원하는 경로를 준비한다.

## 운영 적용 전 절차

1. 운영 스키마·바이너리·웹·DB 계정·GPS 쓰기 작업 목록을 새로 확인하고 전환 대상과 후보 해시를 고정한다. 이번 라운드는 운영을 다시 조회하지 않았다.
2. 실제 VPS의 디스크·RAM·연결 여유와 암호화 변환 중 백업·WAL·임시 파일 공간을 확인한다. 다른 프로젝트·백신·WAF도 포함한다. **단일 API** 기준이다.
3. 외부에 보관할 키·암호화 백업·최신 권리 체크포인트와 담당자를 확인한다. 데이터 수신 중단시간, 단말 버퍼·재전송의 실물 인수도 별도로 확인한다.
4. 정비시간에 모든 GPS 쓰기 작업을 멈추고 세션을 비운다. 바인드 로깅·기존 Timescale 보관 작업을 확인한 뒤 제한된 소유자 계정으로 마이그레이션한다. 정책을 자동으로 켜지 않는다.
5. 승인한 암호화 전환에서 유지보수 차단 → DB/파일 변환 → 평문 잔여·조회 준비 대기 0 확인 → 제한된 runtime 계정과 키로 기동 순서를 따른다. 실패하면 차단 상태를 유지하고 커밋된 지점에서 재개한다.
6. 백업을 복원하면 API를 열기 전에 최신 철회·중지·파기 체크포인트를 적용한다. 과거 동의나 이미 삭제한 위치, 발송 완료 통보가 되살아나지 않아야 한다.
7. API·웹의 동일 릴리스와 권한·수집·원장·복호화·파일·오류율을 확인한 뒤 정비 상태를 해제한다. 원장·제공·파기 정책 활성화는 별도로 확정한 값을 사용한다.

이는 전환 준비 절차이며 이번 시험 도구를 운영 주소로 바꿔 실행하는 절차가 아니다. 운영 현황에 맞는 배포 절차와 복구 대상 고정이 추가로 필요하다.

## 남는 조건과 다음 순서

115차에서 두 API의 월간 조회 408 10건과 느린 I/O의 원장 확인 503 21건이 발생했다. 이번에 성능 수정을 하지 않았으므로 그대로 열린 항목이다. 다음은 **실제 VPS 자원·공유 I/O와 원장 시작/완료 지연 계측, 복호화 SQL 임시 파일·swap 보호**다. 전체 DB 연결 예산도 확인하며 다중 API 증설은 하지 않는다. 상세는 [열린 항목](../reviews/gps-open-items.md)을 따른다.

정책·동의, 키/체크포인트 외부 보관, 관리자 PC/IP/MFA, 실제 FCM/경보, 실물 TLS/24시간 절전, 백신/WAF 실무 검증의 기존 보류도 유지한다. 이 리허설만으로 운영 전환을 승인하거나 위치정보사업 제출 요건 전체 충족을 판정하지 않는다.

## 재실행

`ops/prepare_cumulative116.py`는 고정된 112·115 산출물 해시를 검사한 뒤 전용 작업 폴더를 만든다. 입력은 `gps-tracker-api`, `gps-tracker-web`, `ops`의 Git archive와 파일별 SHA-256 manifest다. 생성된 폴더에서 다음 순서를 따른다.

1. `rehearse_cumulative116.py`: 99→112, 단계별 실패, 암호화 중단·복원.
2. `rehearse_release116.py`: API·웹 교체와 호환 복구.
3. `check_cumulative116.py`: 업무·권리 회귀, 최신 체크포인트 복원.
4. `run_regressions116.py`: 동의 이력·매핑·외부 처리 경계.
5. `src/ops/finish_cumulative116.py check`: 최종 API 재기동·소스·평문 잔여 검사.
6. `src/ops/stage_cumulative116.py`: 결과·소스·과거 SQL을 검사하고 후보 압축·검증.
7. `src/ops/finish_cumulative116.py cleanup`, `export`: 고정 시험 자원 정리와 원본 증빙 내보내기.

스크립트는 이번 고정 작업 폴더를 위한 일회성 시험 도구다. 준비·실행·정리 도구는 운영 주소나 운영 DSN을 입력받지 않는다. 정리된 환경을 재실행하려면 기존 후보·증빙을 보존하고 별도 시험 작업 경로를 명시적으로 준비해야 한다.
