## 배포 중 발견하고 보완한 세 문제

1. **기존 TimescaleDB 2.19.3의 압축 NULL 복원 오류.** 원래 압축 상태의 `pg_dump`를 임시 DB에 복원하자 `heading`의 `Bg==` 표현에서 COPY가 실패했다. 같은 증상은 [공식 이슈 #8893](https://github.com/timescale/timescaledb/issues/8893), [수정 PR #8153](https://github.com/timescale/timescaledb/pull/8153)에 있다. 오류가 있는 덤프를 복구 가능하다고 처리하지 않았다. GPS 연결만 잠시 차단해 PostgreSQL의 DB 단위 템플릿 복사본을 만든 뒤, **백업용 복사본에서만** 25개 청크를 압축 해제했다. 그 덤프를 다시 별도 DB에 복원해 원본 열 해시를 대조했다. 운영 DB의 압축 청크와 공유 PostgreSQL 버전은 변경하지 않았다. 현재 버전의 일반 압축 덤프만으로 복원 가능하다고 가정하면 안 된다. DB 버전 업그레이드는 별도 작업이다.
2. **136차 웹 후보의 legacy base.** API/SQL 후보는 사용할 수 있었지만 웹 빌드가 `/gps-tracker/app/`를 참조했다. 첫 실제 브라우저 검사에서 JS 요청에 HTML이 반환되어 빈 화면이 확인됐다. 즉시 이전 웹 심볼릭 링크로 돌렸고 API/DB는 유지했다. 같은 제품 소스를 `VITE_BASE=/`로 다시 빌드해 브라우저 사전 확인 후 r2로 교체했다. 진입 파일 해시뿐 아니라 JS MIME과 실제 화면까지 확인했다. 이 실패와 임시 복원도 증거에 보존했다.

3. **외부 감시의 GET `/ingest` 호환성.** 새 접근기록 보호가 POST 전용 경로에 대한 GET을 미분류 요청으로 처리해503을 반환했다. 실제 POST 수집은 계속됐지만 외부 감시는405와 `Allow: POST`를 기대하므로 장애로 인식할 수 있었다. 등록된 경로의 허용되지 않은 메서드는 핸들러를 실행하지 않고405/Allow로 거절하도록 수정했다. 미검토 경로는 계속503으로 차단하며 위치조회/인증을 우회하지 않는다. fmt/clippy·Rust **98통과/9격리 검사 제외**,11:26:10 KST r3 적용 후 HTTP/HTTPS GET·HEAD405, 잘못된 JSON POST400을 확인했다.
