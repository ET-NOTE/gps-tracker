## 이번에 완료한 범위

14차의 회사 영수증 원본 연결은 100만 화소·한 변 2048px 이하 PNG/JPG만 열 수 있어 휴대폰으로 찍은 영수증 대부분이 거부됐다. 15차는 서버가 큰 원본을 **한도 안으로 축소하고 촬영 방향을 바로 세운 정규화 이미지**로 만든 뒤, 담당자 화면·영역 선택·미리보기·발급·감사 기록이 모두 그 정규화 픽셀을 기준으로 하도록 했다.

1. 담당자가 **회사에 저장된 영수증 → 원본 확인·불러오기**를 누르면 서버가 원본을 정규화해 보여 준다. 축소했거나 방향을 보정한 경우 화면에 `원본 4000 × 3000px 축소 · 촬영 방향 보정(시계 방향 90° 회전)`처럼 표시한다.
2. 영역 좌표는 정규화 이미지의 픽셀 좌표다. 원본 크기나 회전 전 크기로 보낸 선택은 거부한다.
3. 미리보기·발급 때 서버는 저장된 원본에서 같은 정규화 픽셀을 다시 만들어 선택 영역만 남긴다. 브라우저가 보낸 픽셀은 계속 무시한다.
4. 발급 이력에는 원본이 어떻게 변환됐는지(원본 크기·결과 크기·적용한 방향)만 남는다. 원본 픽셀이나 메타데이터는 복제하지 않는다.

직접 준비한 이미지(수동 경로)도 100만 화소·한 변 2048px를 넘으면 담당자 브라우저에서 같은 규칙으로 축소한다. 수동 경로의 방향 보정은 브라우저가 한다.

## 정규화 규칙

- 결과는 불투명 8비트 RGB, 한 변 2048px 이하·100만 화소 이하다. 비율을 유지하는 가장 큰 크기를 정수 연산으로 정한다(예: 4000×3000 → 1154×865). 이미 한도 안이면 크기를 바꾸지 않는다.
- **JPEG**: 디코더의 DCT 단계 축소(1/8·1/4·1/2) 중 목표 크기에 닿는 가장 작은 배율로 디코딩한 뒤, 정수 면적 평균으로 최종 크기에 맞춘다. 전체 해상도 픽셀을 메모리에 올리지 않는다.
- **PNG**: 행 단위로 읽으면서 면적 평균을 누적한다. 투명 영역은 14차와 같이 흰색 배경으로 합성한다.
- **촬영 방향**: JPEG EXIF Orientation(1~8)을 축소 뒤에 적용한다. 태그가 없거나 손상됐으면 보정하지 않는다. **14차와 달라진 점**: 한도 안의 작은 JPEG도 이제 바로 세운다. PNG의 eXIf는 적용하지 않는다.
- 같은 원본 바이트는 항상 같은 정규화 픽셀이 된다. 서버는 이 픽셀의 SHA-256(정규화 버전·크기 포함)을 계산한다.

## 읽기 증빙과 픽셀 결합

14차의 읽기 증빙은 원본 해시·revision만 묶었다. 축소·회전이 들어가면 "담당자가 본 이미지"와 "선택을 적용한 이미지"가 달라질 수 있으므로, 마이그레이션 `0097`로 다음을 추가했다.

- `privacy_receipt_reads.pixels_sha256`, `normalization`: 담당자에게 보여 준 정규화 픽셀의 해시와 변환 내용.
- `privacy_image_deliveries.source_normalization`: 발급본이 만들어진 변환 내용.
- 미리보기·발급은 **같은 담당자가 1시간 이내에 같은 정규화 픽셀을 읽은 증빙**이 있어야 통과한다. 픽셀 해시가 없는 이전 증빙이나 다른 픽셀의 증빙으로는 선택을 승인할 수 없고, 원본을 다시 불러와야 한다.

원본 변경 시 동작은 14차 그대로다. 지출 수정, 영수증 바이트 교체·제거, 직원 변경, 회사 검토 변경이 있으면 기존 제공본 다운로드를 차단하고 임시 PNG를 제거한다. 교체된 원본은 새로 읽고 새로 선택해야 한다.

| 항목 | 한도 | 넘으면 |

| 프로그레시브 JPEG 축소 | 800만 화소 (전체 해상도 계수를 메모리에 유지하므로) | 400 |

| 큰 원본 동시 축소 | 1건 (기존 디코딩 동시 2건은 유지) | 429 |

한도 밖이면 읽기 증빙을 남기지 않는다. 격리 환경의 API 컨테이너(메모리 550MB 제한)에서 6,400만 화소 JPEG·전체 배율 컬러 JPEG·프로그레시브 JPEG·RGBA PNG를 연속 처리한 뒤 컨테이너 메모리 최고치는 약 142MB(처리 전 약 69MB)였다.

## 제한과 남은 작업

- 축소본은 최대 100만 화소다. 고해상도 사진의 작은 글씨는 축소 후 읽기 어려울 수 있다. 영역을 먼저 고르고 그 부분만 높은 해상도로 제공하는 기능은 없다.
- 세로로 긴 캡처(예: 1080×8000)는 한 변 2048px 제한 때문에 폭이 크게 줄어든다.
- 잘린 JPEG를 고정된 디코더가 오류로 처리하는지, 남은 영역을 채워 여는지는 이번에 검증하지 않았다. 잘린 PNG와 손상된 헤더는 400으로 거부됨을 확인했다.
- WebP 영수증과 PNG eXIf 방향은 지원하지 않는다.

- [x] 운영 배포: 2026-11-06 12:02 KST 완료(아래 "운영 배포").
- 14차의 나머지 열린 항목(공용 문서 귀속, 원본 정정·파기, 증빙·백업 보관, 대리인 확인, TLS 승격·절전 실증·서버 분리)은 그대로다.

## PDF 페이지 제공 — 결정 필요

> **2026-11-06 결정**: 서버가 원본에서 렌더링하되 API 전체의 툴체인은 올리지 않고 PDF 처리기만 별도 툴체인으로 빌드해 분리한다. 구현과 검증은 [16차](location-rights-round16-20261106.md)에 있다. 아래는 결정 전 검토 기록이다.

서버가 PDF 페이지를 직접 그리려면 PDF 렌더러가 필요하다. 순수 Rust 렌더러 `hayro`를 고정 툴체인(Rust 1.88.0)에서 빌드해 본 결과, 0.6.0과 0.9.0 모두 의존 크레이트가 Rust 1.89~1.92를 요구해 **빌드되지 않았다**(추가 크레이트 약 95개). 선택지는 다음과 같다.

| 방식 | 서버 원본에서 픽셀 재생성 | 필요한 것 | 주의 |
|---|---|---|---|
| A. 툴체인을 1.92 이상으로 올리고 서버에서 렌더링 | 유지 | 빌드 이미지·전체 회귀 재검증, 렌더러를 자원 제한된 별도 프로세스로 격리 | 렌더러가 0.x 단계. 한글 글꼴이 내장되지 않은 PDF의 표시 품질은 실제 표본으로 확인 필요 |
| B. 담당자 브라우저에서 pdf.js로 렌더링 | 불가(브라우저 픽셀을 신뢰, 현재 수동 경로와 같은 수준) | 웹 의존성 추가, 원본·페이지·revision 결합과 변경 시 무효화 | 원본 PDF 전체가 담당자 브라우저로 전달됨 |
| C. 서버에 외부 렌더러(poppler 등) 설치 | 유지 | 공유 VPS에 시스템 패키지 설치와 샌드박스 | C/C++ 파서가 API 계정 권한으로 실행됨. 권장하지 않음 |

그때까지 PDF는 기존처럼 필요한 페이지를 이미지로 준비해 수동 경로로 제공한다. OCR은 어느 방식에서도 검토 보조일 뿐 자동 공개 승인에 쓰지 않는다.

   ```bash
   tar -xzOf source.tar.gz ops/stage_privacy_raster.py > stage.py
   /home/etcom-hub/build/gps-location-erasure-20261105/venv/bin/python stage.py "$PWD" <커밋 전체 ID>
   ```

   끝나면 `out/`이 운영 서버에 둘 디렉터리 전체다: API 바이너리, 웹 묶음, 소스 묶음, `manifest.json`, `validation.json`, `rehearsal.json`, 운영 스크립트 2개, 일회용 모의 계정 자격증명(`smoke-private.json`, 권한 600, 출력·커밋하지 않음).

3. **전송** — `out/`을 운영 서버 `/home/mmm/gps-artifacts/privacy-raster-20261106-r1`에 둔다.

4. **점검** — 아무것도 바꾸지 않는다. 운영이 14차 그대로인지(health의 릴리스, 실행 바이너리 해시, 웹 링크, 마이그레이션 1~96 체크섬, 새 열 없음, 이전 시도의 잔여물 없음)와 산출물 해시를 대조한다.

   ```bash
   python3 release_privacy_raster.py check
   ```

5. **적용** — 점검을 다시 한 뒤 진행한다.

   ```bash
   python3 release_privacy_raster.py apply
   ```

### 실패와 되돌림

- 점검이 맞지 않으면 첫 변경 전에 멈춘다. 마이그레이션 트랜잭션이 실패하면 롤백되고 준비 파일만 옆으로 치운다.
- **새 API가 45초 안에 정상이 되지 않으면 `apply`가 스스로 되돌린다**: API 정지 → 0097 제거(열 삭제와 SQLx 기록 삭제) → 이전 바이너리 복원 → 기동 → 이전 릴리스 health 확인. 이 동안 API는 내려가 있다.
- 적용 후 문제가 있으면 `python3 release_privacy_raster.py rollback`으로 같은 되돌림을 한다(웹 링크도 이전으로).
- 되돌림은 **새 열을 쓰는 행이 없을 때만** 허용한다. 15차 화면으로 영수증을 한 번이라도 읽었으면 감사 기록을 지우게 되므로 거부하고, 그때는 앞으로 고친다.
- API가 기동 시 모르는 마이그레이션을 거부하므로, 0097을 남긴 채 14차 바이너리만 복원하는 방법은 쓸 수 없다.
- 적용 중 바이너리 교체·재시작에 몇 초의 API 중단이 있다. 그 사이 진행 중이던 미리보기는 409가 되며 원본을 다시 불러오면 된다. 이미 발급된 제공본은 영향을 받지 않는다.

### 운영 스크립트의 안전장치

- 리허설을 통과한 **그 스크립트와 그 바이너리**만 운영에서 실행된다(`rehearsal.json`의 해시 대조).
- 이전 릴리스·바이너리 해시·웹 경로를 고정했다. 다른 상태에서는 실행되지 않으므로 97 적용 뒤 다시 `apply`해도 변경 없이 멈춘다.
