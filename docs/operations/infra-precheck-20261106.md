## API 실행 권한 (준비 문서 S1의 P0)

- `gps-tracker-api.service`는 `User=mmm`이고 서비스 보호 옵션이 없다(시스템 호출 필터·메모리 한도·`NoNewPrivileges`·`ProtectSystem` 모두 없음).
- `mmm`은 `sudo`·`docker` 그룹이며 `NOPASSWD: ALL`이다. API나 그 자식 프로세스가 뚫리면 서버 전체 권한으로 이어진다.
- 같은 계정으로 `gps-tracker.service`, `pm2-mmm.service`, 계정·파일 정리 타이머, `notion-notify`가 실행되고 배포도 이 계정으로 한다.
- API의 DB 계정 `gps_tracker_app`은 슈퍼유저가 아니다. 환경파일은 `mmm:mmm 600`, 비공개 업로드 디렉터리는 `mmm:mmm 700`이다.
- SSH는 키 인증만 허용하지만 `PermitRootLogin=yes`다.

**분리 방향(미구현)**: 로그인·sudo·docker 권한이 없는 실행 전용 계정을 만들어 API와 정리 타이머를 그 계정으로 옮기고, 배포는 지금처럼 `mmm`+sudo로 한다. 바이너리·환경파일·업로드 디렉터리의 소유와 권한, 서비스 보호 옵션, PDF 처리기의 별도 계정 실행을 함께 정한다. 릴리스 스크립트(`release_privacy_*.py`)가 경로와 서비스 계정을 읽으므로 그 영향도 확인한다.

## 디스크 지연과 느린 쿼리

- API 로그의 `slow statement`(1초 초과) 경고는 어제도 시간당 10~29건이었다. 대부분 `COMMIT`과 단건 `UPDATE`다. 16차 배포나 호스팅사 작업 이전부터 있던 현상이다.
- 30초 표본에서 `vda`는 쓰기 396회·2MB에 **평균 쓰기 지연 115ms**였다. 큰 쓰기를 하는 프로세스는 없었다(30초에 20MB를 넘긴 프로세스 0개). CPU 대기는 0, I/O 대기(PSI full)는 5분 평균 6~15%다.
- 즉 쓰기량이 아니라 저장장치 응답이 느리다. PostgreSQL은 `synchronous_commit=on`, `fsync=on`이라 커밋마다 그 지연을 그대로 받는다. 체크포인트는 시간 기준으로만 돌고 있고 동기화 시간도 짧다.
- 같은 PostgreSQL에 다른 프로젝트 DB(`bbb_db` 5.7GB)와 개발용 사본 DB 6개(합계 약 0.9GB)가 있다.
- 가능한 조치: 카페24에 디스크 지연 문의, GPS 전용 서버 이전(준비 문서의 권장안), 유실을 감수할 수 있는 경로에 한한 `synchronous_commit` 조정. 마지막은 장애 시 최근 커밋 유실 가능성을 받아들이는 결정이라 정책 판단이 필요하다. 아무것도 바꾸지 않았다.

## 외부 접속 감시 — 다음 라운드 준비 (2026-11-06 조사)

### 지금 있는 것

- `status.serial.kr`의 Uptime Kuma 컨테이너가 **이 서버 안에서** 실행된다. 감시 항목은 10개다: 서버가 스스로 보내는 push 4개(디스크, 메모리, pm2, 인증서 만료)와 HTTP·포트 확인 6개(`iot.serial.kr` 3개, `seriallog.com/api-docs`, `https://gps.serial.kr` 첫 화면, mediamtx).
- **알림 수단이 하나도 등록돼 있지 않다**(알림 설정 0건). 감시가 실패를 감지해도 아무에게도 알리지 않는다.
- GPS는 첫 화면만 본다. API `health`(DB 포함), SSH 포트, 단말기 수집 경로는 보지 않는다.
- 11월 6일처럼 서버 전체가 막히면 감시 자체가 같이 멈춘다.

### 서버 밖에서 볼 수 있는 위치

- 사무실 빌드 호스트(`etcom-hub`)는 4주 넘게 연속 가동 중이고, 공인 주소가 VPS와 다르며, 그 자리에서 `https://gps.serial.kr/health`(200), `status.serial.kr`, SSH 22 포트에 닿는다. `curl`·`python3`·`jq`가 있고 사용자 단위 systemd 타이머를 로그인 없이 돌릴 수 있다(linger). 기존 감시 도구는 없다. 외부 메일 발송 포트(587)는 열려 있다.
- 사무실 망과 전원에 의존한다는 한계가 있다. VPS·호스팅 업체와는 독립이다.

### 제안하는 구성 (구현됨: [인프라 2차](infra-round2-external-watch-20261106.md))

1. 빌드 호스트에 사용자 단위 타이머로 1분마다 도는 점검 스크립트(표준 라이브러리만 사용, root 불필요, 새 서비스 설치 없음).
   - `https://gps.serial.kr/health`가 `ok`·`db`·운영 환경인지
   - SSH 22 포트가 응답하는지
   - `status.serial.kr`이 응답하는지
   - 수집 주소가 살아 있는지(위치를 보내지 않는 확인)
2. 연속 실패 횟수로 장애를 판정하고, 발생·지속·복구를 알린다. 한 번의 지연으로는 알리지 않는다.
3. 감시 자체가 멈춘 것을 알 수 있게, 점검 스크립트가 VPS의 Uptime Kuma에 주기 신호(push)를 보낸다. 서로가 서로를 본다. 이를 위해 Kuma에도 알림 수단을 등록해야 한다.
4. 격리 리허설: 가짜 대상 서버로 정상·지연·거부·잘못된 응답·복구를 재현해 판정과 알림 횟수를 확인한다.

### 시작 전에 정해야 할 것 (운영자) — 2026-11-06 결정: 메일(SMTP), 빌드 호스트만, Kuma 알림 등록

- **알림을 받을 수단**: 메일(SMTP 계정), 메신저 웹훅(텔레그램·슬랙·디스코드 등) 가운데 무엇으로 받을지. 비밀값(웹훅 주소·토큰·비밀번호)은 운영자가 빌드 호스트의 본인만 읽는 파일에 직접 넣는다. 에이전트는 비밀값을 받거나 입력하지 않는다.
- **감시 위치**: 빌드 호스트로 할지, 사무실과도 독립된 외부 서비스를 함께 쓸지(외부 서비스 가입은 운영자가 한다).
- **Uptime Kuma 알림 등록**: 같은 수단을 Kuma에도 등록할지. 등록은 Kuma 화면에서 운영자가 한다.
