# 운영 서버 접속 장애 — 호스팅사 시스템 작업 (2026-11-06)

간단 기록이다. 원인은 호스팅사 작업이며 GPS 배포·개발 작업과 무관하다.

## 경과

- **00:00~03:00 KST**: 카페24가 리눅스 가상서버호스팅 긴급 시스템 작업을 진행했다(가상 네트워크 장치 보안 설정 적용). 작업 대상 가상서버가 재부팅됐다. 공지: <https://help.cafe24.com/notice/system-notice/20261106_linux-vps-maintenance>
- **00:32~00:34 KST**: 14차 배포와 확인은 정상 응답했다. 재부팅은 그 뒤다.
- **00:47~00:48 KST**: 서버 로그상 호스팅사 작업에 의한 재부팅. 마지막 단말기 수신은 00:45:29다.
- **10:50~11:17 KST**: 15차 배포 점검을 시작하려다 발견했다. 사무실 망에서 22·80·443 포트 무응답, 해외 경로에서 443 연결 거부. `shield.serial.kr`, `seriallog.com`도 같았다.
- **조치(카페24)**: 서버에 접속해 보니 UFW에 등록된 웹 서비스 허용 규칙이 실제 수신 트래픽 처리 규칙과 연결되지 않아 접속이 차단돼 있었다. 누락된 연결 규칙을 추가해 복구했다.
- **11:01~11:04 KST**: 콘솔에서 재부팅했다. 부팅 후에도 API가 DB에 연결하지 못해 3초마다 재시작을 반복했다(252회). 방화벽 연결 누락이 서버 안의 로컬 연결까지 막은 것으로 보인다.
- **11:39 KST**: 카페24 조치 뒤 API가 DB에 연결돼 정상 기동했다. 단말기 수신은 11:46:25에 재개됐다. **수신 공백은 00:45:29~11:46:25(약 11시간)**이다.
- **11:53 KST**: 사무실 망에서 22·80·443 응답과 `health`(14차 릴리스, DB 정상)를 확인했다.

## 우리 작업과의 관계

장애 중 서버를 볼 수 없어 로컬 기록으로 확인했다.

- 운영 서버에 대한 마지막 명령은 00:34 KST의 14차 배포 확인이다. 그 뒤 장애 발견까지 어떤 에이전트 세션도 서버에 명령을 보내지 않았다.
- 방화벽을 바꾼 것은 11월 5일 11:29~12:10 KST의 TLS 시험뿐이다. 18443 포트의 임시 허용 규칙을 내용 지정으로 추가·삭제했고 22·80·443 규칙은 건드리지 않았다.
- 디스크 여유는 11월 3일 5.4G에서 11월 6일 00:29 4.7G로 줄었다(배포 한 번에 약 45MB). 급증은 없었다.
- GitHub 저장소에는 푸시로 서버에서 무언가를 실행하는 워크플로·웹훅·러너가 없다.

## 열린 항목

- [ ] **재발 가능**: 연결 규칙이 왜 빠졌는지는 카페24도 확인하지 못했다. 서버 재부팅이나 방화벽 설정 재적용 때 같은 문제가 날 수 있다. 부팅 때 방화벽을 적용하는 경로(UFW 서비스, 다른 규칙 복원 서비스, 자동 실행 스크립트)를 점검해야 한다. 인프라 라운드 항목이다.
- [ ] 부팅 후 웹 서버·API 등 서비스가 자동으로 시작되는지 확인.
- [ ] 수신이 막혀 있던 동안 단말기 위치 보고가 유실됐는지, 단말기 버퍼로 복구됐는지는 확인하지 않았다.
- [ ] 장애를 약 10시간 뒤 배포 점검에서야 알았다. 외부에서 접속 상태를 감시하는 수단이 없다.
- 배포 스크립트는 API만 재시작하고 방화벽이나 서버를 재시작하지 않는다.
