## 별도 구성 위험 — 부팅 때 두 방화벽 서비스의 순서 (2026-11-06 오후 조사)

**이번 장애의 원인으로 확정한 내용이 아니다.** 장애 원인은 호스팅 업체가 확인한 긴급 업데이트 문제다. 아래는 운영 서버를 읽기 전용으로 조사하다 확인한 구성상의 위험과, 같은 패키지 버전의 격리 컨테이너에서 한 재현 결과다. 장애와의 관계는 확정하지 않았다.

- **구성**: 2026-05-15에 `iptables-persistent`가 설치된 뒤로 부팅 초기에 `ufw.service`와 `netfilter-persistent.service`가 **순서 없이 동시에** 실행된다. 둘 다 패킷 필터를 다시 쓴다.
- **`netfilter-persistent`가 하는 일**: `/etc/iptables/rules.v4`(5월 15일 저장분)를 복원한다. 이 파일에는 DB 포트(5432) 규칙 3개와 Docker 체인만 있고 UFW 체인이 없다. 복원은 필터 테이블 전체를 비운 뒤 적재한다.
- **이 구성에서 생길 수 있는 일**: 복원이 UFW 초기화 도중에 끼어들면 UFW가 먼저 만들어 둔 `INPUT → ufw-*` 연결 규칙이 지워진다. UFW는 연결 규칙을 처음 한 번만 넣으므로 다시 만들지 않는다. 그 결과 `INPUT` 정책은 DROP인데 UFW 체인으로 가는 길이 없어 **모든 수신이 버려진다. 루프백도 포함**이라 API가 로컬 DB에도 붙지 못한다.
- **같은 날 부팅 로그에 남은 기록**(관찰 사실이며, 호스팅 업체 문제의 결과인지 독립된 현상인지는 확정하지 않았다):
  - 00:48 부팅: `ufw-init`이 `RULE_APPEND failed (No such file or directory): rule in chain ufw-track-output`로 실패하고 `Failed to start Uncomplicated firewall`.
  - 11:04 부팅(콘솔 재부팅): UFW는 "Finished"로 끝났고, 그 뒤에도 `INPUT`에 UFW 연결이 없는 상태였다.
- **순서에 따라 결과가 달라진다**: `netfilter-persistent`가 UFW보다 먼저 끝나면 정상이다. 순서를 정해 두지 않았으므로 재부팅 때 아래 재현의 다른 결과가 나올 수 있다.

### 재현 (격리 컨테이너, Ubuntu 22.04 · ufw 0.36.1 · iptables 1.8.7 nf_tables · iptables-persistent 1.0.16)

UFW 시작은 `iptables-restore`를 10번 호출한다. 그 각 호출 직전에 `netfilter-persistent` 복원을 끼워 넣어 모든 순서를 실행했다.

| 순서 | 결과 |
|---|---|
| `netfilter-persistent` → UFW (끼어들기 위치 1 포함) | **정상**: 정책 DROP, UFW 연결 6개 |
| UFW 시작 도중 (위치 2~10, 9가지) | **전부 차단**: 정책 DROP, UFW 연결 0개. 위치 2·4~9는 UFW가 실패로 끝나고 위치 3·10은 성공으로 끝난다 |
| UFW → `netfilter-persistent` | **전부 개방**: 정책 ACCEPT, UFW 체인 없음. 5432 규칙만 남고 나머지 포트는 걸러지지 않는다 |

차단뿐 아니라 **방화벽이 통째로 꺼진 채 부팅될 수도 있다**는 점이 이 구성의 위험이다. 스크립트와 결과는 [firewall-race](evidence/incident-20261106/firewall-race/)와 [reproduction.json](evidence/incident-20261106/reproduction.json)에 있다.

### 현재 운영 방화벽 상태

- 카페24가 손으로 넣은 규칙 2개(`INPUT`의 22번 포트 허용, `INPUT → ufw-before-input` 연결)로 동작 중이다. 허용 규칙은 적용되지만 표준 구성(연결 6개)이 아니고, **이 규칙들은 저장되지 않아 재부팅하면 사라진다.**
- 이 상태에서 `ufw reload`는 오류(`problem running ufw-init`)로 끝나고 아무것도 고치지 못한다(격리 환경에서 확인). 운영에서 실행하지 않았다.
- IPv6 쪽은 연결 6개가 모두 있다.
- 점검: `sudo bash ops/check_firewall_layout.sh`(읽기 전용). 2026-11-06 현재 운영에서 "부팅 순서 미지정"과 "IPv4 INPUT 연결 1/6" 두 항목이 FAIL이다.

### 수정안 (별도 항목, 운영자가 실행)

권한 분리 라운드와 섞지 않는 별도 항목이다. 방화벽·시스템 설정 변경이므로 에이전트가 적용하지 않았다. 콘솔 접속 수단을 확보한 사람이 실행한다.

1. **부팅 순서 고정** — `sudo bash ops/fix_firewall_boot_order.sh`. `ufw.service`에 `After=netfilter-persistent.service` drop-in 하나를 추가한다. 실행 중인 방화벽은 건드리지 않고 다음 부팅부터 적용된다. 되돌리려면 그 파일을 지우고 `systemctl daemon-reload`.
2. **확인** — 계획된 시간에 카페24 콘솔을 열어 둔 채 재부팅하고 `check_firewall_layout.sh`가 모두 ok인지, 외부에서 22·80·443과 `health`가 응답하는지 본다. 재부팅 없이 표준 구성으로 되돌리려면 `systemctl stop ufw && systemctl restart netfilter-persistent && systemctl start ufw` 순서여야 하며(격리 환경에서 연결 6개로 복구됨을 확인) 그 1~2초 동안은 필터가 열린다.
3. **이후(인프라 라운드)** — 5432 규칙을 UFW로 옮기고 `iptables-persistent`를 제거해 방화벽 관리 도구를 하나로 줄인다. DB 포트의 외부 허용이 아직 필요한지도 그때 확인한다.

## 우리 작업과의 관계

장애 중 서버를 볼 수 없어 로컬 기록으로 확인했다.

- 운영 서버에 대한 마지막 명령은 00:34 KST의 14차 배포 확인이다. 그 뒤 장애 발견까지 어떤 에이전트 세션도 서버에 명령을 보내지 않았다.
- 방화벽을 바꾼 것은 11월 5일 11:29~12:10 KST의 TLS 시험뿐이다. 18443 포트의 임시 허용 규칙을 내용 지정으로 추가·삭제했고 22·80·443 규칙은 건드리지 않았다.
- 디스크 여유는 11월 3일 5.4G에서 11월 6일 00:29 4.7G로 줄었다(배포 한 번에 약 45MB). 급증은 없었다.
- GitHub 저장소에는 푸시로 서버에서 무언가를 실행하는 워크플로·웹훅·러너가 없다.
