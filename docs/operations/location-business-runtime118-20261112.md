## 2. 임시 데이터 보호 구성

이번 선택은 **용량 제한 tmpfs + 프로세스 swap 금지 + 시작 검사 + 마운트 의존성**이다. 현재3GB 공유 서버에 즉시 적용하자는 뜻이 아니다.

- 정렬용256MiB, 기본 fallback64MiB. 모두 `nosuid,nodev,noexec`, PostgreSQL 전용0700.
- 기본 `PGDATA/base/pgsql_tmp`는 보호된 fallback 안의 하위 디렉터리로 향하는 심볼릭 링크다. 마운트가 없어졌을 때 PostgreSQL이 일반 디렉터리를 새로 만들지 못하도록 아래 경로를 root 소유·쓰기 불가로 둔다.
- DB unit은 두 mount에 `BindsTo`/`After`로 연결된다. mount를 중지하거나 외부에서 해제하면 DB도 멈춘다. mount 복구 후 준비 unit이 필요한 하위 경로를 재생성한다.
- 시작 검사는 **실행 프로세스 자신의 mount/cgroup namespace**에서 수행한다. 열린 디렉터리 FD의 `mnt_id`로 실제 최상단 mount를 확인하므로 systemd의 중첩 bind mount를 오인하지 않는다.
- filesystem 종류/옵션/용량, fallback 연결, root 소유 보호 파일·라이브러리 해시, 실제 dumpable=0, `memory.swap.max/current=0`, `memory.max`를 검사한다. 틀리면 DB 시작을 거부한다.
- 실제 SQL 외부 정렬, 선택 tablespace 디렉터리 소실 시 보호 fallback, fallback 가득 참에 따른 실패, 정리 후 정상화를 확인했다. SQL 경로 이름만으로 보호 상태를 판정하지 않는다.

systemd의 mount 의존성은 [공식 문서](https://www.freedesktop.org/software/systemd/man/latest/systemd.mount.html)를 참조했으며 시험은 Ubuntu22.04 설치 버전에서 실행했다. tmpfs 크기는 최대치이고 항상 해당 RAM을 미리 점유한다는 뜻은 아니다. 다만 실제 사용 페이지를 포함한 메모리 상한과 swap 제어가 필요하다.

**암호화 임시 디스크 대안:** 이번에는 채택·설치·성능 검증하지 않았다. 메모리 압박을 줄일 수 있지만 fallback까지 암호화해야 하고 키 생성/폐기, 부팅 실패 처리, I/O 경합 검증이 필요하다. DB/API의 swap·core 문제도 별도로 남는다. 현재 공유 DB의 예산 부족을 해결했다고 표현할 수 없다.

## 3. 코어 덤프 보호와 검증 경계

운영의 `core_pattern`은 Apport 파이프이고 활성 상태다. `LimitCORE=0`만으로는 충분하지 않다. 파이프 방식은 커널이 RLIMIT_CORE를 무시할 수 있다. [Linux core 동작](https://man7.org/linux/man-pages/man5/core.5.html).

`runtime118_nodump.c`는 동적 로더가 실행한 **exec 이후, 애플리케이션 초기화 전**에 `PR_SET_DUMPABLE=0`을 설정·확인한다. 실패하면 종료한다. exec 전에만 설정하는 래퍼는 사용하지 않았다. [PR_SET_DUMPABLE](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), [execve](https://man7.org/linux/man-pages/man2/execve.2.html).

검증한 것:

- 라이브러리·설정은 root 소유이며 group/other 쓰기가 불가능해야 한다. 라이브러리 해시 불일치, 메모리 한도 불일치, 무제한 swap, unsafe mount 옵션은 시작 거부.
- 새 exec 프로세스와 fork 자식에서 dumpable=0. 실제 SIGABRT 시 core-dumped 상태 비트가 꺼짐.
- 실제 PostgreSQL backend를 SIGABRT로 중단한 뒤 DB가 복구됐으며 데이터·보호 정렬은 유지됨. 로그에 signal6이 있고 core-dumped 표시는 없음.
- 빌드 호스트와 운영의 전역 core 설정을 바꾸지 않았다. 타 프로젝트의 덤프 정책을 변경하지 않는다.

| 프로세스 | 이번 확인 | 남은 검증 |
|---|---|---|
| PostgreSQL14 | 실제 서비스 시작·backend 충돌·재시작·swap0 | 공유 운영 클러스터/정확한 운영 패키지 조건 |
| 동적 실행 프로세스 | Python exec/fork/abort로 보조 장치 작동 | 실제117 Rust API의 전체 수집·조회 경로 |
| PDF·암호화/복구·정리 작업 | 보호 프로파일 적용 대상에 포함 | 각 실제 서비스/작업의 전용 계정·swap·라이브러리·임시 파일 경로 통합 |

따라서 **모든 복호화 프로세스의 보호 완료가 아니다.** preload 환경이 제거되는 별도 서비스, 정적 실행 파일, 권한 전환/추가 exec, 프로그램이 dumpable을 다시 켜는 경우를 각각 확인해야 한다. root에 의한 정책 변경을 방어하는 수단도 아니다. 다음 누적 통합 라운드의 필수 게이트로 유지한다.

## 4. 117차 단위 오류 정정

기존 관측기는 `setting`과 `unit`을 구분 없이 연결했다. 실제 `shared_buffers`는 **94967 × 8kB =759736kB ≈741.93MiB**인데, `949678kB`로 오독했고117 시험 재생성에도 반영됐다. 당시 시험은 PostgreSQL 블록 단위 반올림 후 약927.41MiB다.

- 117 원본 JSON/로그/결과는 그대로 보존한다. 기존 수치는 그 잘못된 큰 버퍼 조건에서 나온 결과다.
- 117 문서의 “운영과 같은 버퍼 설정”을 정정했다. 더 큰 버퍼이므로 보수적/더 유리한 시험 중 어느 하나로 단정하지 않는다.
- 관측기는 값과 단위를 별도 JSON 필드로 출력하도록 수정했다. 시험 도구는759736kB를 사용하도록 수정했다.
- **이번21개 시험은 보호 기능 시험(shared_buffers128MB)**이며 수정된742MiB 조건의 월간·동시 부하 재시험이 아니다. 이 성능 재시험은119차에 넣는다.
