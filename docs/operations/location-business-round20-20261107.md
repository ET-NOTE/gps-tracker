# 20차 — 전송·저장 암호화: 핵심 필드 후보 검증

2026-11-07. 구현 기준 `bd00dfbc77889cfc2623fde8741c1db919729707`, 브랜치 `codex/location-business-prep`, [PR #248](https://github.com/ET-NOTE/gps-tracker/pull/248).

**20A(핵심 필드·TLS 후보)는 구현·격리 검증 완료, 운영 미배포다. 20차 전체 완료가 아니다.** 사용자가 별도 회사 암호화 기준 없이 필드 암호화와 단계적 전환을 선택했다. 원본·최근 위치·이벤트를 먼저 전환하고, 파생 저장소/파일·운영 전환을 20B 잔여 항목으로 분리한다. 현재 운영은 계속 **18A / 스키마 99**, 후보는 **103**이다. 실제 기기에 플래시하지 않았고 기존 HTTP 수집도 운영에서 닫지 않았다.

## 정확한 암호화 방식과 신뢰 경계

PostgreSQL `pgcrypto`의 **OpenPGP AES-256 + MDC 무결성 검사**를 사용한다. AES-GCM으로 표기하지 않는다. 별도 파일의 무작위 256비트 키, 매 암호화의 세션키, 압축 OFF, MDC ON을 사용한다. 키가 충분히 무작위이므로 S2K simple 모드이며 사람의 비밀번호를 키로 넣지 않는다. 암호문 안에 논리 테이블·기본키·필드·키 식별자를 결합해 다른 행/필드로 바꿔 붙이면 거부한다. Timescale의 실제 청크 이름 대신 논리 테이블 이름을 사용하고 시각은 UTC로 정규화한다.

`*_sealed` JSON에는 형식 버전·키 ID·암호문만 들어간다. 활성화 후 입력 트리거가 기존 평문 필드를 NULL로 만들고, `gps_read_*` 뷰와 기존 위치 전개/통계 함수가 조회 시 복호화한다. API의 소유권/회사 권한 검사는 계속 필요하다. **암호화는 익명화나 삭제가 아니다.** 정보주체·SIM·인증 하드웨어의 구분은 바꾸지 않았다.

키는 DB 테이블·덤프·명령행 인수에 넣지 않고, 소유자만 읽는 일반 파일(0600)에서 읽는다. API는 PostgreSQL 확장 프로토콜의 바인드 매개변수로 각 연결의 메모리에 키를 넣는다. 유지보수 도구도 psycopg 3의 서버 바인딩을 사용한다. 키를 전달하기 전에 `log_parameter_max_length=0`, `log_parameter_max_length_on_error=0`, `pgaudit.log_parameter=off`를 확인하며 다르면 실패한다. 실제 운영 로그/모니터링 확장까지 별도 검토해야 한다.

이 방식은 저장 데이터·덤프만 유출된 상황을 보호한다. API와 DB 프로세스는 복호화 키와 평문을 처리하므로 **침해된 API·DB 관리자·root로부터의 비밀 유지까지 보장하지 않는다.** 운영 DB는 같은 서버의 로컬 연결을 전제로 한다. 외부 DB를 쓴다면 검증된 TLS 또는 보호된 IPC를 먼저 구성해야 하며, 이번 변경이 모든 DB 연결에 TLS를 강제하는 것은 아니다. HSM/KMS·메모리 키 자동 영점화도 구현하지 않았다.

참고: [PostgreSQL pgcrypto](https://www.postgresql.org/docs/14/pgcrypto.html), [Nginx TLS 모듈](https://nginx.org/en/docs/http/ngx_http_ssl_module.html). 제출 문구는 운영 적용 범위와 구분한다.

## 스키마 103의 암호화 대상

| 테이블 | 암호화하는 필드 | 행 결합 기준 |
|---|---|---|
| `location_records` | `lat`, `lng`, `raw`, `fixes_jsonb` | `device_id`, `recorded_at`, `source` |
| `devices` | `last_lat`, `last_lng`, `last_stationary` | `id` |
| `events` | `data` | `id` |

식별자·시각·소유 계정 등 검색/권한 메타데이터는 평문이다. 기본키를 변경하는 새 기능은 기존 암호문을 그대로 옮기면 안 된다. SIM을 다른 하드웨어로 옮길 때는 논리 장치/이력 ID를 유지하므로 이 변경에 해당하지 않는다.

- 기존 마이그레이션은 수정하지 않았다. 0103은 기존 행을 자동 변환하지 않고 OFF로 생성한다.
- 활성화 후 키 없이 쓰기/복호화하거나 손상된 값을 읽으면 실패한다. 평문으로 되돌아가거나 조용히 NULL을 반환하지 않는다. 명시적으로 위치를 지우는 NULL 갱신은 암호문도 지운다.
- 일부 시간 구간을 지울 때 배치의 나머지 좌표는 보존하고, 삭제된 좌표를 포함할 수 있는 원본 JSON/대표 좌표 복사본은 함께 제거하도록 수정했다.
- DB runtime은 암호화 정책·필드 목록을 읽기만 한다. 마이그레이션/관리 계정은 API에 주지 않는다.

## 검증 결과와 증빙

모두 빌드 호스트의 **내부 Docker 네트워크 + tmpfs TimescaleDB + 합성 계정/좌표**에서 실행했다. 공개 포트·실제 회원 자료·외부 알림 발송을 사용하지 않았다. 원본 결과는 [증빙 폴더](../evidence/crypto20-20261107/)에 있다. 캡처는 실제 결과를 표시한 **검증 보고서**이며 운영 관리자 화면이 아니다.

전체 DB를 `pg_dump -Fc`로 저장하고 새 Timescale DB에서 `timescaledb_pre_restore()` → `pg_restore` → `timescaledb_post_restore()`로 복원했다. **키가 없으면 실패, 별도 보관 키를 넣으면 원본 값과 정확히 일치**했다. 전체 논리 덤프에 시험 좌표 문자열과 키가 없음을 검사했다. 이 표본에 없는 파생 데이터까지 암호화됐다는 증거는 아니다. [Timescale 복원 절차](https://www.tigerdata.com/docs/deploy/self-hosted/backup-and-restore/logical-backup)를 따르며 병렬 복원은 사용하지 않았다.

키 v1→v2를 1행 단위로 전환하고 v2만으로 전체 대상 행을 복호화했다. **현재 DB에서 구키를 더 이상 쓰지 않아도 구키로 만든 보관 백업이 있으면 구키를 폐기하면 안 된다.** 백업/키의 만료와 삭제 승인은 별도로 관리한다.

후보 API SHA-256: `e3ff355248e129d85ae9aa8e7f87edb7cdba5038ca256cf8c4be10e61432fe4b`. 컴파일 이후의 변경은 시험 fixture/유지보수 호환 도구이며 production Rust 소스는 같다. 웹 컴포넌트는 변경하지 않아 웹 시험·APK 빌드를 새로 수행하지 않았다.

## 운영에 적용하기 전 순서

1. **20B 저장 목록을 끝낸다.** `measurement.json`의 열 이름/JSON 후보 목록을 내용·작성자·독자별로 분류한다. 지점/지오펜스 geometry·주소, 운행 정정·스냅샷, AI 결과, 주소 변환 캐시, 레거시 집계, 자료 제공/업로드 파일·영수증 등을 누락 없이 전환하거나 별도 보호한다. 필드명만으로 위치정보 여부를 확정하지 않는다.
2. 현재 99에서 누적 100~103으로 올리는 리허설을 운영 규모 복제본에서 실시한다. **19차 102용 배포 스크립트를 103 운영에 그대로 실행하지 않는다.** 103 호환을 확인한 것은 `admin_db_roles.py`, `admin_security_bootstrap.py`이며 배포 전체 리허설과 다르다.
3. API·정리 작업·별도 워커 등 모든 쓰기 주체를 식별해 중지하고 유지보수 구간을 확보한다. 도구 자체가 모든 쓰기 프로세스 중지를 강제하지 않으므로 운영 체크리스트/잠금 절차가 필요하다. 큰 DB의 WAL/디스크/변환 시간과 복구 시간도 측정한다.
4. DB 권한 분리, 키 로그 비활성 설정, root/API 전용 파일 권한, 별도 키 백업/복원 책임자를 정한다. 키와 DB 백업을 같은 사본에 넣지 않는다. 키를 환경 파일·셸 이력·증빙에 복사하지 않는다.
5. schema103의 `location_storage.py`에서 먼저 읽기 점검, 활성화·작은 배치 변환, 전체 복호화 검사와 평문 잔존 점검을 실행한다. 모든 API 연결에 새 키 설정을 적용한 뒤 쓰기를 재개한다. 키 교체도 같은 원칙으로 한다.
6. 실물 `https-operating`을 식별된 단말기부터 검증한다. 정상/거부 인증서·실외 버퍼·절전 복귀·중지/재개를 확인한다. 전체 사용 단말기 승격 후 GPS Nginx의 모든 수집 별칭과 API에서 HTTP/무서명 예외를 닫는다. 이번 TLS ON 스위치는 전역이며, 구형 단말기와 혼재한 운영에 먼저 켜지 않는다.
7. 운영 키로 복원 시험 후 구 평문 백업·WAL·스냅샷·디스크 잔존 데이터의 처리 범위/기간/담당자를 확정한다. **행을 UPDATE해 평문 열을 NULL로 한 것만으로 과거 디스크 블록까지 안전 삭제된 것이 아니다.** 관련 회사 정책을 임의로 대신하지 않는다.

## 도구와 재실행

- `ops/location_storage.py`: 기본 읽기 점검. `--create-keyring <private-file>`은 기존 파일 덮어쓰기 없이 생성. DSN 파일은 `{"dsn":"..."}`, keyring은 별도 0600 파일. `--activate --convert --batch 500`은 명시적 유지보수 작업이며 운영에서 아직 실행하지 않았다. 활성화는 일방향이다.
- 키 형식: `{"active":"v1","keys":{"v1":"<무작위 32바이트의 base64>"}}`. 예시 문자열을 실제 키로 쓰지 않는다.
- API: `GPS_LOCATION_ENCRYPTION=pilot`, `GPS_LOCATION_KEYRING_FILE=<private-file>`. DB 정책과 API 설정이 다르면 기동 거부. OFF 설정/키 제거로 평문 운영에 복귀할 수 없다.
- `ops/nginx/gps-ingest-tls.conf.example`은 GPS 기존 vhost에 검토 후 합칠 위치 예시다. 전체 서버 파일로 복사하지 않는다. 443의 `/ingest`와 `/gps-tracker/ingest`에서 헤더를 덮어쓰고, 80의 두 별칭은 426으로 거부한다. HTTP POST 리디렉션은 전송된 평문을 보호하지 못한다.
- 빌드 호스트 작업 폴더: `/home/etcom-hub/build/gps-crypto20-20261107`. 최종 API는 `out/gps-tracker-api`, 펌웨어는 `fwsrc/idf_caltest/build/https-operating/`이다. 바이너리는 Git에 넣지 않는다.
- 격리 재실행: 새 `gps-crypto20-*` 작업 폴더에 고정 소스를 `src/gps-tracker-api`, 도구를 루트에 복사하고 `dev_crypto20.sh`를 `dev20.sh`로 둔다. psycopg3+binary 3.2.10을 `python-deps`에 준비한다. `api-check` → `api-release` → `up` → `suite test_crypto20.py` → `suite test_crypto20_bootstrap.py` → `suite measure_crypto20.py` → `suite capture_crypto20_state.py` → `external-all` → `down`. 시험은 빈 환경 1회용이며 DB/키 파일을 재사용해 반복하지 않는다.
- ESP-IDF5.5.4 환경에서 `python idf_caltest/tools/build_firmware.py https-operating`. 이 도구는 빌드만 하며 플래시하지 않는다. 기존 `operating`은 HTTP이므로 이름을 혼동하지 않는다. Git 없는 고정 아카이브 빌드는 `--source-manifest`의 파일 해시를 확인한다.
