# 114차 — 조회 제한 재시도와 조회 취소

2026-11-11. **구현·격리 검증 완료, 운영 미배포. 후보 스키마112 유지.** 새 마이그레이션은 없다. `security114` 백신·WAF 작업과 별개이며, 그 실무 검증 보류는 유지한다.

## 변경한 동작

112차의 동시 조회 제한은 수집 용량을 보호하지만, 웹은429 뒤 자동 복귀하지 않았고 화면을 떠난 뒤에도 DB 쿼리가 남을 수 있었다.

- 위치 이력·페이지·시간 집계 GET이 혼잡으로 거절되면 `429`, `code=location_read_busy`, `Retry-After: 2`, `Cache-Control: no-store`를 반환한다. CORS에서도 `Retry-After`를 읽을 수 있다.
- 웹은 해당 코드의 위치 GET만 **최대2회 재시도(최초 포함3회)**한다. 서버의 대기 시간과1/2초 backoff 중 긴 쪽에0~499ms의 분산 지연을 더한다. 서버가9.5초보다 긴 대기를 요구하면 자동 재시도를 멈추고 수동 재시도 안내를 제공한다. 로그인 제한·다른 API·쓰기·408·네트워크 오류를 이 경로에서 재전송하지 않는다. React Query가429/408을 다시 재시도해 횟수를 곱하지 않는다.
- 장치·기간 변경, 화면 닫기, 로그아웃·계정 변경 시 HTTP와 재시도 대기를 함께 취소한다. 늦게 끝난 이전 응답은 새 화면을 덮어쓰지 않는다. 홈 장치 로더, Fleet 경로, 운행 재생, 진단 집계에 취소 신호를 연결했다. 기존 이력 탐색의 신호 전달도 유지한다.
- 운행 재생의 조회 실패를 ‘기록 없음’으로 표시하지 않고 오류와 다시 시도 버튼으로 구분한다.429는 혼잡 안내,408은 기간을 줄여 조회하라는 안내다. 취소/429를 이전 계정의 저장 데이터로 대체하지 않는다.
- 진단 화면의5초 주기 갱신은 앞선 조회가 끝난 후에만 다음 조회를 시작한다.

## DB까지 이어지는 취소

보호 대상은 `/devices/:id/locations`, `/locations/page`, `/locations/aggregated`의 실제 위치 SQL이다. 필터·정렬·복호화·SIM/소유/동의·이용 중지 조건은 변경하지 않는다.

1. 기존 프로세스당2개/250ms 대기 제한을 획득한다.
2. 전용으로 빌린 일반 조회 연결에서 읽기 전용 트랜잭션과 **SQL20초 제한**을 설정한다. 연결에는 요청마다 다른 표식을 붙인다.
3. 정상 완료는 COMMIT 후 연결을 재사용한다. 핸들러가 취소되면 조회 연결과 동시 조회 자리를 정리 작업이 계속 보유한다.
4. 별도 최대2개 연결 풀에서 `pg_cancel_backend`를 호출한다. 같은 DB 계정과 PID·요청 표식이 모두 맞아야 한다. **슈퍼유저·pg_signal_backend 권한을 추가하지 않는다.** 취소용 풀 획득1초, 취소 SQL2초, 전체 취소 시도3초 한도다.
5. 중단된 연결은 풀로 돌려보내지 않고 닫는다. 취소용 연결이 실패하면 독립 SQL 제한이 끝날 때까지 동시 조회 자리를 유지한다. 취소를 반복해2개 제한을 우회하지 못한다.

취소용 풀은 기존 DB 연결 예산에 **최대2개**를 추가한다. 실제 운영 전환 시 전체 연결 예산에 포함해야 한다. 프록시가 클라이언트의 연결 종료를 상류로 전달하지 않아도 SQL20초 제한이 최종 보호선이다. 이 제한은 위치 SQL에 대한 것으로 모든 인증·원장·네트워크 처리까지20초 안에 끝난다는 보장은 아니다.
