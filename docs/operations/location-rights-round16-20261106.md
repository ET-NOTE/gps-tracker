## 이번에 완료한 범위

회사 지출에 저장된 **PDF 영수증**을 14·15차의 이미지 영수증과 같은 흐름으로 제공한다. 담당자는 브라우저에서 쪽과 공개 영역만 고르고, 화면에 보이는 쪽과 최종 제공 이미지는 모두 서버가 저장된 원본에서 만든다.

1. 담당자가 **회사에 저장된 영수증**에서 PDF를 열면 서버가 1쪽을 그려 보여 준다. `이전 쪽 / 쪽 선택 / 다음 쪽`으로 다른 쪽을 연다. 쪽마다 따로 읽고 따로 선택한다.
2. 그 쪽에서 공개할 영역을 지정하고 미리보기 → 두 확인 → 발급한다. 서버는 원본에서 같은 쪽을 다시 그려 선택 영역만 남긴다. 브라우저가 보낸 픽셀은 무시한다.
3. 요청자는 검토된 영역만 담긴 PNG를 24시간 동안 비밀번호 확인 후 내려받는다. 원본 PDF, 쪽 번호, 처리 내용은 요청자 응답에 없다.

회사에 저장되지 않은 PDF는 종전처럼 필요한 쪽을 이미지로 준비해 수동 경로로 제공한다.

## 구조: API와 분리된 PDF 처리기

PDF 해석은 API가 하지 않는다. 별도 프로그램 `gps-pdf-render`가 한다.

- **별도 빌드**: `gps-pdf-render/`는 독립 크레이트로, 자체 툴체인(Rust 1.92.0)과 자체 빌드 이미지(`ops/pdf-builder.Dockerfile`)에서 정적 바이너리로 만든다. API는 기존 Rust 1.88.0과 의존성을 그대로 유지한다.
- **쪽당 프로세스 1개**: API가 요청마다 처리기를 새로 실행한다. 환경 변수는 비우고, 작업 디렉터리는 `/`, 연결은 입력·출력 파이프 2개뿐이다. 형식은 고정 길이 필드라 API는 길이만 검증한다.
- **입력을 읽기 전에 스스로 권한을 버린다**(되돌릴 수 없음):
  - 새 권한 획득 금지(`no_new_privs`).
  - 자원 한도: 주소 공간 768MB, CPU 10초, 파일 쓰기 0바이트, 열린 파일 3개, 새 프로세스 0개, 코어 덤프 없음.
  - 시스템 호출 허용 목록 21개: 메모리 관리, 이미 열린 파이프 읽기·쓰기, 시간, 종료. **파일 열기, 소켓 생성, 프로그램 실행, 프로세스 생성, 다른 프로세스에 신호 보내기는 목록에 없고**, 목록 밖 호출은 프로세스를 즉시 끝낸다. 네트워크는 소켓 호출 자체가 없어 차단된다.
- **API 쪽 통제**: 15초가 지나면 강제 종료, 응답이 선언한 크기와 다르면 실패 처리, 동시 처리 1건(초과 시 429).
- **자체 점검**: `gps-pdf-render selftest`는 실행 중인 커널에서 금지 동작 6가지가 실제로 프로세스를 끝내는지와 그 제한 안에서 쪽이 정상 렌더링되는지 확인한다. API는 PDF를 처음 처리하기 전에 이 점검을 실행하고, 통과하지 못하면 PDF 원본 연결을 쓰지 않는다.

**분리의 범위와 한계**: 처리기는 API와 같은 운영체제 계정으로 실행된다. 파일·네트워크·실행 호출이 막혀 있어 그 계정의 권한을 쓸 수단이 없지만, 계정 자체를 나누는 것(전용 사용자, systemd 샌드박스)은 하지 않았다. 이는 공유 VPS의 서비스 분리와 함께 인프라 라운드에서 다룬다. 처리기는 표준 입출력만 쓰므로 같은 바이너리를 소켓 활성화 서비스로 옮길 수 있다.

## 원본·쪽·변환 결과·선택 영역의 연결

마이그레이션 `0098`은 PDF를 영수증 원본 범위에 넣고 쪽 번호 열을 추가한다.

- **읽기 증빙**(`privacy_receipt_reads`): 원본 SHA-256, 영수증·지출 revision, `page`, 그 쪽 픽셀의 해시, 변환 내용(쪽수, 쪽 크기, 출력 크기, 처리기 바이너리 SHA-256).
- **선택**: 쪽 번호가 선택 해시에 들어간다. 미리보기·발급은 같은 담당자가 1시간 이내에 **같은 쪽의 같은 픽셀**을 읽은 증빙이 있어야 한다. 1쪽을 읽은 증빙으로 2쪽을 선택할 수 없다.
- **발급본**(`privacy_image_deliveries`): `source_page`와 변환 내용.
- **원본 변경**: PDF 바이트 교체, 지출 수정, 영수증 제거, 직원 변경, 회사 검토 변경 시 기존 제공본 다운로드를 409로 막고 임시 PNG를 지운다. 교체된 원본은 새로 읽고 새로 선택해야 한다.
- 이미지 원본은 쪽을 갖지 않는다. 이미지에 쪽을 붙이거나 PDF에서 쪽을 빼면 거부한다.
- 처리기 바이너리가 바뀌면 SHA-256이 달라지고 증빙에 남는다.

## 렌더러 선정

순수 Rust 렌더러 **hayro 0.9.0**을 골랐다. 합성 표본 23개를 격리 컨테이너에서 처리하고, 품질은 poppler(`pdftoppm`)를 기준으로 같은 크기에서 비교했다. poppler는 비교에만 썼고 제공본 생성에는 쓰지 않는다.

| 표본 | 결과 |
|---|---|
| 한글·표(글꼴 내장, pdfmake) 영수증·3쪽 명세서 | 정상. 기준 렌더러와 육안으로 동일. 6pt 글씨까지 판독 가능 |
| 한글(글꼴 미내장, Adobe-Korea1) | 나눔고딕으로 대체해 정확히 표시. 기준 렌더러는 이 환경에서 글자를 그리지 못함 |
| 스캔 문서(JPEG, 회색조 Flate, CCITT G4 흑백) | 정상. 흑백 스캔은 기준 렌더러보다 부드럽게 축소됨 |
| 표준 14 글꼴, 회전·자르기(CropBox) 쪽 | 정상 |
| 암호화 3종(사용자 암호 AES-256, 소유자 암호만, RC4) | 모두 암호화로 구분해 거부 |
| 손상(머리말만, 쓰레기 값, 쪽 없음) | 읽을 수 없음으로 거부 |
| 201쪽, 20,000pt 쪽 | 한도 초과로 거부 |
| 9억 화소로 풀리는 이미지 | 메모리 한도에서 0.09초 만에 종료 |
| 20만 개 그리기 명령, 자기 자신을 부르는 양식 | 0.06초 이내 처리 |

- 자원: 정상 문서는 쪽당 **약 0.01초, 최대 메모리 약 15MB**(가장 큰 값 0.06초·26MB). 기준 렌더러는 0.02~0.2초·13~17MB였다.
- 선택 이유: 품질이 기준과 같거나 낫고, 자원 사용이 작고, `unsafe` 코드를 금지한 순수 Rust라 시스템 호출 허용 목록으로 가둘 수 있으며, 서버에 시스템 패키지를 설치하지 않아도 된다.
- 평가 스크립트는 `gps-pdf-render/eval/`, 결과는 [renderer-evaluation.json](evidence/location-rights-round16-20261106/renderer-evaluation.json)에 있다.

**확인하지 못한 것**: 표본은 모두 합성이다. 실제 카드사·홈택스 등의 한글 영수증 PDF로는 확인하지 않았다. JBIG2·JPEG 2000 스캔, 블렌드 모드·녹아웃 그룹을 쓰는 문서는 시험하지 않았고 hayro 문서도 일부 미지원이라고 밝힌다. 글꼴이 내장되지 않은 일본어·중국어는 한글 글꼴로 대체되어 일부 글자가 빠질 수 있다. 잘린 PDF는 복구되어 일부만 그려질 수 있으므로 담당자가 화면에서 확인해야 한다.

### 15차 절차와 다른 점

- **프로그램이 둘이다.** API 바이너리 옆(`/home/mmm/projects/gps-tracker-api/bin/gps-pdf-render`)에 처리기를 둔다. API는 같은 디렉터리에서 처리기를 찾으므로 서비스 설정과 환경파일은 바꾸지 않는다. 처리기는 정적 바이너리라 서버의 라이브러리에 의존하지 않는다.
- **`check`가 운영 커널에서 처리기를 먼저 증명한다.** 스테이징 디렉터리의 처리기를 API 서비스 계정으로, API가 실행할 때와 같이 빈 환경·`/`에서 자체 점검시킨다. 파일 열기·소켓·프로그램 실행·프로세스 생성·메모리 초과·CPU 초과가 모두 막히고 그 안에서 한 쪽이 그려져야 통과다.
- **서비스가 처리기에 더하는 제한을 확인한다.** 처리기는 API의 자식 프로세스라 서비스의 제한을 물려받는다. 서비스에 자체 시스템 호출 필터가 있으면 위 점검으로는 증명되지 않으므로 멈춘다. 서비스 메모리 한도가 처리기 한 쪽 분량(768MiB)보다 적게 남았거나 서버의 가용 메모리·스왑이 그 두 배보다 적어도 멈춘다. 커널이 서비스 안의 프로세스를 메모리 부족으로 끝내면 systemd가 API까지 내리기 때문이다(`OOMPolicy=stop`).
- **0098은 열 2개와 함수 1개다.** `privacy_receipt_in_scope`가 PDF를 범위에 넣도록 바뀐다. 적용 전에 PostgreSQL이 출력한 함수 정의를 백업 디렉터리에 저장하고, 되돌릴 때 그 정의를 그대로 다시 실행한 뒤 같은지 대조한다.
- **적용 후에도 처리기를 다시 증명한다.** 재시작 뒤 설치된 처리기의 자체 점검과 서비스 조건을 다시 확인하고, 통과하지 못하면 새 API가 정상이어도 스스로 되돌린다.

### 운영 서버 사전 확인 (2026-11-06, 읽기 전용)

절차를 운영 조건에 맞추기 위해 서비스 속성만 읽었다. DB와 파일은 건드리지 않았다.

- API 서비스는 `mmm` 계정으로 실행되고 자체 시스템 호출 필터·메모리 한도·보호 옵션이 없다(`Seccomp: 0`, `MemoryMax=infinity`). 처리기 자신의 제한이 유일한 격리이며, 서비스 계정으로 한 자체 점검이 실제 실행 조건과 같다.
- 커널 5.15.0-151은 `kill_process` 동작을 지원한다. 가용 메모리 약 1.5GiB, 스왑 여유 약 3.8GiB, API 사용량 약 130MiB였다.
- 서비스 설정이 `OOMPolicy=stop`이므로 위의 메모리 조건을 `check`에 넣었다.

### 순서

1. **소스 묶음** — 배포할 커밋을 PC에서 묶는다. 줄바꿈 변환을 끄지 않으면 마이그레이션 체크섬이 달라질 수 있다. 15차와 달리 `gps-pdf-render`를 포함한다.

   ```bash
   git -c core.autocrlf=false archive --format=tar.gz -o source.tar.gz <커밋 전체 ID> gps-tracker-api gps-pdf-render gps-tracker-web ops
   ```

2. **스테이징** — `source.tar.gz`를 빌드 호스트의 새 작업 디렉터리에 두고 실행한다. 스크립트는 자신이 묶음 안의 것과 같은지, 묶음이 해당 커밋의 `git archive`인지 먼저 확인한다.

   ```bash
   tar -xzOf source.tar.gz ops/stage_privacy_pdf.py > stage_privacy_pdf.py
   /home/etcom-hub/build/gps-location-erasure-20261105/venv/bin/python stage_privacy_pdf.py "$PWD" <커밋 전체 ID>
   ```

   끝나면 `out/`이 운영 서버에 둘 디렉터리 전체다: API 바이너리, PDF 처리기, 웹 묶음, 소스 묶음, `manifest.json`, `validation.json`, `rehearsal.json`, 운영 스크립트 2개, 일회용 모의 계정 자격증명(`smoke-private.json`, 권한 600, 출력·커밋하지 않음).

3. **전송** — `out/`을 운영 서버 `/home/mmm/gps-artifacts/privacy-pdf-20261106-r1`에 둔다. 처리기의 실행 권한(755)과 자격증명의 권한(600)이 유지되어야 하므로 권한을 보존하는 방식으로 옮긴다. 실행 권한이 빠지면 `check`가 그 사유로 멈춘다. 아래 방식은 자격증명이 PC에 저장되지 않는다.

   ```bash
   ssh etcom-hub-lan 'tar -C /home/etcom-hub/build/gps-privacy-pdf-20261106-r1/out -cf - .' | ssh seriallog 'mkdir /home/mmm/gps-artifacts/privacy-pdf-20261106-r1 && tar -C /home/mmm/gps-artifacts/privacy-pdf-20261106-r1 -xpf -'
   ```

   옮긴 뒤 양쪽의 SHA-256을 대조한다.

4. **점검** — 아무것도 바꾸지 않는다. 운영이 15차 그대로인지(health의 릴리스, 실행 바이너리 해시, 웹 링크, 마이그레이션 1~97 체크섬, 새 열 없음, 범위 함수에 PDF 없음, 처리기 미설치, 이전 시도의 잔여물 없음), 산출물 해시, 처리기 자체 점검, 서비스 조건을 확인한다.

   ```bash
   python3 release_privacy_pdf.py check
   ```

5. **적용** — 점검을 다시 한 뒤 진행한다.

   ```bash
   python3 release_privacy_pdf.py apply
   ```

   이전 바이너리와 범위 함수 정의 백업 → 웹 풀기 → 한 트랜잭션에서 0098 적용과 SQLx 기록(잠금 5초·문장 60초 제한) → 처리기 설치 → API 바이너리 교체·재시작 → health가 새 릴리스가 될 때까지 대기 → 설치된 처리기 자체 점검 → 웹 링크 교체 → 제공되는 페이지·자산 바이트, dev-gps·Shield·환경파일·정리 타이머·수집 정책이 그대로인지 확인 → `deployment.json` 기록.

6. **모의 확인(별도 승인)** — `python3 smoke_privacy_pdf.py`. 운영 API가 처음으로 PDF 쪽을 그리는 단계이며, 읽기 응답의 처리기 해시가 설치한 처리기와 같은지 확인한다. API는 첫 PDF 요청 때 서비스 안에서 처리기 자체 점검을 하므로, 이 단계가 통과해야 서비스 안에서의 동작까지 확인된 것이다. 운영 DB에 모의 계정·지출·PDF 영수증을 만들었다가 영수증·지출은 지우고 계정은 이용 종료한다. 실제 계정·SIM·위치는 건드리지 않으며 실행 전후 해시로 확인한다. **이 단계 이후에는 새 열을 쓰는 읽기 증빙이 남으므로 스크립트 되돌림을 쓸 수 없다.**

7. **기록** — `deployment.json`·`production-smoke.json`을 증빙에 넣고 `HANDOFF.md`의 운영 기준을 갱신한다.

### 실패와 되돌림

- 점검이 맞지 않으면 첫 변경 전에 멈춘다. 마이그레이션 트랜잭션이 실패하면 롤백되고 준비 파일만 옆으로 치운다.
- **새 API가 45초 안에 정상이 되지 않거나 설치된 처리기가 증명되지 않으면 `apply`가 스스로 되돌린다**: API 정지 → 0098 제거(열 2개 삭제, 범위 함수 복원, SQLx 기록 삭제) → 이전 바이너리 복원 → 처리기 삭제 → 기동 → 이전 릴리스 health 확인. 이 동안 API는 내려가 있다.
- 적용 후 문제가 있으면 `python3 release_privacy_pdf.py rollback`으로 같은 되돌림을 한다(웹 링크도 이전으로).
- 되돌림은 **새 열을 쓰는 행이 없을 때만** 허용한다. PDF 쪽을 한 번이라도 읽었으면 감사 기록을 지우게 되므로 거부하고, 그때는 앞으로 고친다.
- 적용 중 0098이 들어간 뒤 API를 재시작하기까지 1~2초 동안은 15차 API가 PDF 영수증을 범위에 표시할 수 있다. 열려고 하면 지원하지 않는 형식으로 거부되며 읽기 증빙은 남지 않는다.
- 처리기만 동작하지 않는 경우(예: 이후 서버 설정 변경)에는 PDF 원본만 "사용할 수 없음"이 되고 이미지 영수증과 다른 기능은 그대로다. API는 처리기 실패를 기억하지 않으므로 처리기를 고치면 재시작 없이 다시 쓴다.
