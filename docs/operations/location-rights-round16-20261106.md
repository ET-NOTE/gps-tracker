# 개인정보 권리 대응 16차 — 서버 원본 기반 PDF 쪽 제공과 격리 처리기

2026-11-06 · GPS · `codex/location-business-prep`

> **상태: 개발·격리 검증 완료, 운영 미배포.** 운영은 14차(`privacy-receipts-20261106-r1`, 스키마 96)다. 15차(스키마 97) 배포가 먼저이고, 16차(스키마 98)의 배포 절차는 아직 작성하지 않았다.

## 이번에 완료한 범위

회사 지출에 저장된 **PDF 영수증**을 14·15차의 이미지 영수증과 같은 흐름으로 제공한다. 담당자는 브라우저에서 쪽과 공개 영역만 고르고, 화면에 보이는 쪽과 최종 제공 이미지는 모두 서버가 저장된 원본에서 만든다.

1. 담당자가 **회사에 저장된 영수증**에서 PDF를 열면 서버가 1쪽을 그려 보여 준다. `이전 쪽 / 쪽 선택 / 다음 쪽`으로 다른 쪽을 연다. 쪽마다 따로 읽고 따로 선택한다.
2. 그 쪽에서 공개할 영역을 지정하고 미리보기 → 두 확인 → 발급한다. 서버는 원본에서 같은 쪽을 다시 그려 선택 영역만 남긴다. 브라우저가 보낸 픽셀은 무시한다.
3. 요청자는 검토된 영역만 담긴 PNG를 24시간 동안 비밀번호 확인 후 내려받는다. 원본 PDF, 쪽 번호, 처리 내용은 요청자 응답에 없다.

회사에 저장되지 않은 PDF는 종전처럼 필요한 쪽을 이미지로 준비해 수동 경로로 제공한다.

## 구조: API와 분리된 PDF 처리기

PDF 해석은 API가 하지 않는다. 별도 프로그램 `gps-pdf-render`가 한다.

- **별도 빌드**: `gps-pdf-render/`는 독립 크레이트로, 자체 툴체인(Rust 1.92.0)과 자체 빌드 이미지(`ops/pdf-builder.Dockerfile`)에서 정적 바이너리로 만든다. API는 기존 Rust 1.88.0과 의존성을 그대로 유지한다.
- **쪽당 프로세스 1개**: API가 요청마다 처리기를 새로 실행한다. 환경 변수는 비우고, 작업 디렉터리는 `/`, 연결은 입력·출력 파이프 2개뿐이다. 형식은 고정 길이 필드라 API는 길이만 검증한다.
- **입력을 읽기 전에 스스로 권한을 버린다**(되돌릴 수 없음):
  - 새 권한 획득 금지(`no_new_privs`).
  - 자원 한도: 주소 공간 768MB, CPU 10초, 파일 쓰기 0바이트, 열린 파일 3개, 새 프로세스 0개, 코어 덤프 없음.
  - 시스템 호출 허용 목록 21개: 메모리 관리, 이미 열린 파이프 읽기·쓰기, 시간, 종료. **파일 열기, 소켓 생성, 프로그램 실행, 프로세스 생성, 다른 프로세스에 신호 보내기는 목록에 없고**, 목록 밖 호출은 프로세스를 즉시 끝낸다. 네트워크는 소켓 호출 자체가 없어 차단된다.
- **API 쪽 통제**: 15초가 지나면 강제 종료, 응답이 선언한 크기와 다르면 실패 처리, 동시 처리 1건(초과 시 429).
- **자체 점검**: `gps-pdf-render selftest`는 실행 중인 커널에서 금지 동작 6가지가 실제로 프로세스를 끝내는지와 그 제한 안에서 쪽이 정상 렌더링되는지 확인한다. API는 PDF를 처음 처리하기 전에 이 점검을 실행하고, 통과하지 못하면 PDF 원본 연결을 쓰지 않는다.

**분리의 범위와 한계**: 처리기는 API와 같은 운영체제 계정으로 실행된다. 파일·네트워크·실행 호출이 막혀 있어 그 계정의 권한을 쓸 수단이 없지만, 계정 자체를 나누는 것(전용 사용자, systemd 샌드박스)은 하지 않았다. 이는 공유 VPS의 서비스 분리와 함께 인프라 라운드에서 다룬다. 처리기는 표준 입출력만 쓰므로 같은 바이너리를 소켓 활성화 서비스로 옮길 수 있다.

## 한도

| 항목 | 한도 | 넘으면 |
|---|---|---|
| PDF 파일 | 5MiB (기존 저장 한도) | 저장 단계에서 거부 |
| 쪽수 | 200쪽 | 400 |
| 쪽 크기 | 한 변 14,400pt (200인치) | 400 |
| 출력 | 100만 화소·한 변 2048px (A4는 약 840×1189, 102DPI) | 이 크기로 그림 |
| 처리기 메모리 | 주소 공간 768MB | 프로세스 종료 → 400 |
| 처리 시간 | CPU 10초, 대기 15초 | 프로세스 종료 → 400 |
| 동시 처리 | 1건 | 429 |
| 암호화 PDF | 열지 않음(소유자 암호만 걸린 문서 포함) | 400 |

거부되거나 실패한 문서는 읽기 증빙을 남기지 않는다.

## 원본·쪽·변환 결과·선택 영역의 연결

마이그레이션 `0098`은 PDF를 영수증 원본 범위에 넣고 쪽 번호 열을 추가한다.

- **읽기 증빙**(`privacy_receipt_reads`): 원본 SHA-256, 영수증·지출 revision, `page`, 그 쪽 픽셀의 해시, 변환 내용(쪽수, 쪽 크기, 출력 크기, 처리기 바이너리 SHA-256).
- **선택**: 쪽 번호가 선택 해시에 들어간다. 미리보기·발급은 같은 담당자가 1시간 이내에 **같은 쪽의 같은 픽셀**을 읽은 증빙이 있어야 한다. 1쪽을 읽은 증빙으로 2쪽을 선택할 수 없다.
- **발급본**(`privacy_image_deliveries`): `source_page`와 변환 내용.
- **원본 변경**: PDF 바이트 교체, 지출 수정, 영수증 제거, 직원 변경, 회사 검토 변경 시 기존 제공본 다운로드를 409로 막고 임시 PNG를 지운다. 교체된 원본은 새로 읽고 새로 선택해야 한다.
- 이미지 원본은 쪽을 갖지 않는다. 이미지에 쪽을 붙이거나 PDF에서 쪽을 빼면 거부한다.
- 처리기 바이너리가 바뀌면 SHA-256이 달라지고 증빙에 남는다.

## 렌더러 선정

순수 Rust 렌더러 **hayro 0.9.0**을 골랐다. 합성 표본 23개를 격리 컨테이너에서 처리하고, 품질은 poppler(`pdftoppm`)를 기준으로 같은 크기에서 비교했다. poppler는 비교에만 썼고 제공본 생성에는 쓰지 않는다.

| 표본 | 결과 |
|---|---|
| 한글·표(글꼴 내장, pdfmake) 영수증·3쪽 명세서 | 정상. 기준 렌더러와 육안으로 동일. 6pt 글씨까지 판독 가능 |
| 한글(글꼴 미내장, Adobe-Korea1) | 나눔고딕으로 대체해 정확히 표시. 기준 렌더러는 이 환경에서 글자를 그리지 못함 |
| 스캔 문서(JPEG, 회색조 Flate, CCITT G4 흑백) | 정상. 흑백 스캔은 기준 렌더러보다 부드럽게 축소됨 |
| 표준 14 글꼴, 회전·자르기(CropBox) 쪽 | 정상 |
| 암호화 3종(사용자 암호 AES-256, 소유자 암호만, RC4) | 모두 암호화로 구분해 거부 |
| 손상(머리말만, 쓰레기 값, 쪽 없음) | 읽을 수 없음으로 거부 |
| 201쪽, 20,000pt 쪽 | 한도 초과로 거부 |
| 9억 화소로 풀리는 이미지 | 메모리 한도에서 0.09초 만에 종료 |
| 20만 개 그리기 명령, 자기 자신을 부르는 양식 | 0.06초 이내 처리 |

- 자원: 정상 문서는 쪽당 **약 0.01초, 최대 메모리 약 15MB**(가장 큰 값 0.06초·26MB). 기준 렌더러는 0.02~0.2초·13~17MB였다.
- 선택 이유: 품질이 기준과 같거나 낫고, 자원 사용이 작고, `unsafe` 코드를 금지한 순수 Rust라 시스템 호출 허용 목록으로 가둘 수 있으며, 서버에 시스템 패키지를 설치하지 않아도 된다.
- 평가 스크립트는 `gps-pdf-render/eval/`, 결과는 [renderer-evaluation.json](evidence/location-rights-round16-20261106/renderer-evaluation.json)에 있다.

**확인하지 못한 것**: 표본은 모두 합성이다. 실제 카드사·홈택스 등의 한글 영수증 PDF로는 확인하지 않았다. JBIG2·JPEG 2000 스캔, 블렌드 모드·녹아웃 그룹을 쓰는 문서는 시험하지 않았고 hayro 문서도 일부 미지원이라고 밝힌다. 글꼴이 내장되지 않은 일본어·중국어는 한글 글꼴로 대체되어 일부 글자가 빠질 수 있다. 잘린 PDF는 복구되어 일부만 그려질 수 있으므로 담당자가 화면에서 확인해야 한다.

## 검증

- PDF 처리기: fmt·Clippy(`-D warnings`) 통과, 단위 시험 5개 통과, 자체 점검 통과(파일 열기·소켓·프로그램 실행·프로세스 생성은 SIGSYS로 종료, 메모리 초과는 거부, CPU 초과는 SIGKILL).
- API(Rust 1.88.0): fmt·Clippy 통과, 단위 시험 60개 통과·기존 2개 제외(신규 2개).
- 웹: 시험 224개 통과(신규 1개), 운영용 빌드 통과.
- 격리 통합 시험: 신규 `ops/test_privacy_receipt_pdf.py` 7개 묶음 + 15차 축소 9개 + 기존 회귀 80개 = **96개 묶음 통과**, 스키마 98.
  - PDF가 확인된 범위에 표시되고 관리자만 열 수 있음. 1·2쪽의 픽셀 일치, 읽기 증빙의 쪽·픽셀·처리기 기록, 없는 쪽 거부, 원본 불변.
  - 쪽에 묶인 선택: 위조 픽셀 무시, 선택 밖 검은색, 다른 쪽의 증빙으로는 409, 미리보기와 다운로드 바이트 일치, **다른 계정 404·틀린 비밀번호 401**, 요청자 응답에 원본 정보 없음.
  - **암호화(2종)·손상·빈 문서·201쪽·과대 쪽·압축 폭탄 거부**, 읽기 증빙 없음. 5MiB 문서와 200쪽 문서는 정상. 이후 요청에 영향 없음.
  - **원본 교체·지출 수정 시 409와 임시 PNG 제거, 회수·만료 시 410과 임시 PNG 제거**, 제거된 원본은 읽기 불가.
  - API 컨테이너 안에서 처리기 자체 점검 통과, 요청이 끝난 뒤 남는 처리기 프로세스 없음.
  - 동시 요청은 200 또는 429만 반환.
- 14차 영수증 시험은 "PDF 제외" 단정을 "지원하지 않는 형식(WebP) 제외"로 바꿨다. PDF가 범위에 들어온 것은 의도한 변경이다.
- 화면 검수(실제 컴포넌트 + 모의 API, PC 1280px·모바일 390px): 읽기 응답은 격리 API의 실제 응답, 미리보기·발급은 브라우저에서 흉내 냈다. PDF 표시, 쪽 이동, 쪽별 크기·픽셀, 영역 지정 → 미리보기 → 두 확인 → 발급 → 이력의 쪽 표시를 확인했다. 가로 넘침·콘솔 오류 없음.
- 집계는 [validation.json](evidence/location-rights-round16-20261106/validation.json), 화면 검수는 [ui-verification.json](evidence/location-rights-round16-20261106/ui-verification.json)에 있다.
