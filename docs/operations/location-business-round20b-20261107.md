# 20B — 파생 데이터·파일 암호화와 전환 준비

2026-11-07 20:59 KST 구현·격리 검증·운영 전환 후보 준비 완료. 구현 커밋 `3e41d866295b9c51ce3d671b1f5dad39f50e4da1`. 브랜치 `codex/location-business-prep`, [PR #248](https://github.com/ET-NOTE/gps-tracker/pull/248). 이 문서는 20A의 핵심 8필드에 파생 저장소와 파일을 더한 후보를 설명한다. **운영 배포·활성화 기록이 아니다.** 운영은 18A / 스키마 99다. 이 라운드에서 실물 펌웨어와 Shield는 변경하지 않는다.

## 저장 범위와 경계

암호화 방식은 20A와 같은 PostgreSQL pgcrypto OpenPGP AES-256 + MDC다. 키는 별도 0600 파일, DB 연결에는 확장 프로토콜의 바인드 값으로만 전달한다. AES-GCM·익명화·HSM으로 표현하지 않는다.

| 저장소 | 추가 보호 범위 |
|---|---|
| 지점·지오펜스 | 이름, 좌표, 주소, geometry, 메모, 지점 버전 스냅샷, 방문 시점 지점·그룹명 |
| 운행 정정 | sources/outputs의 좌표·주소·구간 정보, 정정/취소 사유 |
| 파생·감사 | AI 분석 본문, 장치 감사 data, 회사 배정·차량·지출·사용자 감사 before/after JSON |
| 알림 | FCM outbox message 전체. 재시도·권한 경계는 유지 |
| 과거 집계 | location_1min/5min/1hour의 평균·마지막 위경도 |
| 주소 캐시 | 기존 좌표 격자키와 주소. ON에서는 지속 DB 캐시를 중단하고 최대 4,096개·1시간 프로세스 메모리 캐시 사용 |
| DB 파일 | 대여 사진, 지출 영수증, 회사 제출 증빙 파일, 검토 후 제공 PNG 바이트 |
| 파일 시스템 | GPS의 device_documents, fleet_documents, private/car-images 본문 |

20B는 20개 테이블 47필드를 추가하고, 20A를 포함해 23개 테이블 55필드를 보호한다. 정확한 필드와 행 결합 기준은 `ops/crypto20b-fields.json` 및 마이그레이션 0104에 있다. 식별자·SIM 귀속·시각·금액·상태·검색 메타데이터는 이 작업으로 모두 암호화되지 않는다. 파일명·저장 경로·MIME·크기·해시도 메타데이터다. 수동 입력 채팅·회사 주소·차량 프로필·결제 자료를 위치 원본의 파생 저장소와 동일한 범위로 간주하지 않는다. 그 안의 개인정보 전반에 대한 추가 정책은 별도 검토 대상이다.

위치정보의 논리 귀속은 계속 SIM, 인증은 하드웨어별 키다. 차량 배정·과거 운행 귀속·계정 권한을 바꾸지 않는다. 자유 입력란에 사용자가 별도 위치정보를 입력한 모든 경우까지 탐지·암호화한다는 의미가 아니다.

## 데이터·파일 처리

- `gps_read_*` 뷰가 기존 API에 논리 값을 제공한다. 쓰기는 원본 테이블의 암호화 트리거를 거친다. 이름·주소·JSON을 직접 읽던 함수/쿼리와 일부 삭제 조건도 논리 조회로 바꿨다.
- 필수값·좌표·업무 CHECK 검사는 암호화 후 복호화한 논리 행에 적용한다. 일반 DB 실행 계정은 검사 트리거를 끌 수 없다. 전체 덤프 복원에서는 데이터 적재 후 트리거가 설치되므로 복원 명령행에 키를 넣지 않아도 된다. 복원 후 별도 키로 전체 검사를 마치기 전에는 서비스하지 않는다.
- 지점의 변경 감지·버전 기록은 논리 값으로 비교한다. 단순 암호화/키 교체가 새 지점 버전이나 영수증 변경 이력을 만드는 것을 방지한다.
- 파일은 `GPSFILE1` 헤더 뒤 암호화 봉투를 저장한다. 루트 역할 + 상대 경로를 암호문에 결합한다. 다른 경로의 암호문 교체, 키 누락, 헤더 손상, ON 상태의 평문 파일은 거부한다.
- API 파일 읽기·쓰기는 디렉터리 FD를 따라 O_NOFOLLOW로 수행하며 쓰기는 O_EXCL·0600·fsync를 사용한다. 본문은 메모리에서만 복호화한다. 영수증 PDF 처리기는 기존처럼 파이프/서비스 소켓으로 원문을 받는다.
- 운영 Nginx는 공개 `/uploads/car-images/`, `/uploads/device_documents/`, `/uploads/fleet_documents/`를 404로 차단하는 상태를 읽기 전용으로 확인했다. 보호 파일을 정적 서버로 직접 제공하지 않는다.
- 파일 생성과 DB 참조 저장은 하나의 원자적 트랜잭션이 아니다. 참조 저장 실패의 미참조 파일도 변환 목록에 포함한다. 기존 정리 큐 및 별도 잔여 파일 점검을 유지한다.

## 쓰기 차단과 복구 원칙

`location_storage_policy.maintenance`가 켜지면 정상 API 기동과 정리 워커 기동을 거부한다. DB 쓰기 차단은 실제 접속자(session_user)를 확인하므로 SECURITY DEFINER를 통한 우회도 막는다. schema owner는 유지보수 권한을 가지므로 **모든 API·워커 연결 중지 확인**을 함께 요구한다. 운영의 기존 소유자 자격증명으로 API를 재가동하면 안 된다.

`ops/crypto20b_transition.py`의 fence/convert/resume는 다른 GPS DB 세션이 남아 있으면 실패한다. 변환은 배치 100행·잠금 5초·문장 60초 한도다. 참조·원본 보호 트리거 전체를 끄지 않으며, 버전/불변 파일의 재암호화를 위한 고정 허용 목록만 잠금 안에서 잠시 해제하고 같은 트랜잭션 안에서 복원한다. 실패한 트랜잭션은 해당 상태까지 되돌린다. 차단된 계정·SIM의 기존 보관 자료도 논리 값을 바꾸지 않고 재암호화하도록, maintenance + 실제 schema owner + 트랜잭션 한정 rewrite 표시를 모두 충족할 때만 기존 쓰기 검사를 우회한다. runtime은 같은 표시를 설정해도 우회할 수 없으며, 수집/계정 차단 상태는 그대로 보존한다. 압축 Timescale 테이블의 트리거를 비활성화하지 않는다. 전체 작업 실패 후에도 maintenance는 유지한다.

파일은 암호문 임시 파일을 fsync한 뒤 원자적으로 교체한다. 중단 시 기존 파일 또는 완성된 암호문이 남고, 미완성 staging 파일은 자동 무시하지 않고 재개를 차단한다. 반복 실행은 남은 평문·구키 행/파일만 처리한다. resume는 모든 등록 열의 평문 0건, 전체 복호화 성공, 파일 평문 0건을 요구한다.

활성화는 일방향이다. 구 API/schema로 단순 되돌리는 기능은 없다. 장애 시 읽기/쓰기를 막고 키·암호문을 보존한 채 호환 수정본으로 복구한다. 복원도 격리 환경에서 전체 DB+GPS 파일+별도 키를 함께 검사하고, 이후 접수된 삭제/철회 의무를 다시 적용한 뒤 서비스한다.

## 키·백업 수명 관리

키 파일과 DB/파일 백업은 다른 접근 통제 경로에 보관한다. 키 ID·생성/활성 시각·사용 중인 백업 목록·복원 시험·폐기 승인을 별도 대장으로 관리한다. 키는 저장소, 환경변수 값, 명령행, 증빙 캡처에 넣지 않는다. `GPS_LOCATION_KEYRING_FILE`에는 파일 경로만 둔다.

교체는 **신키·구키를 포함한 키 파일을 먼저 안전하게 저장·별도 보관한 다음** 신키를 active로 둔 상태로 변환 → 신키만으로 전 범위 복호화 검사 → 재가동 순서다. 현재 DB에서 구키가 없어져도 과거 백업이 구키를 쓰면 폐기하지 않는다. 실제 키 책임자·별도 보관소·보관/폐기 기간은 회사 결정 항목이며 이번 시험용 무작위 키와 구분한다.

평문 열을 NULL로 바꾸거나 파일을 교체한 것은 과거 MVCC 페이지·WAL·임시 파일·스왑·호스팅 스냅샷의 안전 삭제가 아니다. 기존 평문 백업은 접근 제한 및 보관 근거/만료를 검토하고, 무단 일괄 삭제하지 않는다. 외부 다운로드·브라우저 캐시·제3자 사본도 이 변환이 자동 회수하지 않는다.

## 운영 전환 준비

현재 운영 스키마는 **99**, API SHA-256은 `fa1e51e3d39473ca2852ac6b2899790547fa6667bb7337c646d29258a3e1c0fe`다. 20B 후보는 **104**이며 100~104를 누적 적용한다. 19차 102 전용 배포 스크립트를 그대로 재사용하지 않는다. 웹은 19차 관리자 보안 UI를 포함하는 같은 브랜치 산출물을 준비한다. PDF 처리기와 다른 프로젝트 서비스는 교체하지 않는다.

1. `ops/crypto20b_preflight.py`로 실행 파일/스키마·DB/파일 용량·기타 연결·키 로그 설정을 다시 확인한다. 기존 계정·SIM·실제 위치 본문은 출력하지 않는다. 디스크와 WAL 여유는 GPS 변환 외의 다른 프로젝트 증가량도 포함해 잡는다.
2. 실제 키 책임자·분리 보관·복구용 계정·백업·유지보수 시간대를 확정한다. 실제 관리자 PC/IP 및 19차 관리자 보안 적용 여부도 별도로 결정한다. 키 보관 실패 시 시작하지 않는다.
3. API와 GPS 전용 두 정리 타이머/서비스를 중지하고 모든 GPS DB 연결을 확인한다. 별도 수집/분석 워커가 추가됐는지 재점검한다. 다른 서비스 7개나 공용 방화벽을 함께 멈추지 않는다.
4. DB 전체·GPS 파일의 보호된 백업과 스키마/실행 해시를 남긴다. 쓰기 중지 상태에서 스키마 100~104를 적용하고 OFF 호환성을 확인한다. OFF 배포도 원래 99 바이너리로 단순 복귀 가능한 것으로 취급하지 않는다.
5. **운영의 log_parameter_max_length=-1을 0으로 변경하고 새 연결에서 검증한다.** error=0/pgaudit=off와 DB/모니터링 로그 정책도 확인한다. 키를 먼저 읽게 하지 않는다. 이 라운드에서는 운영 설정을 변경하지 않았다.
6. `admin_db_roles.py`의 104 호환 도구로 schema owner/runtime을 분리한다. runtime·키 파일은 API/정리 워커에만 전달한다. 키 파일은 실제 실행 계정 소유 0600으로 둔다. 기존 root:gps-api 640 환경파일을 키 파일로 대신 쓰지 않는다.
7. API/워커가 모두 중지된 상태에서 아래 도구의 check → fence → convert → check → resume를 실행한다. 실패하면 중지/maintenance를 유지하고 원인을 해결한 뒤 재개한다.
8. API와 두 워커의 환경에 `GPS_LOCATION_ENCRYPTION=pilot`, 키 파일 경로, runtime DSN을 함께 적용한다. 워커에 psycopg[binary] 3.2.10과 privacy_worker_db.py/location_storage.py 의존성을 설치한다. OFF 기존 운영은 psycopg2 호환을 유지한다.
9. API만 먼저 시작해 본인 조회·타 계정 거부·신규 수집·PDF·사진·자료 제공·정당한 파기를 확인한다. 그 뒤 워커/타이머를 재개한다. 운영 암호문·로그·성능 캡처는 여기서 별도로 생성한다.
10. 단말기 전체 TLS 승격/실외·절전 시험 후 HTTP 예외를 닫는 일은 별도다. 저장 암호화만으로 수집 전송구간이 암호화된 것으로 기록하지 않는다.

```bash
# 모두 GPS 서버의 별도 유지보수 계정에서 실행. 자격증명은 경로로만 전달.
python crypto20b_transition.py check --dsn-file /PRIVATE/gps-maintenance.json --keyring-file /PRIVATE/location-keys.json --uploads /GPS/uploads --private /GPS/private
# 모든 GPS 서비스/워커 정지 후 같은 인수로 fence, convert, check, resume 순서.
```

DSN JSON은 `{"dsn":"..."}`, 키 파일 형식은 20A 문서 참고. 경로 예시는 그대로 실행하지 않는다. 운영 적용은 이번 작업 범위가 아니므로 실제 활성화 명령은 실행하지 않았다.

### 재현 방법

빌드 호스트 작업 디렉터리는 `/home/etcom-hub/build/gps-crypto20b-20261107`이다. 테스트 Docker 네트워크는 internal이며 DB는 tmpfs에만 저장한다. 실계정/실제 위치를 복제하지 않는다.

1. API 소스와 의존 JSON, `examples`, `migrations`를 준비한다. **과거 마이그레이션은 작업 사본 줄바꿈이 아니라 Git blob 원본 바이트**로 가져온다. `git -c core.autocrlf=false archive` 또는 `git show HEAD:경로`를 사용한다. 0085만 원래 CRLF다. 타임스탬프가 과거인 tar를 푼 경우 Cargo 캐시가 입력 변경을 놓치지 않도록 `touch src/gps-tracker-api/src/main.rs` 후 빌드한다.
2. `ops/dev_crypto20b.sh`를 작업 디렉터리의 `dev20b.sh`로 두고 관련 Python 도구·`crypto20b-fields.json`·기존 회귀 시험 8개를 `fixtures/`에 준비한다. 운영 키/FCM/메일/결제 자격증명은 넣지 않는다.
3. `api-check` → `api-release` → `up` → `suite test_crypto20b.py` → `run_crypto20b_regressions.py` → `external-all` → `suite test_crypto20b_recovery.py` → `suite test_crypto20b_upgrade.py` → `suite capture_crypto20b.py` 순서로 실행한다. 격리 작업 경로/내부 네트워크/tmpfs 검사에 실패하면 진행하지 않는다.
4. 회귀 어댑터는 기존 업무 기대값을 유지하며 DB 연결을 psycopg3 서버 바인드/논리 뷰로 바꾼다. 10월 차량 자료는 11월 현재 월 대시보드에 포함되지 않도록 기대값을 날짜에 맞췄다. 오래된 시험의 계정 DELETE 정리는 최근 권리 대응 FK와 충돌하므로 합성 DB 전체 폐기로 대체한다. 대상 시험이 없으면 조용히 통과시키지 않고 기본 8개를 실행한다.
5. `stage_crypto20b.py --job ... --commit <전체 SHA>`는 최종 검증 바이너리 해시·회귀 결과·웹 소스 308개의 일치를 검사한 뒤 후보 파일만 묶는다. **배포/서비스 재시작/DB 접속을 하지 않는다.** 실제 키·자격증명·업로드·DB 사본·PDF 처리기 교체는 묶음에서 제외한다.

### 이번 검증에서 바로잡은 문제

- 유지보수 오류가 stderr로 출력되는 경우도 기동 거부 시험에서 확인하도록 수정했다.
- 차단/종료된 계정 자료의 암호문 교체가 일반 수집 차단 트리거와 충돌하던 문제를 owner 전용 트랜잭션 표시로 해결했다. 차단 상태를 해제하거나 runtime에 우회 권한을 주지 않는다.
- Timescale 압축 테이블의 트리거 비활성화와 압축 튜플의 `FOR UPDATE`가 지원되지 않으므로, 해당 방법을 쓰지 않고 테이블 배타 잠금 아래 제한된 배치 UPDATE로 변환한다.
- 키 교체 중 실패해도 신키를 잃지 않도록 **변환 전에 신·구키 파일을 보존**한다. 중단 후 재시도는 마지막 확정 배치부터 이어진다.
- 운영과 같은 구 바이너리의 체크섬 검사가 Windows 작업 사본의 과거 SQL 줄바꿈 차이를 차단했다. DB checksum을 덮어쓰지 않고 Git 원본 입력과 강제 재컴파일로 해결했다. 업그레이드 시험은 기존 모든 마이그레이션의 SHA-384도 대조한다.

- 업그레이드 시험에서 Docker API 종료 후 PostgreSQL의 ClientWrite 연결이 남아 전환이 거부됐다. 검증에서는 제거된 컨테이너의 전용 합성 DB 세션만 정리한 뒤 재개했다. 운영 도구는 다른 세션이 남으면 계속 거부하며 이를 자동 종료하지 않는다.
