# 22차 — 정보주체 연결·제공 내역·통보 재시도

2026-11-08. `codex/location-business-prep` / draft PR #248. **후보 스키마 106, 운영 미배포·통보 미활성**. 내부 Docker 네트워크, tmpfs DB와 합성 계정만 사용했다. 실제 회원·SIM·회사 자료, 운영 서비스·키·방화벽·펌웨어는 변경하지 않았다.

## 이번 후보의 범위

회사 관리자가 **로그인 계정이 연결된 직원 + 차량의 SIM 연결 + 시간 구간**을 제안하고, 해당 직원이 자기 계정에서 확인·거절하도록 구현했다. SIM 소유자, 차량 예약자, 운행일지에 입력된 운전자명만으로 정보주체를 자동 확정하지 않는다. 이는 계정 사용자의 명시적 진술·동의를 기록하는 기능이며 PASS 등의 실명 확인이나 물리적으로 누가 운전했는지를 증명하는 기능은 아니다.

본인 확인된 구간에 대해 회사가 위치를 조회하면 조회 원장과 통보 대기를 같은 트랜잭션에 먼저 저장한다. 개인의 **내 정보 → 권리 요청 화면**에서 연결 요청과 제공 내역을 확인할 수 있다. 회사 측 진입점은 **법인차 → 사용자 → 운전자와 위치 기록 연결**이다. 검증용 제한으로 기존 단말기 상태 조회가 차단된 경우에도 연결 화면은 접근할 수 있다.

**전체 법인 지도·리포트에 통보가 완전히 연결됐다는 뜻은 아니다.** ON 후보에서 허용하는 위치 제공은 `/devices/:id/locations/page`의 검증된 기간 조회와 신규 `/corporate/subject-mappings/:id/locations`뿐이다. 후자는 DB의 확인된 시작·종료 시각으로 조회하고 URL로 범위를 늘릴 수 없다. 기존 전체 지도·최근 위치·혼합 리포트·미분류 외부 전달은 확인 구간으로 응답 범위를 제한하는 작업이 끝나지 않았으므로, 해당 회사/연결 자료가 포함되면 차단한다. 정책은 전역이므로 현재 후보를 정상 운영에 켜면 기존 법인 화면이 제한된다. **22B 경로 확장과 전체 사용 흐름 검증을 마친 뒤 운영 전환을 판단한다.**

## 연결과 동의

- 확인 단위는 기존 `devices.id`(SIM 자료 식별자), 차량 연결 ID, 회사 계정, 본인 로그인 계정, `[시작, 종료)` 구간이다. 하드웨어 인증 UID가 바뀌어도 원본 데이터 키를 UUID로 바꾸지 않는다.
- 기간은 최대 31일, 시작 시각은 현재 이전이다. 종료가 미래인 선언도 가능하므로 사전 지정은 완료된 실제 운전의 증거로 해석하지 않는다. 운전자 교대·오등록 정정 절차는 별도 인수 대상이다.
- 제안한 회사 관리자도 본인을 대신해 확인하지 못한다. 대리 로그인 토큰과 회사 범위 헤더로 본인 확인 API를 호출하면 거부한다. 확인 당시의 직원 소속·차량 연결 유효성을 다시 검사하고, 조회할 때에도 차량·SIM 연결과 기간이 유지되는지 재검사한다. 확인 후 배정 기간이 축소됐으면 기존 동의만으로 바깥 자료를 제공하지 않는다.
- 같은 SIM의 확인 구간 중복은 DB 배제 제약으로 거부한다. 중복 요청 번호와 revision으로 재전송·동시 변경을 처리한다. 확인/거절/철회와 이력은 원자적으로 저장한다.
- 퇴사하여 현재 회사 계정 연결이 해제돼도 과거 연결은 남아 이용·제공 중지 및 철회 차단에 사용한다. 기능 또는 조회 기록을 OFF로 바꿔도 기존 철회 차단은 유지한다. 본인 권리 요청·통보 확인은 차단하지 않는다.
- 진행 중인 위치 처리와 철회가 경합하면 409로 변경을 거부하고 다시 시도하도록 한다. 이미 전달된 응답·다운로드 파일을 회수했다고 표시하지 않는다.
- 본인 연결 목록은 200개 단위 커서 페이지로 과거 요청까지 확인한다. 회사 제안 목록·차량 연결 선택은 최근 200개 범위이며 직원 선택은 활성 직원 전체를 불러온다. 대규모 조직의 검색/페이지 확장은 남아 있다.

보수적 제약: 철회된 구간 위에 새 확인을 추가해도 이전 철회를 자동 해제하지 않는다. 같은 사람의 재동의·잘못된 연결 정정은 별도 검토 경로가 필요하다. 아직 매핑하지 않은 개인 자료의 정보주체를 소급 추정하지 않는다.

## 통보와 재시도

`location_provision_notices`에는 제공 사건·매핑·본인·회사·실제 조회 계정·SIM·차량 ID, 목적, 동의 버전, 정책 근거 식별자, 구간과 시각을 저장한다. 좌표·FCM 토큰·비밀번호를 복제하지 않는다. 표시 편의를 위해 현재 회사명/차량명을 조회하지만, **당시 고정된 식별자는 ID**다. 현재 표시명을 과거 명칭 증빙으로 해석하지 않는다.

| 상태 | 의미 |
|---|---|
| 사전 대기 | 위치 제공 전 DB에 통보 의도를 저장했음. 아직 사용자에게 제공 완료로 표시하지 않음 |
| 서버 응답 준비 | 서버가 응답 데이터를 준비함. 브라우저가 실제 받았다는 증명은 아님 |
| 전달 결과 미확인 | 중단 등으로 결과를 확정하지 못함. 완료로 덮지 않고 내역에 표시 |
| 푸시 서버 접수 | FCM이 요청을 수락함. 스마트폰 수신·열람 완료와 구분 |
| 본인 확인 | 사용자가 해당 내역의 확인 버튼을 직접 누른 시각 |
| 발송 확인 필요 | 영구 오류·등록 해제 토큰·한도 초과 등. 내역은 남고 본인이 재시도 요청 가능 |

통보 워커는 DB 대기열을 사용한다. `FOR UPDATE SKIP LOCKED`, 90초 lease와 완료 시 lease ID 대조로 중복 워커·늦은 결과를 제어한다. 재시도는 지수 지연(최대 하루), 자동 시도 10회 후 검토 상태로 전환한다. 전송 직후 프로세스 중단으로 완료 기록이 없더라도 이미 획득한 시도 횟수에 포함한다. **전송 성공과 DB 기록 사이의 장애에서는 중복 푸시가 가능하다. exactly-once 배달을 보장하지 않는다.** Android 알림 tag는 사건 ID를 사용한다.

통보의 기간은 조회 요청 범위이며 그 안의 모든 좌표가 반환됐다는 뜻은 아니다. 현재 회사 기간 조회는 처음 500건과 추가 데이터 여부만 제공한다. 워커는 5초 주기로 한 건씩 처리하므로 정상 단일 워커도 분당 최대 약 12건(네트워크 소요 제외)이다. 자동 갱신·대규모 운행 조회에 그대로 확장하지 않으며 22B/운영 인수에서 발송 정책·처리량·대기열 경보를 검증한다.

현재 유효한 본인 계정·FCM 토큰을 전송 직전 다시 확인하고, 계정/토큰 행 잠금을 전송 동안 유지한다. 일반 알림 OFF·장기 미통신 24시간 제한은 이 대기열에 적용하지 않는다. 키가 없거나 푸시 정책이 OFF면 실제 발송은 하지 않고 앱 내 내역을 유지한다. 토큰이 없으면 재시도·검토 상태로 남긴다. 푸시 본문은 위치·차량·운전자 이름 없는 일반 안내다. 실제 FCM 서버·실물 휴대폰 도착, iOS, 알림 클릭 후 전용 화면 이동은 이번 격리 시험에서 검증하지 않았다.

## 권한·암호화·보관·복원

- API runtime은 정책 ON/근거 변경을 할 수 없다. 연결/통보 삭제, 연결 이력·시도 이력 수정/삭제, 트리거 변경을 거부한다. 필요한 업무 DML과 정책 읽기만 부여한다. 기존19차 역할 분리를 갱신해 적용해야 한다.
- 20B 암호화 ON 상태에서도 위치 읽기는 기존 복호화 함수/뷰를 사용한다. 원본 좌표는 암호문으로 보존되며 새 매핑·통보 메타데이터에 좌표는 없다. 메타데이터는 익명정보가 아니며 일반 개인정보 보호·보관 정책의 대상이다.
- 회사에서 연결이 해제된 정보주체도 회사 자료 보관·파기를 자동 확정하지 않도록 기존 보관 엔진에 보류 근거를 추가했다. 계정 종료 영향 목록에도 연결·통보 수를 표시한다. 새 이력의 법정 분류·보존 기간·철회 시 삭제 범위는 회사 정책 확정 전 임의 삭제하지 않는다.
- checkpoint v2에 연결 상태/버전, 연결 이력, 통보, 시도 이력을 포함한다. 최신 독립 사본의 해시와 계정·SIM 식별 검사를 통과하고 API/워커를 모두 멈춘 상태에서만 복원한다. 이미 더 최신인 철회를 과거 동의로 덮지 않고 식별자 충돌은 전체 트랜잭션을 거부한다.
- schema106 복원에는 v2가 필요하다. v1 또는 식별자가 충돌하는 파일은 거부한다. 복원 후 연결·푸시 정책은 OFF, 미완료 통보는 검토 상태로 전환하며 자동 재발송하지 않는다. FCM 접수·열람 시각은 서로 독립적으로 보존한다. 외부 사본 최신성·파기까지 자동 증명하는 기능은 아니다.

검증 중 소스 archive의 오래된 mtime 때문에 Cargo가 이전 release 실행 파일을 재사용하는 문제가 발견됐다. 앱 패키지의 debug/release 산출물을 각각 정리한 뒤 재컴파일하고 전체 통합 시험을 새 실행 파일로 다시 수행하도록 절차를 고쳤다. 최종 증빙에는 이 재실행 결과만 사용한다. 소스 전송 시 줄바꿈 정규화는 텍스트에만 적용한다. PNG/ICO/TTF 등 바이너리까지 바꾸지 않도록 원본을 재전송하고 웹을 다시 검증했다.

5. 시험 후 `down`으로 컨테이너·네트워크·tmpfs 자료를 지우고 시험 키·runtime 자격증명·checkpoint를 제거한다. 검증 로그·소스·후보 빌드는 남긴다.

**22B를 먼저 진행:** 기존 법인 지도·최근 위치·운행 리포트·다운로드·예약 연계의 실제 응답을 확인된 정보주체 구간으로 제한하고 통보 사건과 연결한다. 부분 응답·정보주체 미확정·동의 철회·운전자 교대·재동의·회사 이름 변경·대규모 목록·권한 변경을 UI부터 검증한다. 승인되지 않은 공유/외부 처리 경로는 계속 차단한다. 이 작업 전에는 전체 22차 또는 운영 제공 통보 완료로 표시하지 않는다.

별도 운영 인수: 위탁/제3자 제공 분류, 동의 문안·받는 자·통보 방법/시기·보관 근거 확정; 실제 FCM/대체 채널 수신 및 알림 진입 확인; 누적99→106 운영 규모 리허설; 대기열 체류·검토 건수 경보/담당자; 관리자 PC/IP/MFA, 키와 최신 checkpoint 독립 보관, TLS 전량 승격, 글로벌 처리 잠금의 부하 검증. 23차 운영 증빙은 이 조건과 실제 설비 준비에 맞춰 수집한다.
