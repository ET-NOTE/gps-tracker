# 124차 DB 조회·복호화·재시도 대기 계측과 병목 개선

## 범위

123차에서 남은 전체 이력 지연과 높은 최종429를 분해한다. 운영 VPS에는 접근하거나 배포하지 않는다. `etcom-hub`의 내부 전용망·합성 데이터에서 이전123 API와124 후보를 비교한다. 기존 SIM·수신 당시 소유자·동의·철회 경계는 유지한다.

**구현·격리 검증·후보 보존 완료 / 운영 미배포 / 성능 인수 보류.** 후보는113, 마지막으로 확인한 운영은99다. 운영의 현재 상태를 이번 라운드에서 재조회한 것은 아니다.

## 계측의 의미

- API: 실행 허용 대기(`admission_ms`), DB 풀 대기(`pool_ms`), 트랜잭션 준비(`setup_ms`), 연결을 보유한 처리 구간(`scope_ms`)을 별도로 기록한다. `RUST_LOG=info,gps_read_timing=debug`에서만 출력한다. 계정·장치·좌표·SQL·URL·자격증명을 출력하지 않는다. 마지막 구간은 SQL뿐 아니라 결과 전달·애플리케이션 처리·COMMIT도 포함하며, 별도 비동기 취소 정리 시간은 제외한다.
- SQL: 실제 API SQL을 같은 비소유 DB 역할로 준비한 뒤 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`으로 실행한다. `pg_stat_xact_user_functions`의 같은 트랜잭션 통계로 `gps_open_cell`과 내부 `pgp_sym_decrypt`를 측정한다. SQL 시간에는 복호화 시간이 이미 포함된다. 중첩 함수 시간을 더하지 않는다.
- 클라이언트: 최초 요청과 재시도의 HTTP 소요 시간 합계, 재시도 대기, 전체 성공 응답 지연을 분리한다. 각 지표의 p95끼리는 더할 수 없다. 최종429는 성공으로 세지 않는다. 최대3회 시도·기존 `Retry-After`와 지수 대기 정책은 유지한다.

## 수정 전 확인

첫 SQL 진단에서 단일 SIM의 월간 조회가 같은 계정의 다른 SIM 행까지 해시 조인 입력으로 읽는 것을 확인했다. 대상14880행에 비해59520행을 읽었다. materialized 후보 키의 장치 조건이 복호화 뷰의 조인 입력으로 전파되지 않은 것이다. 집계는 필요하지 않은 넓은 원본 payload도 materialized 중간 결과로 보유했다.

113번 마이그레이션은 기존 조건을 유지하면서 조인 입력에 `r.device_id=wanted_device`를 명시하고, 속도 집계의 중간 열을 실제 사용 열과 boot 식별값으로 줄인다. 기존 SQLx 마이그레이션 파일은 수정하지 않는다. 저장 데이터·암호화 방식·거리 계산·동의 정책은 변경하지 않는다.

추가 대조에서 전체 이력의 강제 범용 계획은 수정 전 중앙값35.894초, 수정 후에도33.649초였다. 같은 입력값의 custom 계획은1.349/1.324초였다. 이에 비싼 위치 조회의 읽기 전용 트랜잭션 안에서만 `SET LOCAL plan_cache_mode='force_custom_plan'`을 적용한다. 공유DB의 전역 설정이나 풀 기본값은 바꾸지 않는다. 강제로 선택한 범용 계획의 위험을 재현한 결과이며, 기존 API의 느린 요청 전부가 그 계획을 썼다는 증거는 아니다. 실제 API와 최종429의 영향은 아래 부하 대조로 별도 판단한다.

## 분리 계측으로 확인한 병목

수정본의 완료 조회 트랜잭션에서 DB 풀 대기 p95는0.237~0.284ms, 준비 단계는0.216~0.246ms였다. 이 시험에서 DB 풀 부족은 주된 대기가 아니다. 전체 이력의 연결 보유 처리 p95는1.446/1.459/1.477초, 나머지 조회는1.622/1.628/1.651초다. 완료 요청의 실행 허용 대기 p95는약185~236ms, 거절 요청은약252ms로 기존250ms 시한에 가까웠다.

클라이언트에서 전체 이력의 HTTP 시도 합계 p95는 수정 후2.590/2.548/2.509초, 재시도 대기 p95는4.576/4.559/4.380초였다. 페이지는 HTTP 합계1.003/1.032/1.172초에 비해 재시도 대기4.526/4.588/4.453초다. **실행 자리를 기다리다429를 받고 다시 기다리는 시간이 남은 사용자 지연의 큰 부분**이다. 각 p95를 더한 값이 전체 p95는 아니다.

수정 SQL의 custom 계획에서 `gps_open_cell` 포함 시간 중앙값은 전체 이력339ms·월간 집계302ms·Fleet301ms·페이지26.6ms였다. 그 안의 실제 PGP 함수 시간은각146/137/138/11.4ms다. 복호화만으로 전체 이력 SQL1.324초나 HTTP 성공p95약7초를 설명할 수 없다. 암호화 검증을 줄이거나 평문 캐시를 추가하는 방향은 채택하지 않았다.

API 계측은 opt-in이며 한 HTTP 요청이 여러 조회 트랜잭션을 사용할 수 있다. 월간 페이지 순회도 포함되므로 트랜잭션 완료 건수와 HTTP 성공 수는 일대일이 아니다. 계측 기본값으로 운영 로그량이나 보존정책을 바꾸지 않는다.

## 검증 중 확인·수정한 사항

압축이 활성화된 Timescale hypertable에서 `DISABLE TRIGGER`를 허용하지 않아 첫 시험 데이터 생성이 실패했다. 제품 SQL을 변경하지 않고 검증기의 경계 메타데이터 생성 방법을 수정했다. 시험 트랜잭션 안에서 해당 메타데이터 트리거 함수만 잠시 대체한 뒤 원문을 복구하고 비교한다. 암호화·소유권 트리거는 유지하며 전체 시험은 rollback한다. 실패 로그를 증빙으로 보존한다.

서로 다른 SIM·수신 당시 소유자, 빈/역전/무한 시간 범위, 지연 수신·경계 메타데이터 미완성, 빈 fixes·누락 fix,5000바이트 원본 payload를 포함한80개 비교가 일치했다. 늦은 데이터 추가·삭제 후80개 비교도 일치했고 rollback 후 원래 결과가 복원됐다. 키 누락과 암호문 문맥 불일치는 실제 복호화 오류(`P0001`과 고정 오류문구)를 확인해 단순 권한 오류와 구분했다. 물리 평문 열은0이었다.

API fmt·clippy(`--all-targets -D warnings`)·일반 Rust91개·release 빌드가 통과했다. 일반 실행에서 제외된 DB 시험9개 중 이번 읽기 설정 시험1개를 비소유 런타임 역할·비특권 OS 계정으로 별도 실행해 통과했다. 읽기 전용·20초 제한·custom 계획 설정과 COMMIT 후 풀 기본값 복원을 검증했다. 나머지 제외8개를 통과로 계산하지 않는다.

## 기능·권리·최종 검증

이전/수정28개 HTTP 응답이 의미상 일치했다. XLSX는 생성 메타데이터 `docProps/core.xml`만 제외하고 셀·시트·스타일·링크 등 나머지 모든 항목을 비교했다. 실제112→113 마이그레이션과 보호된 API 재기동이 성공했다. 기존 SQLx 이력 체크섬을 변경하지 않았다.

전체 이력 실행1건/전체2건, 대기 이력의 DB 연결 미점유, 대기·실행 취소와 자리 회수,429의 `Retry-After: 2`를 실제 HTTPS로 확인했다. 최종 전체 이력 자리 재사용은0.0145초, 집계/페이지 회수는0.0083/0.0086초였고 남은 조회는0건이다.

22/22B/22D의20개 업무 시험군(7+7+6)이 스키마113에서 통과했다. 정보주체·회사 권한·동의·중지·철회·재동의·정정, 통보 저장 실패 시 응답 차단, 기존 지도·리포트·다운로드, SIM 기준 이력과 하드웨어 인증 교체, 공개 공유 경계, 오래된 권리 체크포인트의 철회 부활 차단을 포함한다. 외부 FCM은 보내지 않았다.

최종 정상28조회·타 계정8거부, 평문 수집426·미등록 장치 서명 요청401을 확인했다. 스키마113·10월 집계248일이며, 물리 평문 위치·열린 트랜잭션·임시 이미지·정리 대기·잔여 PDF 처리기는 모두0이다. 원본 증빙67파일·7,378,855바이트를 빌드 호스트와 SHA-256으로 대조했다. [증빙 안내](../evidence/runtime124-20261114/README.md)의 계측 범위와 실패 기록을 함께 읽는다.
