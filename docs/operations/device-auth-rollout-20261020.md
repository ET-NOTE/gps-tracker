# GPS 장치 인증 전환 및 실기기 재등록 검증

2026-10-20 KST. 대상은 gps.serial.kr 운영 서버와 단말-520211이다. dev-gps에는 배포하지 않았다.

> 후속 변경: 아래 등록번호 중심 절차는 같은 날 [SIM 기준 등록·하드웨어 인증 분리](sim-first-hardware-rollout-20261020.md)로 대체했다. 현행 사용자 등록은 SIM 전체 번호와 이름만 입력한다. 이 문서는 최초 배포의 이력이다.

## 배포 및 확인 결과

- 서버: `dev-20261020-131847-7bcbff3`, 소스 `7bcbff3346fe8bf51d59a61c1085a631ba49bfdb`. release 문자열과 별개로 environment는 production이다. DB는 추가 마이그레이션 69/70을 적용했다.
- 펌웨어: `idf-caltest/operating-7bcbff3346`, ESP-IDF 5.5.4. 절전 활성, timer wake 활성, KC 비활성. 이전 운영본의 PWR/DTR 보호 동작을 유지했다.
- 실물: COM62, ESP32-C3, MAC `68:ee:8f:21:33:64`. 장치 ID 3163, UID `sim-47520211`, 소유 계정 user@user4.com(ID 28).
- 플래시 전 boot/NVS 64 KiB와 기존 앱 512 KiB를 백업했다. 기존 앱 checksum과 validation hash가 유효했다. 전체 4 MiB 읽기는 USB 수신 오류로 완료하지 못했으며 전체 백업으로 취급하지 않는다. 쓰기는 bootloader/partition/OTA 초기 데이터/app 구간만 수행했고 NVS는 지우지 않았다. 새 플래시의 모든 구간 해시가 일치했다.
- 장치별 인증정보를 USB로 프로비저닝한 뒤 LTE HTTP 200과 요청·응답 서명 검증(counter 1~9)을 실물에서 확인했다.
- 로그인된 웹 UI에서 **데이터 보관 후 해제**를 실행했다. DB owner_id가 NULL로 바뀌고 과거 기록이 유지되는 것을 확인했다.
- 실물 시리얼의 `REGISTER` 명령으로 새 1회 등록번호를 생성했다. 성공한 서명 전송 후 그 번호를 웹에 입력해 같은 계정으로 재등록했다. 장치 ID 3163이 유지되고 owner_id=28로 복원됐다. 등록번호는 소비됐다. 13:31 이전 계정 소유 기록 38,910건은 그대로 유지됐다. 검증 중 추가된 no-fix 기록은 이 숫자와 별도다.
- 재부팅 뒤 NVS 인증정보를 재사용하여 counter 4097, 4098의 HTTP 200 및 응답 서명 검증을 확인했다. 별도 재페어링은 필요 없었다.
- 실내 GNSS fix는 얻지 못했다. 이번 검증으로 실외 좌표 수신·운행 경로 정확도나 실제 절전 진입까지 검증됐다고 판단하지 않는다.

## 사용자 등록 방법

1. 개별 인증정보가 준비된 운영 펌웨어를 켜고 시리얼 모니터를 115200 baud로 연다.
2. `[REGISTER]` 뒤의 등록번호를 확인한다. 장치의 서버 전송 성공 후에만 사용할 수 있다.
3. 웹 **단말기 → 추가**에서 장치 등록번호와 이름을 입력한다. UID/SIM을 직접 입력하거나 전수 스캔하지 않는다.
4. 정상 사용과 재부팅에는 재등록하지 않는다. 연결을 해제한 뒤 재등록하려면 시리얼에 `REGISTER`를 입력하고 Enter를 누르거나 전원을 다시 켠다. 새 번호가 전송된 뒤 등록한다.

등록번호는 미소유 장치에 대해 24시간 유효하며 한 번만 사용한다. 서버에는 원본 번호가 아닌 해시를 보관한다. 계정별 실패 횟수도 제한한다.

## 운영자 순차 전환

인증키는 공통 소스나 다운로드 펌웨어에 하드코딩하지 않는다. 장치별로 `ops/provision_gps_credential.py`를 사용해 서버 DB에 digest를 넣고, 비밀 파일을 `ops/provision_connected_gps.py`로 해당 USB 실물에만 입력한다. 파일은 공개 웹 경로·Git·로그에 넣지 않는다. 기존 인증정보를 다시 입력하면 카운터가 초기화되므로 임의로 재프로비저닝하지 않는다. 키 교체는 서버와 실물을 함께 처리한다.

기존 다른 GPS 하드웨어는 migration 69 시점의 행에 한해 `ingest_legacy_allowed=true`로 전환 기간 통신을 유지한다. 신규 미등록 장치의 익명 생성은 허용하지 않는다. 개별 장치에서 첫 서명 전송이 성공하면 그 장치의 unsigned fallback은 영구 차단한다. 전체 장치 인증 완료 전에는 다른 구버전 장치의 위조 위험이 모두 제거됐다고 표현하면 안 된다.

현행 modem HTTP 전송에 양방향 HMAC과 증가 카운터를 추가했다. 무결성·장치 인증·재전송 차단을 제공하지만 **TLS 암호화는 아니며 전송 중 좌표의 기밀성을 제공하지 않는다.**

명령은 UUID로 재시도하고 펌웨어 NVS에 수신 ID를 저장하여 중복 수신을 억제한다. ACK는 명령 수신 확인이며 물리적 동작 완료 증명은 아니다.

## 복제 검증과 복구

운영 DB의 127,536개 location_records를 복제·행 해시 대조했다. 인증/변조/재전송, 등록번호 재사용, phone JWT, 차량 정보/사진 소유권, 만료 인계 링크, 명령 재시도/ACK, 공유 결제 원자성, WebSocket 소유권·만료, 통계 실패 격리, housekeeping 보관 테스트가 통과했다. 기존 API/배치·복원력/속도/WebSocket/배터리/업무/FCM 회귀도 통과했다. 웹 97개 테스트와 Rust 정적 검사·단위 테스트 및 별도 FCM/AI 트랜잭션 테스트도 통과했다.

복제 통계 poll=5초에서 기존 legacy retry의 500ms 타이밍 한계를 넘기는 테스트 지연이 발생했다. 운영 poll=300초로 실행한 회귀는 통과했다. legacy 수신에는 여전히 그 기존 시간 기반 중복 판정 한계가 있으며 새 인증 카운터와 혼동하지 않는다. 속도 테스트의 fixture run ID는 보안 helper의 요구에 맞춰 전체 UUID로 수정했다.

운영 백업: `/home/mmm/backups/gps-security-20261020`. Timescale 압축 복구 때문에 logical dump와 location_records CSV를 함께 보관해야 한다. 외부 PC 복사본 8개 파일의 SHA256을 검증했다. 기존 API 소스에 migration 69/70만 추가한 schema70 호환 복구 바이너리를 빌드하고 복제 DB에서 기동을 확인했다. 배포 스크립트 `ops/release_device_security.py`는 API/웹/환경/nginx 기준 해시를 검사하고 실패 시 런타임을 복원하며 추가 스키마를 삭제하지 않는다.

차량 사진은 공개 uploads에서 분리하고 인증된 API로 제공한다. nginx 공개 car-images 경로는 차단했다. 전수 스캔 UI는 관리자에게도 노출하지 않는다. 백엔드 KC 전용 예외는 운영에서 비활성이다.

이번 배포는 우선순위 P1 및 일부 서버 처리 보완이다. 별도 감사 항목의 FCM 딥링크, 라우트/모바일 Fleet, 지도 실패 안내, 모달 포커스, Android 다운로드 등 후속 UI·앱 작업이 모두 완료됐다는 의미는 아니다.
