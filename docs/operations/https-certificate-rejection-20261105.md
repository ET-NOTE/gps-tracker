# HTTPS 인증서 거부 실기기 시험 — 2026-11-05

> 후속 갱신: 같은 날 ESP32 Mbed TLS 경로로 교체해 **호스트명·만료·미신뢰 CA 거부 재시험을 통과**했다. 현재 설치 빌드는 `https-pilot-6ce474583c`다. [후속 보완 기록](https-mcu-verification-20261105.md)을 참조한다. 아래는 교체 전 모뎀 SHSSL 경로의 1차 시험 이력이다.

## 1차 판정

**시험은 완료했으며 F1 운영 전환 판정은 불합격이다.** SIM7080G `1951B12SIM7080`의 현재 SHSSL/SHCONN 경로에서 신뢰하지 않는 CA와 만료 인증서는 거부했지만, 신뢰하는 CA가 발급한 **다른 호스트명의 인증서를 수락하고 HTTP 요청까지 보냈다.** SNI 설정을 서버 이름 검증으로 간주하면 안 된다.

HTTPS/TLS 1.2 연결과 HMAC 요청·응답 인증의 정상 동작은 확인됐으나, 목적 서버의 인증서 이름까지 검증하는 TLS 구현은 아직 확보하지 못했다. HMAC은 위치 본문의 기밀성을 대신하지 않는다. 이 결과를 모뎀의 모든 버전·다른 AT 통신 경로로 일반화하지 않는다.

## 대상과 격리

- 대상: 단말-520211, ESP32-C3 `68:ee:8f:21:33:64`, COM62, SIM7080G `1951B12SIM7080`.
- 펌웨어 커밋: `c0ce01310b303c749cd6f052bd44d2e6db2d8f7f`, ESP-IDF 5.5.4. 호스트 회귀 156개 통과.
- 시험 프로필: `tls-cert-test`. 절전 OFF, 타이머 기상 OFF, 워치독 ON.
- 시험 entry point는 운영 GPS 수집·telemetry·장치 인증 초기화를 실행하지 않는다. 실제 `lte.cpp`의 TLS 연결 경로를 사용하며 연결 성공 후 고정 `GET /tls-probe`만 전송한다. 시험 서버에 실제 위치·인증키·HMAC 헤더를 보내지 않았다.
- 임시 목적지: `https://gps.serial.kr:18443/tls-probe`. DNS는 바꾸지 않았다. 운영 Nginx/443 인증서, 수집 API, DB 설정은 바꾸지 않았다.
- 서버는 임시 Python TLS 리스너이며 loopback 및 시험 단말기 1NCE 출구 IP만 허용했다. 임시 UFW 규칙도 같은 출구 IP로 제한했다.
- 정상·만료·호스트 불일치는 같은 시험 루트 CA를 신뢰한다. 신뢰하지 않는 CA 사례만 별도 루트다. 루트·중간 CA는 EC P-384, leaf는 EC P-256, 서명은 SHA-256이다. 운영 인증서의 개인키는 사용하지 않았다.
- 연결마다 새 TLS 컨텍스트를 만들고 세션 티켓을 껐다. 서버 로그의 `reused=false`로 각 성공 연결이 재개 세션이 아님을 확인했다.

재현 소스는 `idf_caltest/main/tls_cert_probe.cpp`, `idf_caltest/tools/tls_cert_fixture.py`다. `build_firmware.py tls-cert-test --test-ca-header <공개-시험-CA-헤더>`로만 생성하며 운영 프로필과 분리한다. 실제 실행 시 고정 시험 포트와 허용 IP, 비공개 키 저장소, 시간 제한을 준비하고 종료 후 회수한다.

## 시험 결과

PC OpenSSL/Python 클라이언트에서 같은 시험 루트·서버 이름으로 대조했다. 정상은 HTTP 200, 만료는 verify code 10, 미신뢰 CA는 20, 호스트 불일치는 62로 거부됐다. 이후 아래 실기기 시험을 진행했다. 시간은 KST이며 각 행의 반복은 독립 RUN 명령이다.

| 인증서 | 실기기 시험 시각 | TLS 연결 시도 | HTTP 요청 | 판정 |
|---|---|---:|---:|---|
| 정상 `gps.serial.kr` | 11:36:37, 11:40:27, 11:41:55 | 3회 | 3회, 모두 200 | 정상 대조 성공 |
| 만료된 `gps.serial.kr` | 11:37:07, 11:41:08 | 4회: RUN당 재시도 포함 2회 | 0회 | 거부 성공 |
| 미신뢰 CA의 `gps.serial.kr` | 11:37:27, 11:41:31 | 4회: RUN당 재시도 포함 2회 | 0회 | 거부 성공 |
| 신뢰 CA의 `wrong-host.invalid` | 11:40:05, 11:40:44 | 2회 | **2회, 모두 200** | **거부 실패** |

모든 성공 연결은 `TLSv1.2 / ECDHE-ECDSA-AES256-GCM-SHA384`였다. SNI는 네 사례 모두 `gps.serial.kr`이다. 호스트 불일치 인증서의 CN·SAN은 모두 `wrong-host.invalid`이며 만료되지 않았다. 두 번의 불일치 시험 사이와 마지막에 정상 대조를 통과했다.

만료 사례는 단말의 `SHCONN` 실패와 서버의 `SSLV3_ALERT_CERTIFICATE_EXPIRED`, 미신뢰 사례는 `TLSV1_ALERT_UNKNOWN_CA`로 확인했다. 오류 문자열의 SSLV3/TLSV1 표기는 협상 버전이 아니다. 만료 사례에서 서버 OpenSSL의 handshake 완료 로그 뒤 수신 단계에 거부 alert가 왔으므로, “핸드셰이크가 전혀 수행되지 않았다”고 기술하지 않는다. 확인한 차단 경계는 **HTTP 응용 요청 전**이다.

인증서 유효기간(UTC): 정상·미신뢰·다른 호스트는 2026-11-04 02:28:40부터 2027-11-05 02:28:40까지, 만료 사례는 2026-11-04 02:28:40에 만료됐다. RTC는 각 RUN마다 실제 2026-11-05 시각을 확인했으며 `IGNORERTCTIME=0`을 유지했다. 거부 후 HTTP나 빈 CA 목록으로 전환하지 않았다.

## 함께 수정한 준비 결함

1. 첫 NTP 결과는 `+CNTP: 1,"2026/11/05,02:32:04"`였다. 성공 코드 1만 있는 줄을 기다리던 코드가 시각이 붙은 성공 응답을 45초 대기 실패로 오인했다. 출력 모드를 명시하고 결과 코드를 구분해 읽은 뒤 실제 CCLK를 재검사하도록 고쳤다. 오류 코드·코드 접두사·미완성 응답 회귀 사례도 추가했다.
2. 첫 시험 CA 파일명은 SHSSL의 20바이트 한도를 넘었다. 19바이트 이름 `gt-e1a645020e52.pem`으로 바꾸고 컴파일 시 길이를 검사한다.

이 두 준비 실패는 TLS 인증서 거부 결과에 포함하지 않았다. 수정 후 11:36:36 시험 부팅과 11:43:16–17 복구 부팅에서 첫 시각 동기화가 약 1초 안에 완료됐다. 인증서 유효기간 검사는 끄지 않았다.

[SIMCom AT 매뉴얼 V1.07](https://dfimg.dfrobot.com/60c1e008bddfc41c3293de80/wiki/e8879bae8fcb219d1eeda40686910686.pdf)의 SHSSL 및 CNTP 항목을 확인했다. 해당 매뉴얼에서 호스트명 검증을 활성화하는 별도 설정을 확인하지 못했다. 이것만으로 다른 모뎀 버전의 지원 여부를 단정하지 않는다.
