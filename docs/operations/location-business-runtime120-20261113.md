# 120차 — PDF 전역 동시성·취소·메모리 한도

2026-11-13. 구현과 아래 격리 검증을 완료했다. **운영 미배포, 스키마 112 후보, `activation_ready=false`.** 운영 VPS를 조회하거나 변경하지 않았다. 실제 운영의 마지막 확인은 119차 기록을 따른다.

## 바뀐 동작

- 별도 PDF 서비스가 공용 잠금을 잡은 뒤 한 문서만 처리한다. API별 제한 외에 서비스 전체 제한이 생겼다. 다른 요청은 문서를 읽기 전에 Busy로 거부하고 API는 429를 반환한다.
- 감시 프로세스는 문서 내용을 읽지 않는다. 실제 처리 자식만 기존 시스템 호출 제한을 적용해 PDF를 해석한다. 감시자와 자식이 같은 잠금을 보유하여 API 요청 취소나 감시자 종료가 잠금을 먼저 풀지 못한다.
- 정상적인 요청 송신 종료는 허용한다. 연결 전체 종료는 자식을 종료·회수하고, 열린 연결도 최대 13초 후 종료한다. API 제한은 15초, 서비스 제한은 20초다.
- 잠금 파일은 root 소유·쓰기 불가·빈 일반 파일이어야 한다. 재시작 때 같은 파일을 유지한다. 자식은 부모 종료 시 강제 종료되며 서비스 중지는 프로세스 묶음 전체를 종료한다.
- PDF 묶음에 896MiB 한도를 적용한다. 개별 요청 832MiB와 별개이며, 자체 점검·감시자도 묶음 안에 포함한다. 소켓 최대 연결 수는 4로 유지한다.
- API는 원본 최대 5MiB를 선확인한다. 초기 자기검사도 API 내부 동시성 제한에 포함한다. 문서를 읽지 않은 Busy 응답 뒤 연결이 reset되는 경우 정확한 12바이트 거부 응답만 인정한다.

## 자원 조건과 한계

Ubuntu22.04의 실제 systemd에서 API 2개와 PDF 분리 서비스를 실행했다. DB는 보호된 TimescaleDB/PG14 컨테이너를 사용했다. 둘을 빌드 호스트의 전용 `gps120.slice` 아래에 넣어 **합계 4GiB·swap 0**을 적용했다. 이 시험 범위 밖의 프로젝트는 넣지 않았다.

| 항목 | 시험 한도 | 정상 시험 peak |
|---|---:|---:|
| 전체 시험 컨테이너 합계 | 4,096MiB | 약 679MiB |
| API 1 | 550MiB | 약 271MiB |
| API 2 | 550MiB | 약 16MiB |
| PDF 서비스 전체 | 896MiB | 약 132MiB |
| DB 컨테이너 | 1,500MiB | 전체 합계에 포함 |

시험 host 컨테이너 한도는 2,400MiB, DB는 1,500MiB다. API 2는 전역 PDF 경쟁·복구 확인용이며 동등한 지속 부하를 주지 않았다. DB는 shared_buffers128MB·max_connections50, 소량 합성 영수증 데이터다. **714,240점 월간 부하나 실제 공유 VPS 용량 인수가 아니다.** 4GiB는 시험 상한이며 필요 RAM 확정치도 아니다.

운영에 남은 조건:

1. 운영의 약 3GiB RAM 안에서 DB·API·PDF·타 프로젝트·OS·백신675MiB의 동시 예산을 확정하거나 분리/증설한다. PDF가 평소 적게 써도 최악 동시 사용 예산은 필요하다.
2. API는 내부 풀 최대 28개를 사용한다. 이번 두 API의 소량 PDF 성공을 근거로 운영 API를 두 개로 늘리지 않는다. DB 전체 연결 예산 문제는 그대로다.
3. 네이티브 운영 PostgreSQL 서비스와 정리·복구 작업을 같은 보호/예산 정책에 묶고, 119 누적 전환/복원에 120 처리기·unit 후보를 합쳐 재검증한다. 이번 DB는 보호된 컨테이너이며 운영 DB unit의 완전 대체 검증이 아니다.
4. 전역 잠금은 **새 `service` 실행 모드 + 공용 잠금 + API Busy 해석**을 함께 설치해야 작동한다. 개발용 직접 자식 실행 fallback은 전역 제한 대상이 아니다. 운영은 별도 소켓 설정을 필수로 확인한다.
5. 본 라운드에서 99→112 암호화 전환·월간 부하·전체 복원은 재실행하지 않았다. 해당 증거는119차이며 새로운 누적 운영 인수와 혼동하지 않는다.

## 사용자 질문: 빌드 백업이 계속 쌓이는가

**현재는 그렇다.** 라운드별 소스·빌드 후보·검증 로그·실패 진단 자료를 별도 디렉터리에 보존한다. 검증용 DB·컨테이너·임시 이미지와 자격증명 정리는 수행하지만, 빌드 후보의 자동 개수/기간 제한은 없다. 11월6일 캐시 정리 도구는 수동 실행용이다. 위치정보 보관·파기 timer와 다른 문제다.

11월13일 읽기 전용 조사: 빌드 호스트 GPS 폴더87개 약21.48GiB, 그 안의 공유 빌드 캐시 약4.77GiB, 전체 디스크 여유 약3.22GiB. 폴더 수는 백업 개수와 같지 않고 서로 다른 기능·펌웨어·검증 작업을 포함한다. 이 호스트는 다른 프로젝트도 함께 쓰므로 디스크 전체 사용량을 GPS 탓으로 단정하지 않는다. [원본 조사](../evidence/runtime120-20261113/build-storage.json).

이번에는 보관 파일을 임의로 삭제하거나 자동 정리를 켜지 않았다. 재포장 중 만들어진 미완성 후보의 복제 바이너리2개만 원본을 보존한 채 정리하고 다시 만들었다. 시험 컨테이너 정리는 위 검증 종료 절차다.

후속 정리 순서:

1. 진행 중인 빌드와 잠금을 확인한 뒤 재생성 가능한 GPS 컴파일 캐시부터 정리한다.
2. 현재 운영본·검증된 복구본·최신 누적 후보와 그 의존 묶음을 보호 목록으로 만든다. 단순히 최근2개만 남기면 이전 라운드 의존성이 사라질 수 있다.
3. 코드·문서·작은 증거는Git에 보존하고, 오래된 중복 압축/풀어놓은 복사본을 분류한다. 실제 DB 백업·키·권리 체크포인트는 빌드 캐시와 같이 지우지 않는다.
4. 보호 목록·해시·외부 보관 확인과 dry-run 결과를 갖춘 빌드 산출물 정리 정책을 별도 적용한다. 새 무거운 빌드 전에 여유 공간을 먼저 확보한다.
