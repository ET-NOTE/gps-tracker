# 위치정보 권리 처리 3차 — 집계 보존 및 `sss` 운영 파기 검증

2026-11-05 · `codex/location-business-prep` · **GPS 운영 반영·대상 SIM 검증 완료**.

이번 라운드는 이전 라운드의 다른 SIM 집계 손실 위험을 해소하고, 사용자가 폐기를 허용한 `sss` 한 SIM의 운영 DB 자료를 실제로 삭제한 단계다. 계정 탈퇴나 모든 저장매체의 개인정보 파기 완료가 아니다. `user@user4.com` 계정 전체, 다른 SIM, dev와 Shield는 변경하지 않았다.

## 집계 처리 변경

운영 v82의 위치·운행 조회는 계정 범위를 검사하는 `location_*_between` 함수로 원본 및 배치를 조회한다. 기존 `location_1min`, `location_5min`, `location_1hour` 연속 집계의 실행 코드 참조는 저장 용량 진단뿐이었다. 운영 소스 아카이브와 기준 커밋 `4b6bbaf958f6d3bdf53a097a6d50eedcdc9e45e5`의 파일 내용을 대조했고, 원본이 없어도 남아 있는 집계를 다시 계산할 이유가 없음을 확인했다.

`0085_preserve_legacy_aggregates.sql`은 세 집계의 **기존 행을 그대로 일반 테이블에 보존**한다. 모든 공개 집계를 잠근 뒤 복사하고, 양방향 `EXCEPT ALL`로 모든 값을 비교한 다음 공식 `DROP MATERIALIZED VIEW`로 기존 연속 집계를 종료한다. 같은 이름으로 보존 테이블을 제공하고 갱신 작업 3개를 제거한다. 예상하지 못한 의존 객체가 있으면 `CASCADE` 없이 전체 트랜잭션을 롤백한다. Timescale 내부 테이블을 직접 변경하지 않는다.

- 전환 전: 1분 8,908행, 5분 2,422행, 1시간 481행, 각 9개 SIM.
- 전환 직후: 모든 SIM의 행 수와 행 내용 지문 일치, 위치 원본 행 수 동일.
- 이후: 명시적으로 허용한 SIM만 `DELETE WHERE device_id=...`로 삭제한다. 다른 SIM을 포함하는 시간 구간을 재집계하지 않는다.
- 현재 지도·운행 조회 방법은 그대로다. 진단 화면에는 `과거 집계 · 자동 갱신 종료`라고 표시한다.
- 보존 테이블로 바꾼 것이 보관 기간을 새로 확정했다는 의미는 아니다. 원본·집계별 보관/파기 정책은 열린 항목이다.

[Timescale 보관과 연속 집계 설명](https://www.tigerdata.com/docs/learn/data-lifecycle/data-retention/data-retention-with-continuous-aggregates), [공식 연속 집계 관리 API](https://www.tigerdata.com/docs/reference/timescaledb/continuous-aggregates)를 참고하고 운영과 같은 PostgreSQL 14 / TimescaleDB 2.19.3에서 검증했다.

## 추가로 발견해 고친 결함

1. 압축 배치 삭제 시 실제 논리 행이 삭제됐어도 `ROW_COUNT=0`이 반환됐다. 쓰기 차단 후 논리 행 수를 먼저 계산하고, 삭제 후 별도 잔여 검증을 통과해야 완료 처리한다.
2. 이벤트를 먼저 지우면 연결 알림 이력의 `ON DELETE SET NULL`이 쓰기 차단 트리거에 걸렸다. 연결 알림 이력을 먼저 삭제하도록 순서를 변경하고 명시적인 회귀 시험을 추가했다.
