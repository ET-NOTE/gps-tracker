# 121차 — 네이티브 DB·작업 서비스와 누적 전환 통합

2026-11-13. **운영 미배포, 스키마112 후보, `activation_ready=false`.** 운영 VPS에 접속하거나 서비스를 변경하지 않았다. 운영의 마지막 관측은119차 문서를 따른다.

## 범위

120차 API/PDF 바이너리를 그대로 사용하여119차 누적99→112 전환을 다시 실행했다. 이번에는 DB를 별도 DB 컨테이너로 띄우지 않고 Ubuntu22.04의 네이티브 PostgreSQL14.24 + TimescaleDB2.19.3 서비스로 실행했다. 단일 API, DB, 마이그레이션, 암호화 전환, 파일 정리, 계정 종료 작업, DB 복원, 권리 체크포인트 작업을 실제 systemd unit에 연결했다. 모두 하나의 폐쇄된 시험 컨테이너 안에 있으며 운영 구성의 자동 설치기가 아니다.

실제 작업 unit은 보호 경로 검사, swap0, core0, `NoNewPrivileges`, 읽기 전용 시스템 경로, 작업별 메모리 한도를 적용한다. 임시 저장소3개는 `nosuid,nodev,noexec` tmpfs이며 DB의 기본 정렬 fallback도 보호 경로로 연결했다. 경로가 없어지면 API/DB/작업 서비스가 함께 중지되고 보호 경로 복구 전에는 시작하지 못하게 했다.

## 실행 중 발견하고 고친 사항

- 시험 환경에서 `LoadCredential`의 전달 디렉터리가 서비스 계정에 읽히지 않았다. 원본 설정은root0700 부모 아래에 두고 작업별 읽기 전용 namespace 경로로 전달하도록 바꿨다. 전역 자격증명 설정은 변경하지 않았다.
- 실제API용 DB권한을 적용할 때 `GPS_DATABASE_MODE=runtime`이 누락되면 API가 마이그레이션을 시도하고 정상적으로 거부됐다. 시험 실행기에 runtime 모드를 명시했다.
- 검증용 전체 이력 연결에 `temp_tablespaces`가 누락되어64MiB fallback이 가득 찼다. 조회는 오류로 중단됐고 일반 디스크로 우회하지 않았다. 검증 연결도 실제API와 같은256MiB 전용 공간을 사용하도록 수정한 뒤 전체 누적 검사를 다시 통과했다.
- 재사용한 시험 코드의 `job` 변수 이름이 서비스 실행 함수를 가렸다. 이름을 분리했다. 종료한 시험 연결이 DB 통계에서 빠지기를 기다리는 절차도 넣었다. 연결 강제 종료로 운영 문제를 숨기는 방식은 쓰지 않았다.
- API 시작 직후 실제 통계 집계의 공유 잠금과 첫 매핑 등록이 겹쳐 일시적인409가 발생했다. 사업 흐름 시험은 시작 작업의 잠금이1초 연속 해제된 것을 확인하고 시작하도록 했다(최대60초, 초과 시 실패). 작업을 끄거나 HTTP 변경 요청을 재시도하지 않으며, 의도적으로 조회 잠금을 잡고 철회/정정의409를 확인하는 기존 검사는 그대로다. 시작 대기 시간은 별도 원본에 기록한다.
- PDF 강제종료 확인 중 `/proc` 파일을 연 뒤 대상 프로세스가 사라지면`ProcessLookupError`가 날 수 있었다. 기존`FileNotFoundError`와 함께 종료 경쟁으로 처리하며 권한 오류 등은 계속 실패시킨다. 처리기 코드는 바꾸지 않았고 PDF10검사·빈`/run` 재기동·최종 상태 검사를 재실행했다.
- **실제 서비스 구성 보완:** 기본 의존성을 가진underlay서비스가sysinit뒤에서 시작하려고 하고, mount는local-fs보다 앞서 시작하려고 해 부팅/종료 순서가 순환했다. 반복 부팅에서DB 시작 작업이 생략되는 문제를 재현했다. underlay를`DefaultDependencies=no`와명시적인remount-fs이후/local-fs이전 순서로 고쳤다. `systemd-analyze verify`의 반환값뿐 아니라 순환/작업삭제 경고도 검사하고 실제 빈`/run` 부팅을2회 연속 확인했다.
- 장애 시험을 같은DB에서 반복할 때 고정된 합성 파일 경로가 기존 정리 이력의고유키와 충돌했다. 시험 파일명을매회고유하게 만들고, 실패한 시험이 다시 만든가짜파일1개만경로·내용·기존정리상태를대조해제거했다. 정리이력은지우지않았다. 실제업무자료변경이나암호화오류무시는없다.
- **실제 작업 도구 보완:** 기존 체크포인트 도구는 유지보수 중에도 일반 작업 연결을 사용해 차단됐다. `GPS_PRIVACY_CHECKPOINT_MAINTENANCE=1`을 명시한 체크포인트 작업에 한해, 정책 테이블 소유권과 다른 클라이언트0건을 확인하고 진행하게 했다. 플래그 없음·runtime역할·다른 접속·암호화 모드 불일치는 거부한다. 유지보수 차단을 내리지 않고 복구하며 일반 정리/계정종료 작업의 차단은 유지한다. 잘못된 체크포인트 해시도 거부한다.

개발 중 실패 출력은 별도 보존하며, 통과한 마지막 출력과 구분한다. API·PDF·SQL 마이그레이션은 이 라운드에서 변경하지 않았다.

## 권한·자원·증거의 경계

- 전체 시험4GiB, DB1,500MiB, API550MiB, 각 작업550MiB, PDF묶음896MiB, swap0. DB버퍼128MB·최대연결50. **공유3GiB 운영 VPS의 용량 인수가 아니다.** 운영의 약742MiB 버퍼·714,240점 월간300초 부하를121차에서 다시 실행하지 않았다.
- API·파일 정리·계정 종료는 `gps-api`, DB·복원·권리 체크포인트는 `postgres`로 실행한다. 암호화 전환은 파일 소유권 보존을 위해root와`CAP_CHOWN`·`CAP_DAC_OVERRIDE`만 유지한다. 모든 작업이 비특권이라는 주장을 하지 않는다. 실제 운영의 정비 계정·DB 복원 권한과 실행 승인 절차는 별도 확정해야 한다.
- 원본 fixture 생성·검증 대조는 격리된root 시험 제어기다. 실제 전환·정리·복원은 보호 unit에서 실행했다. 계정 종료 unit의 빈 대기열 실행과 전체 회원탈퇴 시나리오의 재실행은 같은 주장이 아니다.
- 중첩systemd를 위해 시험 컨테이너에SYS_ADMIN과 완화된 외부 seccomp/AppArmor를 사용했다. 내부망·외부포트0·호스트bind0이다. 이를 운영 컨테이너 보안 설정으로 복사하지 않는다.
- 시험DB의PGDATA/WAL은 폐기할 컨테이너 계층이다. 필드 암호화가 과거WAL·스냅샷·백업의 평문까지 지웠다는 뜻이 아니다. 키/백업/최신 권리체크포인트의 외부 보관·파기 인수도 이번 범위가 아니다.
- 실제 이용자 자료·실물 단말기·외부 통보는 사용하지 않았다. PASS/MFA·관리자 회선·전체TLS 승격·24시간 절전·백신/WAF 실무 검증의 기존 보류 상태는 유지한다.

## 재현과 산출물

`ops/rehearse_runtime121.py`의 고정 빌드 경로에서`setup → run`으로 누적검사를 실행한다. `ops/validate_runtime121.py`는`regressions → restore → faults → pdf → reboot`를 실행한다. `ops/collect_runtime121.py`로 비밀값을 제외한 실제 unit·결과·작은 보호도구 묶음을 보존한 뒤 라벨이 일치하는 시험 컨테이너와 네트워크만 제거한다.

최종 소스 커밋은`cce99a67c030e132dc8dcecb28c9bc74de1e4820`이다(본 구현`55bc29c`, 시작 대기`971409b`, 프로세스 관측 경쟁`8b5b2ef`, 시작 순서·반복 fixture`cce99a6`). 정본git archive의`971409b`로 누적 전환부터 권리 회귀·복원·경로 장애까지 다시 통과했다. PDF 검사 함수의 종료 경쟁 처리 후 PDF10검사를 통과했고, 시작 순서 수정 후 경로 장애·작업 복구·빈`/run` 부팅2회·최종 상태를 재확인했다. 변경과 검증 범위를 분리해서 기록하며 마지막 커밋으로 전체 누적시험을 다시 했다고 주장하지 않는다. 최종 묶음의전체ops380파일도git archive와바이트대조했다. API/PDF는120차 해시,99 기준 바이너리는116차 해시를고정한다. 새Rust빌드캐시를만들지않았다.

121 보호도구는665,276바이트이며변경없는바이너리를다시묶지않고120후보를의존성으로명시한다. 운영99용독립설치기가아니다. SHA-256은`e8208d08c2a1d20a4f6b362713814158eec3aaf627d14a89a5f7744de7acdf07`, 경로와각파일해시는[명세](../evidence/runtime121-20261113/candidate-manifest121.json)에있다. 13:14KST에시험컨테이너·내부망을제거하여시험DB/WAL·키·덤프를폐기했다. 기존컨테이너32개의식별자/시작시각/재시작수와필수보존산출물5개해시는그대로다. 빌드호스트여유는7.778GiB이며자동보관제한은추가하지않았다.

## 다음 운영 인수 조건

1. 공유 VPS의 전체RAM·DB연결·디스크I/O 예산을 실제 프로젝트 구성으로 확정한다. 필요하면 GPS를 분리하거나 증설한다. 이번4GiB 시험을3GiB 운영 승인으로 사용하지 않는다.
2. 확정한 한도로 네이티브 후보의 월간 지속 부하·수집·조회 취소·PDF와 정리 작업의 동시 실행을 검증한다. 운영 API 증설은 하지 않는다.
3. 별도 키, 보호된 복원본, 최신 권리체크포인트, 회사 정책과 정비창을 고정한 후 운영 전환 절차를 인수한다. 아직 운영에 반영하지 않는다.
