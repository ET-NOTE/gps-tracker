## 해결한 파일 삭제 결함

기존 서류 삭제는 DB 행을 먼저 지운 뒤 파일 삭제 오류를 무시했다. 차량 사진 교체에는 이전 파일의 정리 작업이 없었다.

1. 서류 삭제/경로 변경, 장치·차량 사진 삭제/교체 시 DB 트리거가 **같은 트랜잭션**에서 정리 작업을 기록한다. FK 연쇄 삭제도 포함하고, 롤백되면 정리 작업도 롤백된다.
2. 작업은 계정·장치의 FK 삭제에 따라 사라지지 않는다. 여러 계정·차량이 같은 파일을 쓰면 각 참조 제거의 출처도 남긴다.
3. 실행기는 참조 테이블을 먼저 잠그고 남은 참조를 확인한다. 공유 파일은 `shared`로 보존한다. 새 참조 추가와 삭제가 동시에 진행돼도 확인과 파일 삭제 사이에 참조가 끼어들지 못한다.
4. 허용한 업로드 하위 경로만 처리한다. 상위 경로 이동, 외부 URL, 심볼릭 링크, 일반 파일이 아닌 대상, 하드링크가 여러 개인 파일은 차단한다. 설정된 저장소 자체가 없으면 삭제 완료가 아닌 재시도로 남긴다.
5. 파일시스템 오류는 `retry`, 검토가 필요한 경로는 `blocked`, 실제 로컬 부재가 확인되면 `local_absent`다. 파일 삭제 후 DB 커밋 전에 중단돼도 다음 실행이 부재를 재확인한다.
6. `local_absent`는 해당 서버 경로의 부재만 뜻한다. 백업·스토리지 하위 복제·외부 전달본·물리 매체의 완전 소거를 증명하지 않는다.

기존 미참조 파일을 소급해서 일괄 삭제하지 않았다. 파일을 쓴 뒤 DB 등록 자체가 실패한 업로드의 고아 파일, 기존 고아 파일 전수 조사 및 처리도 별도 항목이다. 운영 반영 시 `device_documents`, `rental_photos`, `fleet_expense_receipts`는 모두 0행이었고 새 정리 큐도 0건이었다. 이번 배포에서 운영 파일이나 과거 기록을 추가로 삭제하지 않았다.
