- `GPS_LOCATION_TEMP_TABLESPACE`는 단일 전용 이름만 허용한다. 기본 tablespace·쉼표 목록·빈 값 등은 거부한다.
- 연결을 새로 만들 때와 풀에서 빌릴 때마다 존재·CREATE 권한을 확인하고 해당 세션의 `temp_tablespaces`를 설정한다. 설정이 사라지거나 권한을 회수하면 기존 풀에서도 조회가 차단된다.

- **이 SQL 검사는 파일시스템·swap 보호를 증명하지 않는다.** 운영 전 호스트 검사와 부팅·마운트 의존성 검증이 별도로 필요하다.

PostgreSQL은 역할 기본 설정에 지정한 tablespace가 없거나 접근할 수 없으면 그 설정을 무시할 수 있다. 따라서 이름을 설정하는 것만으로는 보호되지 않는다. [PostgreSQL14 설정 문서](https://www.postgresql.org/docs/14/runtime-config-client.html).

더 나아가 유효한 tablespace의 물리 디렉터리에서 임시 파일을 만들지 못하면 기본 tablespace로 다시 시도한다. 이를 실제 경로 소실 시험으로 재현했다. 기본 임시 경로도 함께 보호해야 한다. [PostgreSQL14 `OpenTemporaryFile` 구현](https://raw.githubusercontent.com/postgres/postgres/REL_14_STABLE/src/backend/storage/file/fd.c).

재실행 도구는 `ops/runtime117.py`, `runtime117_faults.py`, `preflight_temp117.py`이며 모두 고정된 합성 시험 공간만 대상으로 한다. `setup`의 초기 DB 생성은 미설정 파일럿이라 운영 보호 증거가 아니다. 최종 API를 준비한 뒤 `protected-final` → `runtime117_faults.py` → 업무 회귀 → `probe` → `preflight_temp117.py` → `cleanup` 순서로 사용한다. 비교용 `limited`는 보호 구성을 만든 뒤 재사용하지 말고 새 시험 환경에서 실행한다. 운영에 이 도구를 적용하지 않는다.

## 7. 다음 118차와 운영 전환 조건

1. **공유 DB 전체 연결·메모리 예산**: 다른 프로젝트 상한과 정비/취소/백그라운드 여유를 포함한다. 단일 API를 유지하며 필요한 제한은 격리 환경에서 먼저 검증한다.
2. **운영 임시 데이터 보호 구성**: 전용·기본 fallback 임시 파일, 복호화 가능한 모든 프로세스의 swap/core, 마운트 해제·부팅·복구 순서까지 검증한다. 메모리만으로 충분한지 또는 별도 암호화 저장소가 필요한지 자원 예산과 함께 결정한다.
3. 해당 구성을 116 누적 전환·복구 절차와 결합해 최종117 API로 다시 검증한다. 마운트 소실 시 일반 디스크가 노출되지 않도록 서비스 의존성과 실패 차단을 확인한다.
4. 그 뒤 운영 최신 상태·키/외부 보호 백업/권리 체크포인트·정책·수신 중단 대응·정비 시간을 고정하고 운영 전환을 판단한다.
